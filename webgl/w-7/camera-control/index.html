相机控制与视角

用轨道相机展示视角移动、缩放和旋转的交互控制。

开场问题：你做了个 3D 零件展示页，想让人绕到背面看看。你把模型本身转了过去，结果背是转过来了，可原本朝上的顶面跟着歪到了侧面——连从上方打来的光都好像跟着太阳一起转了。用户想动的是眼睛，你却动了物体。

视角切换实现

你已经有了 View 矩阵，它负责把世界坐标变换到相机空间，本质就是把相机搬到原点、视线对齐轴。于是「换视角」这件事，最后都归结为一个问题：相机该放在哪、看向哪？

手里只有最原始的做法——直接给相机一个位置 eye 和一个目标点 target，那你就得为用户的每一次操作手动算数：

  • 用户想「往左转 30 度」，你得自己推出 eye 的 x、y、z 各该改成多少，三角函数在脑子里绕三圈还容易错。
  • 用户想「拉近一点」，你得把 eye 沿着朝向目标的方向缩，方向向量也得现算。
  • 转和缩放同时发生时，三个坐标互相牵连，改一个不动另一个，相机就飘。

问题于是收束成一句：有没有一组参数，让「绕圈」和「缩放」各只改一个数，而且互不干扰？

相机位置与朝向

最朴素也真能跑的做法：维护 eye 和 target，用 lookAt(eye, target, up) 生成 View 矩阵。想换视角就改 eye，把相机沿一个圆圈挪动，就能绕着物体转。

这个方案做对了一件事：它把「观察」和「被观察」分开了。改 View 矩阵不会碰模型数据，物体该在哪还在哪，视角变化只是换个机位。

参数耦合与误差

  • 「转 30 度」这种对用户最自然的说法，落到 eye 上却变成三个坐标的联立修改，转久了还会累积误差。
  • 缩放和旋转共用同一组 x、y、z，想单独调一个，另外两个就会跟着漂。
  • 观察点固定在原点：想让相机绕着零件某个偏离原点的部位转，你只能整个场景平移。
  • 相机走到目标点正上方或正下方时，视线方向与 up 共线，lookAt 求出的坐标系退化，画面会突然翻转甚至整体消失。

球坐标参数化

看清了病根——「相机在哪」用笛卡尔坐标描述不合适，于是换一组更贴合「看着一个东西绕圈」的参数：球坐标。用半径 radius、方位角 theta、仰角 phi 加上目标点 target，就能完整描述相机相对目标的位置。整个流程是：

  1. 维护半径 radius、方位角 theta、仰角 phi 与目标点 target。
  2. 由球坐标换算相机位置：eye = target + r * (sin(phi)·cos(theta), cos(phi), sin(phi)·sin(theta))。
  3. 用 lookAt(eye, target, up) 生成 View 矩阵。
  4. 把 View 与 Projection 相乘得到 VP（本课再合并为 uMVP），传入顶点着色器。

换参数的好处立刻显现：每个交互只动一个数——滚轮改 radius 就是拉近拉远，水平拖动改 theta 就是绕目标左右转，垂直拖动改 phi 就是上下转。三者独立，互不牵连，也不再需要你在脑子里解三元方程。

lookAt 本身也值得说清：它拿视线向量（eye - target）与 up 做叉积，重建出右、上、前三个互相正交的基向量，组成旋转部分；再配上把 eye 平移到原点的平移，合起来就是 View 矩阵。

必须记住的边界：仰角 phi 要约束在 (0, π) 的开区间内，也就是不要贴到 0 或 180 度。一旦越过天顶或天底，up 与视线共线，lookAt 的基退化，画面会瞬间翻转。演示里滑杆范围是 0.1 到 3.04 而不是 0 到 π，正是为了避开这两个奇点。

还有一点要分清：View 矩阵只决定「从哪看」，不会修改模型数据本身。轨道相机适合围绕单个物体观察；如果你要做的是第一人称漫游，通常直接累加 yaw / pitch 与位移，而不是套用这套绕目标的球坐标。

轨道相机解耦

轨道相机把「相机在哪」翻译成三个互相独立的旋钮——半径管远近、方位角管左右、仰角管上下，再用 lookAt 把它们收成一个 View 矩阵。换视角就是改参数，永远不用碰模型数据。

「轨道相机」用球坐标 (radius, theta, phi) 加目标点描述相机相对目标的位置，再由 lookAt 生成 View 矩阵，从而围绕目标旋转与缩放。必须记住：phi 要限定在 (0, π) 内，否则 up 与视线共线会导致画面翻转；View 只改变观看方式，不改变模型数据。
