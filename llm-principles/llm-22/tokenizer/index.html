Tokenizer与子词分词

Tokenizer 分词器把文本切成有限词表可查的子词 token 并映射成整数 ID，主流 BPE 从字符出发反复合并高频相邻对；正因模型看到的是 token 而非字符，strawberry 才数不对 r、中文也更耗 token。

开场问题：模型眼里的「字」是什么？为什么 strawberry 数不对 r 的个数？

文字切分为可查token

前两课从头到尾摆弄的都是「词向量」——一串数字。可键盘上敲进去的「我 是 一只 小猫」是文字，不是数字，中间缺了一步：谁把文字变成向量？模型内部藏着一张有限的查找表，文字进来就查——查到哪个单元，就取出对应那一行向量。但表必须是有限的，不可能为每一种文字串都留一行，所以文字进门的第一步，必须先切成「表里查得到的单元」。这一步叫分词（tokenize），切出来的每一块就是一个 Token。

副作用：问顶尖模型「strawberry 里有几个字母 r？」，它常一本正经答「2 个」，正确答案是 3 个。不是它语文没学好——strawberry 常常整块就是表里的一个 token、不可分割。模型眼里它不是 10 个字母，而是一坨整体，就像你把「中国」当一个词，从不去数它有几个笔画——那 3 个 r 藏在整体内部，对模型根本不可见。

最小方案两条朴素路

  • 按「词」切：一个词一个 token，看着自然。但英语词形几乎无穷（单复数、时态、人名、拼写错误、新造词），词表开到上百万都兜不住；更糟的是遇到表里没有的词，模型只能吐「未知」占位符 [UNK]，信息全丢。中文更尴尬——根本没有空格告诉你词的边界。
  • 按「字符」切：词表缩到几千甚至 256，再也不怕生词；但序列长得吓人，「understanding」=13 个 token，一篇文章 token 数翻好几倍——而注意力的复杂度是 O(n²)，序列翻倍、成本就翻四倍；模型还得从头学「c-a-t 合起来才是猫」。

两堵墙逼出一个折中：子词（subword）。常见的整词当一个 token，生僻的长词拆成几个常见片段，实在没见过的退到字符/字节，保证永远不会「完全不认识」。剩下唯一的问题：这些片段从哪来、按什么规则切？

迭代BPE合并高频对

现代大模型几乎都用 BPE（字节对编码），它造词表的办法像玩积木——从零开始，谁老黏在一起，就把谁俩焊成一块：

  1. 先把所有词拆到最小单位（字符/字节），每个字符就是一个 token。
  2. 扫一遍语料，数哪一对相邻 token 出现得最频繁。
  3. 把这一对合并成一个新 token，加进词表。
  4. 重复第 2、3 步，直到词表攒到目标大小（比如 5 万）。

拿三句话当迷你语料走两轮：①我爱吃苹果，苹果很甜。②红苹果和绿苹果都是水果。③水果店卖水果。全拆成单字后，「苹 果」对出现最多（① 2 次 + ② 2 次 = 4 次），第 1 轮合并成「苹果」；重新数，「水 果」最多（② 1 次 + ③ 2 次 = 3 次），第 2 轮合并成「水果」。套回「苹果是水果」就切成了「苹果 / 是 / 水果」3 个 token。数、合并、再数、再合并几万轮之后：高频词整个变成一个 token，中频词留成几个常见片段，生僻字才碎到单字——既不爆词表，也不会完全不认识。

掀开真相一串整数

切出 token 只是第一步，token 并不以「文字」的样子进模型。每个 token 在词表里有个固定编号（ID），模型真正吃进去的是一串整数；每个 ID 再去巨大的嵌入表里取出自己那一行数字——这就是第 15 课的词向量（大模型里叫 embedding）。一句话进模型是：文本 → 切成 token → 查编号 ID → 查嵌入表得向量 → 加位置 → 进注意力层。分词器是这条流水线的第一道工序。

回头看开头谜题就通透了：模型看到的是 ID 7124（straw）和 15717（berry）两个整数以及对应向量。字母 r 从一开始就没进过模型的视野。它答不准，不是笨，是因为这道题问的东西在它的输入里压根不存在。

发现不足中文吃亏

GPT-4 的词表（tiktoken，约 10 万 token）以英文语料为主，中文占比较小。后果是同样的意思中文往往要花更多 token：英文「The quick brown fox」= 4 tokens，中文同义句可能要 8 tokens——上下文窗口能放的汉字更少，按 token 计费也更贵。

既然 token 不对应字符，模型就栽在一些只跟字母有关的任务上，根源全是一个：它看不见 token 内部的字母。例如数字母（一个 token 里的 r 数不清）、逆序拼写（把 HELLO 倒成 OLLEH 要逐字符操作）、押韵 / 藏头（每行首字母拼成词常对不齐）。这些不是智力问题，而是 tokenization 的固有盲区。缓解思路是让模型访问字符级信息，或干脆用字节级 tokenizer——但代价又回到「序列太长」那堵墙上，仍是权衡。

分词流水线首道工序

模型看到的不是文字，是 token 的整数编号。按词切会爆词表、按字符切序列太长，BPE 折中——从字符出发、反复合并最频繁的相邻对。本课要点：两条朴素路的墙；子词折中（常见整块、生僻拆片段、永不完全不认识）；BPE 的「数频率 → 合并 → 重复」规则；真正输入是 文本 → token → 整数 ID → 向量；以及 token 内部字符不可见带来的数字母、逆序、藏头等既有盲区。

「Tokenizer 分词器」是指把文本切成有限词表里可查到的 token（主流是 BPE 子词切法：从字符出发反复合并高频相邻对）并映射成整数 ID、再经嵌入表转为向量的第一道工序；正因模型看到的是 token 而非字符，strawberry 才能数错 r、中文也需更多 token。
