模块配置、!default 与 with

让样式库暴露有限配置项，并在首次 @use 时完成定制。

开场问题：在入口写下 @use "library" with ($radius: 20px)，编译器却报错说这个模块已经被加载过、配置不生效——你明明只写了一处 with，到底是谁先加载了它？

样式库定制入口

你把公司的一整套按钮、表单、提示样式打包成内部样式库，希望使用方既不必改库源码，又能把它调成自己品牌的圆角、前缀和主色。这就是「可配置」的诉求：库要暴露少量开关，同时保护内部实现不被随意破坏。

难点在于，Sass 的模块是只加载一次的。谁先加载、在哪加载、配置在哪个时刻生效，直接决定了这套定制机制能不能成立。搞不清加载顺序，就会出现「配置写了却报错」这种看起来毫无道理的失败。

缺省与全局变量

最朴素的做法是不给默认值，让使用方必须传；或者干脆把变量做成全局变量，谁都能改。前者让库变得难用——只想改圆角的人也得把所有变量填一遍；后者则回到 @import 时代的全局污染，任何一处赋值都可能影响别处的输出。

这个方向想对了一件事：可复用的库需要留出定制入口，而不是要求使用方 fork 一份源码去改。问题只是入口的形态没选对。

全量配置暴露实现

  • 把所有内部变量都做成配置项，等于把实现细节全部暴露，内部一改结构，所有使用方都要跟着改。
  • 全局变量没有作用域边界，一处赋值影响全局，很难追溯到底是哪次覆盖生效。
  • with 配置必须唯一，且必须发生在任何其他加载之前；一旦模块先被别的文件 @use 过，这里就会被忽略并报错。
  • 配置在首次加载时就冻结，之后不能二次修改，把它当成运行时主题开关会直接失败。
  • 复杂配置（比如按主题分别给一批值）用 with 表达起来很笨重。

可覆盖缺省值

不推翻「留出定制入口」，而是让入口有默认、有边界、且只在加载时生效一次。模块用 !default 声明「可被覆盖」的顶层变量：如果变量已经有值就保留原值，否则赋默认值。使用方在首次 @use 的 with 子句里传值，即完成定制。

一个样式库通常只暴露少量开关，下面这几项就是典型的可配置项：

配置项类型默认值作用
$prefixstring"app"生成类名的前缀
$radiusnumber12px按钮与卡片的圆角
$brandcolor#e85d04主色令牌，供派生使用
$densitynumber1尺寸缩放系数

实现顺序可以这样安排：

  1. 用 !default 为可配置的顶层变量提供默认值。
  2. 在应用入口首次 @use 的 with 子句传入配置。
  3. 让配置驱动选择器前缀或令牌，产出期望的样式。
  4. 把所有可配置项写成文档表格，说明类型、默认值与影响范围，方便使用者对照。

回头看开场的报错就清楚了：with 之所以「被忽略」，几乎总是因为该模块在此处之前就已经被别的文件加载过。模块只有第一次加载时能配置，第二次想改已经晚了。排查这类问题时，要顺着整个依赖链检查加载顺序，看是谁抢先把它引入了。

三条边界：不要把所有内部变量都做成配置项，只暴露真正需要定制的少数开关；配置在首次 @use 的 with 中确定后无法二次修改，需要运行时切换的主题应交给 CSS 自定义属性；遇到 with 传值失败，优先检查依赖链里是否有更早的加载。

with配置即时生效

配置一次即冻结

!default 与 with 共同回答了「库怎么既让使用方定制、又守住内部实现」：库用 !default 给出可覆盖的默认值，使用方在首次 @use 时传配置，配置一次冻结、只此一回。理解「模块只加载一次」这条规则，配置失败的原因就一目了然。

「!default 与 with」!default 为顶层变量声明「可被覆盖」的默认值：变量已有值则保留，否则取默认值。使用方在首次 @use 的 with 子句中传值完成定制。由于模块只加载一次且配置在首次加载时冻结，同一模块的配置必须唯一、且必须发生在任何其他加载之前，否则会被忽略并报错；运行时可变主题应改用 CSS 自定义属性。

关键代码

SCSS
// _library.scss
$prefix: "ui" !default;
$radius: 0.5rem !default;
.#{$prefix}-button { border-radius: $radius; }

// app.scss：配置必须出现在模块首次加载时
@use "library" with (
  $prefix: "forest",
  $radius: 0.75rem,
);
