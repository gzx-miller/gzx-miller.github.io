配置管理：@nestjs/config 与环境

用多环境部署场景展示 ConfigModule 读取 .env、自定义配置与启动校验。

开场问题：数据库密码一开始直接写在代码里，本地跑得好好的；换到生产要改一次、换回本地又要改回来，某次提交还把它带进了仓库——配置到底该放在哪？

配置项随环境变化

几乎每个应用都会遇到同一类值：端口、数据库地址、Redis 过期时间、第三方密钥。它们的共同点是代码逻辑不变，值却随环境变化——本地连 localhost，生产连内网域名，测试用的又是另一套。这些值一旦写死在源码里，「同一份代码部署到多个环境」这件事就做不到了。

把配置抽出来是必然的，但抽到哪里、怎么读、读不到怎么办，每一步都有代价。处理不好，就会得到最难排查的一类问题：本地能跑，线上爆，而且现场离病因很远。

环境变量文件读取

最省事的做法：把值放进 .env 文件，代码里用 process.env.PORT 这样的写法去读。

这一步做对的是最关键的一件事：配置与代码分离。同一份代码，部署时只要替换环境变量，行为就变了，本地开发与生产运行的差异不再靠改代码来切换。这是所有后续方案的基础，方向完全正确。

散落读取与类型隐患

  • process.env 的读取散落在各个文件里，同一个配置项可能在多处出现，改一处漏一处。
  • 环境变量永远是字符串：process.env.DB_PORT 读出来是 '5432'，不手动转换就会参与字符串拼接而不是数值计算。
  • 没有任何类型与默认值信息，拼错一个变量名只会拿到 undefined，而且要到运行中才暴露。
  • 缺失的必填项不会让应用拒绝启动，而是等到某次请求才崩，错误现场和病因隔着很远。
  • .env 一旦忘了加进忽略列表，密钥就被提交进仓库，等于公开了生产凭证。
  • 每个模块都要单独引入一次 dotenv 之类的库，初始化顺序本身又成了新的隐患。

统一配置中间层

不推翻「环境变量」，而是给读取过程加一层统一的中间层。ConfigModule.forRoot() 在启动时读取环境文件并合并成一个配置对象，之后所有代码只跟这个对象打交道，不再直接碰 process.env。这一步把「到处读」收敛成「一处装配、处处注入」。

读取的入口是 ConfigService，它通过构造器注入，和普通服务没有任何区别。取值时可以带上泛型来获得类型提示，例如 this.config.get<string>('database.name')。但要记住，这里的泛型只是给 TypeScript 看的类型断言，运行时并不会真的转换类型——它让调用方知道期望的类型，却不能代替转换。

三个关键选项：isGlobal: true 把配置模块注册为全局模块，之后任何模块都能直接注入 ConfigService，不必在每个模块的 imports 里重复声明；load 传入配置工厂数组；envFilePath 用数组声明多个文件及其加载顺序。

与其让各处自己解析字符串，不如把「默认值 + 类型转换」集中到配置工厂里。工厂就是一个返回普通对象的函数，它在读取环境变量的同时完成 parseInt 与兜底：端口读不到就取 3000，数据库名读不到就取一个本地默认值。这样业务代码拿到的已经是正确类型的值，ConfigService 只负责按路径把它取出来。

环境文件按优先级分层，是这个方案的另一半。常见的组合是：.env 放公共且不含密钥的配置并提交仓库，.env.local 放本地覆盖、不进仓库，.env.production 放生产专用配置。加载顺序决定覆盖关系，越靠后的文件优先级越高。还有一条必须记住的规则：真实的系统环境变量优先级高于任何环境文件——所以在 docker 或 CI 平台上用 Secret 注入的值会覆盖文件里的默认值，这正是生产环境的正确用法。

最后是启动校验。配置问题的理想暴露时机是应用启动的那一刻，而不是某次请求。用 Joi 或 class-validator 对配置对象声明校验规则，必填项缺失或格式不对就抛出错误、让进程直接起不来——这叫「快速失败」：一个起不来的实例，远比一个能启动、却会在半夜某个请求里崩掉的实例安全。

开发生产读值对比

类型校验与默认值

配置管理的本质，是把「随环境变化的值」从代码里请出来，并给读取过程加上类型、默认值与校验三道保险：ConfigModule.forRoot() 统一装配，配置工厂集中做转换与兜底，ConfigService 负责注入读取，启动校验保证缺失即失败。密钥只走环境变量与 Secret，永远不进仓库。

「配置管理」由 @nestjs/config 提供：ConfigModule.forRoot() 读取 .env 等文件并合并配置，isGlobal: true 后所有模块可直接注入 ConfigService，用 this.config.get<string>('database.name') 按路径读取（泛型只是类型断言，不做运行时转换）。默认值与类型转换集中在 load 的配置工厂；真实系统环境变量优先级高于环境文件，敏感配置只进 Secret，并用 Joi 等做启动校验以避免带病启动。

关键代码

TypeScript
// config/configuration.ts —— 自定义配置工厂（类型安全）
export default () => ({
  port: parseInt(process.env.PORT ?? '3000', 10),
  database: {
    host: process.env.DB_HOST ?? 'localhost',
    port: parseInt(process.env.DB_PORT ?? '5432', 10),
    name: process.env.DB_NAME ?? 'classroom',
  },
  redis: {
    ttl: parseInt(process.env.REDIS_TTL ?? '3600', 10),
  },
})

// app.module.ts —— 全局配置模块
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,               // 所有模块都可注入 ConfigService
      load: [configuration],        // 加载自定义配置工厂
      envFilePath: ['.env.local', '.env'],
    }),
  ],
})

// 任意服务中注入使用
@Injectable()
export class AppService {
  constructor(private readonly config: ConfigService) {}

  getDbName() {
    return this.config.get<string>('database.name')
  }
}
