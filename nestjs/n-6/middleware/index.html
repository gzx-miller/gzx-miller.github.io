中间件：请求链路的洋葱模型

用请求日志链路展示中间件与守卫、管道、拦截器的执行顺序：洋葱模型的层层包裹。

开场问题：你把鉴权逻辑写进了中间件，运行时却发现反射不到 @Roles() 的元数据；还有一次忘了调用 next()，请求就一直卡在那里没有响应——中间件究竟站在请求链路的哪一层，它到底能拿到什么、拿不到什么？

跨路由公共逻辑

你在维护一个课程平台，每个请求进来都想记一行访问日志，另外还要处理跨域（CORS）、Cookie 解析这些「跟具体路由无关」的事。这些活儿有个共同点：它们发生在业务之前，而且对所有路由都成立，跟某个具体接口是查课程还是报名的逻辑没有半点关系。

如果不在请求链路的最前面统一处理，这些代码要么塞进每个处理器，要么散落各处重复一遍。更糟的是，日志需要在「匹配到具体路由之前」就记下来，CORS 需要在响应头里提前写入——这些时机是处理器方法内部根本够不着的。不解决它，你要付的代价是：横切逻辑与业务逻辑搅在一起，时机又对不上。

处理器内记录日志

最省事的做法，是直接在需要的那几个控制器方法里动手：方法开头写一行 console.log(req.method, req.url)，需要跨域就手动往响应头里塞 Access-Control-Allow-Origin。

它做对了一件实在事：日志和跨域确实被处理了，而且就写在你最熟悉的地方。接口少、需求临时时，这样最快，改动范围也最小。

日志重复与时机偏差

  • 与路由无关的逻辑却按路由复制，几十个接口就是几十份相同的日志代码。
  • 时机不对：日志要求「请求刚进来」就记，而处理器执行时路由、参数都已经处理过一轮了。
  • CORS、Cookie 解析这类需要直接操作原始 req / res 的活，写进处理器里很别扭。
  • 没有统一入口按路径批量限定范围，比如「只对 /courses 开头的请求生效」。
  • 想给整体加一个访问审计时，只能一个个接口补，漏掉一个就是一条盲区。

中间件前置位置

不推翻「在业务前处理请求」，而是给它一个独立于路由、又站在最前面的位置——这就是中间件（Middleware）。它是请求生命周期的最外层，直接操作原始的 req / res，并且在守卫之前执行。只写一个 use(req, res, next) 方法，所有匹配到的请求都会经过它。

中间件里有一条约定的铁律：处理完必须调用 next() 放行。它相当于把请求交给链路的下一站；不调用 next()，请求就会一直悬在中间件里，永远不会到达业务。所以异步逻辑（比如读取 Cookie、写日志）要 await 完成之后再放行。

「对哪些路由生效」由 MiddlewareConsumer 声明：consumer.apply(LoggerMiddleware).forRoutes('courses') 让日志中间件只作用于 /courses 开头的请求；想排除某些路由，用 exclude()；而作用到全部路由的全局中间件，直接在启动时用 app.use() 注册。CORS、helmet 这类安全中间件，通常就走全局这条路。

真正理解中间件，要把它放回整条请求链路里看。NestJS 把一次请求的处理拆成了环环相扣的几层，像一个洋葱：越靠外的层越「通用」，越靠内的层越「业务」。请求由外向内穿，响应再由内向外返回：

  1. 中间件：链路最外层，拿到原始 req / res，记录日志、解析 Cookie，调用 next() 放行。
  2. 守卫：决定请求是否放行——鉴权与授权在这里做，它能读到完整的 ExecutionContext 和反射元数据。
  3. 拦截器前置：进入处理器之前的一段逻辑，比如记录开始时间。
  4. 管道：校验并转换参数，不合法就直接拒绝。
  5. 处理器：控制器调用服务，执行真正的业务。
  6. 拦截器后置：用 map / tap 包装响应、统计耗时。
  7. 异常过滤器：上面任一环节抛出异常，都在这里被捕获并转成统一的错误响应。

看清楚这条链路，「中间件拿不到 @Roles() 元数据」就好解释了：中间件太靠外，它只有原始的请求对象，没有完整的执行上下文。而 @Roles() 这类元数据要靠 ExecutionContext 反射出来，这属于守卫的能力范围。所以「涉及角色授权就交给守卫」，不是随口的建议，而是由层次位置决定的职责边界。

两个必须记住的点：其一，next() 务必调用，异步逻辑完成后放行，否则请求会一直悬挂；其二，中间件适合日志、CORS、请求体解析、Cookie 解析这类与路由无关的横切逻辑，涉及鉴权与授权的判断应写进守卫，那里才有完整的上下文。

洋葱模型分层含义

中间件站在请求链路的最外层，用最少的约定（一个 use 方法加一次 next()）把日志、CORS、Cookie 解析这类与路由无关的横切逻辑集中起来。而「洋葱」的真正含义在于分工：每一层只管自己该管的事，越靠外越通用，越靠内越贴近业务。搞清层次，就知道某段逻辑到底该写在哪一层。

「中间件与洋葱模型」中间件实现 NestMiddleware，在守卫之前执行、直接操作 req / res，用 apply().forRoutes() 限定生效范围、exclude() 排除路由，全局中间件用 app.use() 注册；next() 不调用会导致请求悬挂。执行顺序为中间件 → 守卫 → 拦截器前置 → 管道 → 处理器 → 拦截器后置 → 异常过滤器，请求由外向内穿、响应由内向外返回，越外越通用、越内越业务。中间件拿不到完整的 ExecutionContext，鉴权授权应交给守卫。

关键代码

TypeScript
// logger.middleware.ts —— 中间件是请求进入路由前的第一站
@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: () => void) {
    console.log(`${req.method} ${req.originalUrl} @ ${new Date().toISOString()}`)
    next()  // 必须调用 next() 放行，否则请求卡死
  }
}

// app.module.ts —— 配置中间件作用于哪些路由
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(LoggerMiddleware)
      .forRoutes('courses')          // 仅对 /courses* 生效
      // .forRoutes({ path: '*', method: RequestMethod.ALL })
  }
}
