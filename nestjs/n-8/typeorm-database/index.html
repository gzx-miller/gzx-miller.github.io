TypeORM 数据库：实体、仓储与事务

用课程报名业务展示实体定义、Repository 模式与事务：名额不足时整笔回滚。

开场问题：报名接口先查询课程、判断名额、再把报名人数加一，三步分开写。两个人同时抢最后一个名额，为什么两边都提示「报名成功」，课程却超卖了？

名额检查与计数递增

课程报名这件事，落到数据库上就是一句话：确认已报名人数还没到容量，然后把已报名人数加一。看起来是「查一下、判一下、写一下」，三步都很普通。

可当请求并发到来时，问题就藏在这三步之间的缝隙里。两个请求可能交替执行：A 读到「还剩 1 个名额」，还没来得及写回，B 也读到了同样的「还剩 1 个名额」——两边都通过了检查，都执行了加一，于是容量被击穿，报名人数超过了上限。不解决它，你要付的代价是：校验逻辑在并发下形同虚设，数据被悄悄写坏。

仓储顺序调用

最省事的做法，是顺序调用仓储（Repository）：findOneBy(Course, { id }) 查出课程，判断 enrolled 是否够用，再用 increment 把人数加一。TypeORM 的实体用装饰器描述表结构，Repository 则提供类型安全的增删改查：

@Entity('courses')
export class Course {
  @PrimaryGeneratedColumn() id: number
  @Column({ length: 100 }) title: string
  @Column({ default: 0 }) capacity: number
  @Column({ default: 0 }) enrolled: number
}

它做对了两件事：表结构被清晰地写在了类上，读写走的是类型安全的 API，不用自己拼字符串 SQL，字段写错编译期就能发现。单请求、无并发的场景下，这个顺序写法完全正确。

检查写入竞态窗口

  • 「查 → 判 → 写」三步之间存在窗口，并发请求会互相插队，检查形同虚设。
  • 中途任一步失败时，前面已经写下的改动不会自动撤销，数据可能停在半截状态。
  • 手动 new 一个 Repository 既啰嗦又难以测试，依赖关系也不透明。
  • 表结构变更靠手工改库，容易和实体定义脱节，上线时对不上。

事务原子边界

不推翻「检查后写入」，而是给这组写操作加一个原子边界，让它们要么全部成功、要么整体不发生。分三步补齐。

第一步，解决「Repository 从哪来」。用 @InjectRepository(Course) 注入实体对应的仓储，交给依赖注入容器管理，无需手动 new：

constructor(
  @InjectRepository(Course)
  private readonly courseRepo: Repository<Course>,
) {}

第二步，也是最关键的一步，用事务把多步写操作包起来。manager.transaction 接收一个回调，回调内的所有语句都在同一个数据库事务中执行：任一步抛错，整笔操作整体回滚；全部走完，才统一提交。

await this.courseRepo.manager.transaction(async (manager) => {
  const course = await manager.findOneBy(Course, { id: courseId })
  if (!course) throw new NotFoundException('课程不存在')
  if (course.enrolled >= course.capacity) throw new BadRequestException('课程名额已满')
  await manager.increment(Course, { id: courseId }, 'enrolled', 1)
})

报名流程因此变成一条清晰的链路：

  1. 请求携带 courseId 到达报名接口。
  2. 事务开启，查询课程并检查 enrolled 是否小于 capacity。
  3. 名额充足则自增 enrolled；不足则抛出 BadRequestException，整笔回滚。
  4. 事务提交，返回报名成功；若中途异常，则返回 400 且数据库没有任何改动。

第三步是收尾：把表结构的变更交给迁移（Migration）管理，而不是手工改库；复杂查询则用 QueryBuilder 链式拼装，比如 createQueryBuilder('course').where('c.capacity > :n', { n: 0 }).getMany()。此外，课程与学员这类「一对多」「多对多」的关系，用 @OneToMany / @ManyToMany 加关联选项描述，实体就能表达出表之间的关系。

事务保证的是「一组写操作要么全做要么全不做」，但它并不能自动消除竞态：即使包在事务里，「先查询再判断再写入」仍是两个请求可能同时读到剩余 1 个名额、同时通过检查。生产环境要用 SELECT ... FOR UPDATE 悲观锁，或乐观锁（@Version 列）来保证并发一致性。

报名事务分步观察

多步写入原子约束

用 TypeORM 处理写业务，关键不在会写几张表的增删改查，而在把多步写操作放进同一个原子边界：实体负责描述结构，@InjectRepository 负责拿到仓储，事务负责让「检查后写入」要么全成、要么全退。最后再补上并发这一课——事务解决的是原子性，锁解决的才是一致性，两者各司其职。

「实体、仓储与事务」TypeORM 用 @Entity 加 @Column 等装饰器把类映射为表；@InjectRepository(Course) 注入 Repository<Course>，无需手动 new。多步写操作放进 manager.transaction(async (manager) => ...)，回调内所有语句同属一个事务，任一步抛错整体回滚。复杂查询用 QueryBuilder，表结构变更用迁移（Migration）管理。注意事务只保证原子性，「先查再判再写」的并发竞态还需 SELECT ... FOR UPDATE 悲观锁或 @Version 乐观锁。

关键代码

TypeScript
// course.entity.ts —— 实体映射数据库表
@Entity('courses')
export class Course {
  @PrimaryGeneratedColumn() id: number
  @Column({ length: 100 }) title: string
  @Column({ default: 0 }) capacity: number      // 课程容量
  @Column({ default: 0 }) enrolled: number      // 已报名人数
}

// enrollment.service.ts —— 报名事务：检查名额 → 扣减 → 落库
@Injectable()
export class EnrollmentService {
  constructor(
    @InjectRepository(Course)
    private readonly courseRepo: Repository<Course>,
  ) {}

  async enroll(courseId: number) {
    // 事务保证三步操作要么全部成功，要么全部回滚
    await this.courseRepo.manager.transaction(async (manager) => {
      const course = await manager.findOneBy(Course, { id: courseId })
      if (!course) throw new NotFoundException('课程不存在')
      if (course.enrolled >= course.capacity) {
        throw new BadRequestException('课程名额已满')
      }
      await manager.increment(Course, { id: courseId }, 'enrolled', 1)
    })
  }
}
