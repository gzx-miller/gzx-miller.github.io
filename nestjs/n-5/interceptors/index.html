拦截器：统一响应与请求计时

用请求耗时面板展示拦截器的执行顺序：在处理器前后织入逻辑，统一包装响应结构。

开场问题：二十个接口都要返回同一套 { code, data, timestamp } 外壳，你在每个控制器方法里各写了一遍；产品突然说「再加一个 duration 字段」，你只能挨个接口改过去——有没有办法不改业务代码，就把响应统一包装起来？

响应外壳统一约定

你在写一个课程 API。前端和运维都跟你有约定：所有响应必须是 { code, data, timestamp } 的统一结构，方便前端一处解包；同时线上想统计每个接口的耗时，好在监控里看出哪个接口变慢了。

这两件事本身都不难，难的是它们和业务无关，却要在每个接口上各发生一次。接口只有两三个时，顺手在返回值里包一层、在方法开头记一个时间戳就完了；可当接口涨到几十个，同一段包装代码就复制了几十份，契约一变就得全线回归，还总有人漏改。不解决它，你要付的代价是：契约的统一性靠自觉维护，而不是靠框架保证。

逐处理器手动包装

最省事的做法，是在每个处理器里手动完成：方法开头写 const started = Date.now()，返回前把结果包成 { code: 0, data, timestamp, duration }。

它做对了一件很关键的事：响应确实被统一打包了，耗时也确实被记了下来。在接口数量少、结构还稳定的时候，这个做法完全够用，逻辑还全在一处，读起来一目了然。

包装逻辑重复散落

  • 样板代码在每个处理器里重复，几十个接口就是几十份几乎相同的包装逻辑。
  • 契约一变（加字段、改字段名）就得全量修改，极易漏改，回归成本高。
  • 耗时统计、日志这类与业务无关的代码混进业务方法，职责边界被打破。
  • 想给所有接口统一加一层缓存、审计或限流时，找不到共同的入口，只能再复制一遍。

拦截器织入位置

不推翻「包装与记时」，而是把它们从业务方法里搬到一个能同时看到「请求」与「响应」的位置——这正是拦截器（Interceptor）要解决的问题。它是一类横切关注点的织入点：在不修改业务代码的前提下，于处理器执行的前后各插一段逻辑。

拦截器的关键在于它基于 RxJS 的 Observable 模型。它拿到的不是一个处理器，而是一个 next 句柄；调用 next.handle() 得到的是处理器结果的数据流（Observable<any>），而不是结果本身。于是「前置」与「后置」就有了明确的位置：

intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
  const started = Date.now()
  return next.handle().pipe(
    map((data) => ({ code: 0, data, timestamp, duration })),
  )
}

next.handle() 之前的代码（记录开始时间）在处理器之前运行；pipe 里挂上的 map 在处理器之后运行，负责把返回值包成统一结构。前后两段写进同一个方法，中间隔着一次 handle() 调用——这就是「在处理器前后织入」的准确含义。

操作符作用典型场景
map转换返回值，改变流里的数据统一响应包装
tap只做副作用，不修改数据日志、耗时统计、埋点

把计时改用 tap 更贴切：日志不需要改变返回值，用 tap 记一句耗时即可，数据本身原样通过。厘清 map 与 tap 的分工，是写拦截器时最容易被忽略的一点。

再往下走有两个值得记住的扩展。其一，多个拦截器按注册顺序执行，处理器返回的数据流会依次穿过每个拦截器的 pipe——你注册了包装拦截器与计时拦截器，它们就按顺序各包一层。其二，拦截器可以直接返回一个 new Observable()，在内部决定是否调用 next.handle()——命中缓存时干脆跳过处理器，直接把缓存数据流出去，这就是请求级缓存的实现方式。

拦截器与守卫、管道是互补的三层：守卫决定请求「能不能进」（放行决策），管道决定参数「合不合法」（校验转换），拦截器决定「进出的前后怎么处理」（包装、计时、缓存）。各管一段，职责分明。

横切关注点收敛

拦截器把「响应包装、耗时统计、日志、缓存」这类横切关注点从业务方法里抽了出来，收敛到一处。它借助 Observable 数据流，在 next.handle() 前后分别织入前置与后置逻辑，让业务代码只关心业务。契约的稳定因此不再靠自觉，而是由框架的织入点来保证。

「拦截器」实现 NestInterceptor，基于 RxJS 的 Observable 模型：next.handle() 返回处理器结果的数据流（Observable<any>），其之前的代码在处理器前运行，pipe 里的 map（转换返回值）与 tap（只做副作用）在处理器后运行。多个拦截器按注册顺序依次穿过，返回 new Observable() 可实现请求级缓存；它与守卫（放行）、管道（校验）关注点互补。

TypeScript
// transform.interceptor.ts —— 统一响应包装
@Injectable()
export class TransformInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const started = Date.now()

    return next.handle().pipe(
      // 处理器执行完成后，把返回值包装成统一结构
      map((data) => ({
        code: 0,
        data,
        timestamp: new Date().toISOString(),
        duration: `${Date.now() - started}ms`,
      })),
    )
  }
}

// logging.interceptor.ts —— 记录请求耗时（前置逻辑用 tap）
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    return next.handle().pipe(
      tap(() => console.log(`耗时 ${Date.now() - start}ms`)),
    )
  }
}
