微服务：TCP 传输与消息模式

用下单场景展示微服务间 TCP 传输：ClientProxy 代理调用与 @MessagePattern 扣库存的请求-响应式 RPC。

开场问题：扣库存的代码放在同一个应用里时，一次方法调用就完事了；可当库存要被第二个应用复用时，它就只能被复制一遍——同一个业务逻辑，为什么非得跨进程存在两份？

单应用内直接调用

订单服务里有一个 StockService，下单时直接注入调用扣减库存。单应用阶段这很自然：一次方法调用、一个事务、类型全程可见。但随着业务变大，订单和库存的变化原因和节奏不再相同：库存要被秒杀、门店、后台等多个入口访问，还要独立扩容、独立发布，而订单侧只想按自己的节奏走。

如果它们仍在一个进程里，任何一个模块的内存泄漏、一次发布、一个依赖升级，都会同时影响两边；两边甚至被绑死在同一套技术栈和同一次构建里。你需要的是一种「能力独立、逻辑仍在一起」的组织方式。

模块导入式复用

最省事的做法：把库存模块作为普通模块导出，订单模块通过 imports 引用它，构造器注入 StockService 后直接调用方法。

它做对了一件事：调用边界是清晰的——谁提供能力、谁使用能力，被模块的 providers 与 exports 显式声明出来，而不是散落在代码各处。「服务提供方法、调用方只依赖它」这个结构，正是微服务要保留的东西；区别只在于这次调用最终走的是进程内，还是走网络。

共同部署与连锁故障

  • 两边必须一起部署、一起扩容：库存压力大时，只能连订单服务一起多开实例，资源浪费。
  • 故障不隔离：库存侧某处内存飙升或死循环，会把整个订单应用一起拖垮。
  • 技术栈被绑死：想给库存换一门语言或运行时，等同于重写整个应用。
  • 复用靠复制：第三个应用要用库存能力时，只能把代码拷一份，逻辑很快出现多个版本。
  • 边界容易模糊：模块之间互调越来越随意，最终退回成一个「模块化没做好」的单体。

进程间调用迁移

不推翻「服务提供能力、调用方只依赖它」，而是把这次调用从进程内挪到进程之间。做法是让库存服务用 NestFactory.createMicroservice<MicroserviceOptions>(...) 独立启动，指定 transport: Transport.TCP 与监听端口。它不再是一个 HTTP 应用，而是一个「监听消息、处理消息、回一个响应」的进程。

两个进程之间需要约定消息长什么样。NestJS 的做法是把消息模式（Pattern）当成寻址方式：服务方用 @MessagePattern({ cmd: 'deduct_stock' }) 声明「我来处理这个模式的消息」，方法参数用 @Payload() 取消息体，而方法的返回值就是回给调用方的响应。这里没有 HTTP 路由，也没有状态码，匹配依据就是那个模式对象。

调用方的入口是 ClientProxy。用 @Client({ transport, options }) 声明一个代理并注入到需要调用库存的服务里，再调用 send({ cmd: 'deduct_stock' }, dto) 发起请求-响应式调用：消息经 TCP 发到库存服务，服务端匹配到处理器、执行、回传结果，调用方拿到结果后继续自己的流程。这就是一次跨进程的 RPC，只是参数和返回值仍然是普通对象。

第一个必须补上的能力是超时。send() 返回的是一个 Observable，而不是 Promise；进程内调用失败会立刻抛异常，跨进程调用却可能永远等不到回应——对方进程挂了、网络断了、请求丢了，调用方会一直悬着。所以要用 pipe(timeout(5000)) 设保护，必要时再叠加 retry，最后才转成 Promise 使用。

TCP 只是传输层的一种实现。NestJS 把传输层抽象为 Transport 策略（TCP、Redis、MQTT、gRPC、Kafka、RabbitMQ 等），业务代码里写的 @MessagePattern 与 send 完全不变，只换 transport 的值：

传输策略适用场景
TCP默认传输，简单可靠，适合内部服务之间的 RPC
Redis基于发布订阅，适合事件广播与轻量任务
gRPC强类型契约（.proto），适合跨语言服务
Kafka / RabbitMQ消息队列，高吞吐事件流与削峰

除了请求-响应，还有第二种消息模式：emit()。send() 会等回执，emit() 发完即走、不等待响应，适合「下单成功后通知积分服务」这类下游可以异步消费的场景。两种模式在标识方式上也不同：消息模式用 { cmd: '...' } 这样的对象描述，事件模式则用一个字符串标识（如 'order_created'）。把非关键路径从 send 改成 emit，主流程就不必再为下游的延迟和故障买单——这是从「同步调用」走向「事件解耦」的关键一步。

最后两条经验来自运维现场。其一，TCP 传输默认端口是 3000，多个服务挤在同一台机器上必须显式分配不同端口，否则直接冲突。其二，一次下单横跨多个服务，日志分散在各处，没有统一的 traceId 就无法把一条链路的日志拼起来，而链路追踪正是排查微服务问题的前提。此外，同步调用会把延迟和故障互相传染，所以超时、重试之外，还要考虑熔断与降级，必要时用事件把强依赖改成弱依赖。

调用边界与职责划分

微服务的核心不是「把应用拆开」，而是把服务间的调用从进程内搬到进程间，同时保持调用边界清晰。服务方用 @MessagePattern 声明能处理什么消息，调用方用 ClientProxy 的 send 发起请求-响应调用、用 emit 发送事件，传输层由 Transport 策略决定。网络调用比进程内调用多了不确定性，所以超时、重试、熔断、链路追踪不是可选项，而是配套的基础设施。

「微服务」把单体拆成独立进程，用 Transport 策略（TCP / Redis / gRPC / Kafka 等）通信。服务方用 @MessagePattern({ cmd: '...' }) 声明消息处理器、@Payload() 取数据，返回值即响应；调用方用 @Client() 注入 ClientProxy，send() 是请求-响应式 RPC、emit() 是不等回执的事件。TCP 默认端口 3000，多服务需错开端口，并保证调用方设置 timeout 容错。

关键代码

TypeScript
// main.ts —— 库存服务作为 TCP 微服务启动
const app = await NestFactory.createMicroservice<MicroserviceOptions>(
  StockModule,
  {
    transport: Transport.TCP,      // 传输层：TCP（默认 3000 端口）
    options: { port: 4001 },
  },
)
await app.listen()

// stock.controller.ts —— 微服务控制器：监听消息模式
@Controller()
export class StockController {
  // 客户端 send({ cmd: 'deduct_stock' }, data) 会匹配到这里
  @MessagePattern({ cmd: 'deduct_stock' })
  deductStock(@Payload() data: { skuId: string; qty: number }) {
    return this.stockService.deduct(data)   // 返回值回传调用方
  }
}

// order.service.ts —— 订单服务通过 ClientProxy 调用库存服务
@Injectable()
export class OrderService {
  @Client({
    transport: Transport.TCP,
    options: { port: 4001 },
  })
  private readonly stockClient: ClientProxy

  async createOrder(dto: CreateOrderDto) {
    const stock = await this.stockClient
      .send({ cmd: 'deduct_stock' }, dto)   // 请求-响应模式
      .pipe(timeout(5_000))                  // 超时保护
      .toPromise()
    return this.orderRepo.save({ ...dto, stock })
  }
}
