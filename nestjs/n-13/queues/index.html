消息队列与异步任务

用订单通知展示 BullMQ 生产者/消费者、幂等消费、指数退避重试与死信队列。

开场问题：支付回调里依次写订单、发邮件、生成海报，接口要等三件事都做完才返回。某天邮件服务超时，用户钱已经付了，回调却返回 500，重试又把订单写了两遍——这些「必须做、但不该让用户等」的工作，为什么不能先从请求链路里拿出去？

请求链路之外的耗时工作

一个下单请求真正必须同步完成的，只有「校验、扣库存、写订单」这几步。发确认邮件、生成分享海报、同步数据到报表仓库，这些工作要么耗时，要么依赖外部服务，和用户能否立刻看到「下单成功」没有直接关系。

把它们留在请求链路里，接口响应时间就等于所有下游服务耗时之和，其中最慢的那个决定整体体验。更隐蔽的问题是失败语义被混在一起：邮件发不出去，到底算下单失败还是成功？如果算失败，订单已经落库；如果算成功，用户又收不到回执。请求线程里同时承担「业务写入」和「后续通知」，责任边界从一开始就模糊了。

正确的拆分是：请求只完成必须同步的部分，然后把「稍后要做的事」包装成一条消息投递出去，立刻返回 202 Accepted。客户端拿到任务编号，需要结果时再查询任务状态。

同步等待的三重代价

  • 延迟叠加。邮件服务一次调用 800ms，海报生成 2s，用户就要多等近 3 秒；流量高峰时下游变慢，请求线程被长期占用，连接池很快耗尽。
  • 失败即丢失。进程重启、下游超时、网络抖动都会让「还没执行的通知」直接消失，没有任何补做机制。
  • 重试放大。为了不丢消息，只能在请求里手写重试循环，可重试又会拖长响应时间；上游等不及先超时，用户再点一次，订单和通知都可能重复。

这些问题不是靠「多加几个 try / catch」能解决的，因为它们来自同一个结构缺陷：把异步工作塞进了同步链路。

生产者与消费者解耦

消息队列把一次工作拆成两个角色：生产者只负责把任务描述写入队列，消费者从队列取出任务并执行。两者通过队列名和任务数据格式约定契约，彼此不需要知道对方部署在哪、有多少实例。

NestJS 通过 @nestjs/bullmq 接入 BullMQ，底层使用 Redis 保存队列。根模块用 BullModule.forRoot 配置连接，业务模块用 registerQueue 声明自己使用的队列。队列名是生产与消费两侧唯一的约定，改名就等于换了一条队列。

队列带来的直接收益是削峰：突发流量先把任务堆在队列里，消费者按自己的处理能力慢慢取，下游不会因为瞬时并发被打垮。任务也不会因为一次失败就消失，而是留在队列中等待下一次尝试。

注册队列与 WorkerHost

一个完整的队列模块需要三部分：模块里注册队列、服务里注入 Queue 投递任务、处理器继承 WorkerHost 消费任务。处理器本身也是 Provider，必须登记在模块的 providers 中，容器才会启动它。

角色关键写法职责
模块BullModule.registerQueue({ name: 'mail' })声明队列并配置默认任务选项。
生产者@InjectQueue('mail') queue: Queue用 queue.add(name, data, opts) 投递任务。
消费者@Processor('mail') class MailProcessor extends WorkerHost实现 process(job)，处理单条任务。

process 正常返回即视为任务完成，抛异常则视为失败。消费者不接触 HTTP 请求上下文，因此任务数据必须自包含：订单号、收件地址都要放进 job.data，而不是依赖当前登录用户或请求对象。

至少一次与消费者幂等

主流队列提供的是 at-least-once（至少一次）语义，而不是「恰好一次」。消费者可能已经执行完业务逻辑，但在向队列确认之前进程崩溃，队列就会把同一条任务再投一次。网络分区、消费者重启也会造成同样的结果。

既然重复不可避免，消费者就必须幂等：同一个业务键执行一次和执行多次，结果一致。最常用的做法是给业务动作建立唯一键，例如以 orderId 作为回执表的唯一索引，处理前先查、处理中靠数据库唯一约束兜底。这样即使两个消费者同时处理同一条任务，也只有一个能写入成功。

jobId 也常被用来去重：相同 jobId 的任务在记录保留期间不会被重复加入队列。但它只覆盖「入队」阶段，任务完成记录被清理后仍可再次入队，所以不能把 jobId 当成永久的幂等方案。真正的幂等键必须落在业务数据里。

重试、死信与限流

失败并不可怕，可怕的是失败后既没有重试，也没有记录。BullMQ 用三个选项描述重试策略：attempts 是最大尝试次数（含首次执行），backoff 决定两次尝试之间等多久，removeOnFail 决定失败记录保留多久。

  • 指数退避。backoff: { type: 'exponential', delay: 1000 } 让等待时间按 1s、2s、4s 递增，给下游恢复的时间，避免立刻重试把对方再次打垮。
  • 最大尝试次数。次数用尽后任务进入失败状态。失败记录不要立刻删除，否则问题现场就没了。
  • 死信队列。在 failed 事件里判断是否已耗尽尝试，把任务数据转投到专门的死信队列，后续人工排查或批量重放。
  • 并发与限流。@Processor('mail', { concurrency: 5, limiter: { max: 100, duration: 60000 } }) 控制单实例并发和每分钟处理上限，保护下游配额。

还有一个容易被忽略的边界：数据库写入与任务投递是两次独立操作。如果先投递后提交事务，事务回滚时任务已经发出；如果先提交后投递，投递前进程崩溃，任务又丢了。可靠做法是把任务先写进业务库的 outbox 表，与业务数据同事务提交，再由后台轮询转投队列。

两个最容易踩的坑：其一，消费者里直接写「发邮件」却不做去重，重复投递就会给用户发两封；正确做法是以业务唯一键先查后写，并用数据库唯一约束兜底。其二，处理器忘记登记到模块的 providers，队列有任务却永远没人消费——@Processor 只负责标记，注册仍然要靠模块。
「消息队列与异步任务」把耗时或易失败的工作从请求链路剥离：生产者用 Queue.add 投递，消费者用 @Processor + WorkerHost.process 处理。队列提供至少一次投递，因此消费者必须按业务唯一键幂等；失败通过 attempts 与指数退避重试，耗尽后转入死信队列人工处理；concurrency 与 limiter 负责削峰限流；数据库与队列的双写要用 outbox 模式保证一致。

关键代码

TypeScript
// 场景：订单支付成功后异步发送回执邮件，失败按指数退避重试，最终失败转入死信队列。
// 结构：Module 装配队列与 Provider，Controller 只负责接收请求，Service 投递任务，Processor 消费任务。

// ═══ 1. 共享契约与基础设施 Provider ═══
import { Body, Controller, HttpCode, Inject, Injectable, Logger, Module, Param, Post } from '@nestjs/common'
import { BullModule, InjectQueue, OnWorkerEvent, Processor, WorkerHost } from '@nestjs/bullmq'
import { IsEmail } from 'class-validator'
import { DataSource } from 'typeorm'
import type { Job, Queue } from 'bullmq'

export interface SendReceiptPayload {
  orderId: string
  email: string
}

export interface MailTransport {
  sendMail(message: { to: string; subject: string }): Promise<void>
}

@Injectable()
export class SmtpMailTransport implements MailTransport {
  async sendMail(message: { to: string; subject: string }): Promise<void> {
    // 说明：真实项目在这里调用 SMTP 客户端或第三方邮件 API
    void message
  }
}

@Injectable()
export class MailReceiptRepository {
  constructor(private readonly dataSource: DataSource) {}

  async wasSent(orderId: string): Promise<boolean> {
    const rows = await this.dataSource.query(
      'SELECT 1 FROM mail_receipt WHERE order_id = $1 LIMIT 1',
      [orderId],
    )
    return rows.length > 0
  }

  async markSent(orderId: string): Promise<void> {
    await this.dataSource.query(
      `INSERT INTO mail_receipt (order_id, sent_at)
       VALUES ($1, NOW())
       ON CONFLICT (order_id) DO NOTHING`, // 结果：并发重复写入被唯一约束吸收
      [orderId],
    )
  }
}

@Injectable()
export class MailerService {
  constructor(@Inject('MAIL_TRANSPORT') private readonly transport: MailTransport) {}

  async sendReceipt(email: string, orderId: string): Promise<void> {
    await this.transport.sendMail({
      to: email,
      subject: `订单 ${orderId} 的回执`,
    })
  }
}

// ═══ 2. 生产者：Service 投递任务，Controller 立即返回 202 ═══
@Injectable()
export class MailService {
  constructor(
    @InjectQueue('mail')
    private readonly mailQueue: Queue<SendReceiptPayload>,
  ) {}

  async enqueueReceipt(orderId: string, email: string) {
    return this.mailQueue.add(
      'send-receipt',
      { orderId, email },
      {
        jobId: `receipt:${orderId}`, // 说明：记录保留期间相同 jobId 不会重复入队
      },
    )
  }

  async getJobState(jobId: string) {
    return this.mailQueue.getJob(jobId) // 结果：可按 jobId 查询任务当前状态
  }
}

export class NotifyDto {
  @IsEmail()
  email!: string
}

@Controller('orders')
export class MailController {
  constructor(private readonly mailService: MailService) {}

  @Post(':id/notify')
  @HttpCode(202)
  async notify(@Param('id') orderId: string, @Body() dto: NotifyDto) {
    const job = await this.mailService.enqueueReceipt(orderId, dto.email)
    return { accepted: true, jobId: job.id } // 结果：客户端拿到任务编号，不再等待邮件发送
  }
}

// ═══ 3. Processor：WorkerHost 消费任务并做业务幂等 ═══
@Processor('mail', {
  concurrency: 5,                           // 结果：单实例最多 5 条任务并行
  limiter: { max: 100, duration: 60_000 },  // 结果：每分钟最多处理 100 条，保护邮件服务配额
})
export class MailProcessor extends WorkerHost {
  private readonly logger = new Logger(MailProcessor.name)

  constructor(
    private readonly mailer: MailerService,
    private readonly receipts: MailReceiptRepository,
    @InjectQueue('mail-dead-letter')
    private readonly deadLetterQueue: Queue,
  ) {
    super()
  }

  async process(job: Job<SendReceiptPayload>): Promise<void> {
    const { orderId, email } = job.data
    if (await this.receipts.wasSent(orderId)) {
      this.logger.warn(`订单 ${orderId} 已发送过回执，跳过重复任务 ${job.id}`)
      return // 结果：重复投递直接短路，不再发第二封邮件
    }

    await this.mailer.sendReceipt(email, orderId)
    await this.receipts.markSent(orderId) // 说明：唯一约束保证并发下也只写入一次
    this.logger.log(`第 ${job.attemptsMade + 1} 次尝试成功：${job.id}`)
  }

  @OnWorkerEvent('failed')
  async onFailed(job: Job<SendReceiptPayload>, error: Error): Promise<void> {
    this.logger.error(`任务 ${job.id} 第 ${job.attemptsMade} 次失败：${error.message}`)
    const maxAttempts = job.opts.attempts ?? 1
    if (job.attemptsMade >= maxAttempts) {
      await this.deadLetterQueue.add('send-receipt-dead', {
        ...job.data,
        failedReason: error.message,
      })
      this.logger.error(`任务 ${job.id} 已耗尽尝试次数，转入死信队列`)
    }
  }
}

// ═══ 4. 业务写入与任务投递的一致性：outbox ═══
@Injectable()
export class PaymentService {
  private readonly logger = new Logger(PaymentService.name)

  constructor(
    private readonly dataSource: DataSource,
    private readonly mailService: MailService,
  ) {}

  async markPaid(orderId: string, email: string): Promise<void> {
    await this.dataSource.transaction(async (manager) => {
      await manager.query(
        'UPDATE orders SET status = $1 WHERE id = $2',
        ['PAID', orderId],
      )
      await manager.query(
        'INSERT INTO mail_outbox (order_id, email, created_at) VALUES ($1, $2, NOW())',
        [orderId, email],
      )
    })
    this.logger.log(`订单 ${orderId} 已支付，outbox 记录等待独立轮询任务转投队列`)
  }

  async relayOutbox(): Promise<number> {
    const rows = await this.dataSource.query(
      `SELECT id, order_id, email
       FROM mail_outbox
       WHERE published_at IS NULL
       ORDER BY id
       LIMIT 50`,
    )
    for (const row of rows) {
      await this.mailService.enqueueReceipt(row.order_id, row.email)
      await this.dataSource.query(
        'UPDATE mail_outbox SET published_at = NOW() WHERE id = $1',
        [row.id],
      )
    }
    return rows.length // 结果：返回本轮转投数量，供调度器记录
  }
}

// ═══ 5. Module 装配：队列、Controller、Processor 与基础设施 ═══
@Module({
  imports: [
    BullModule.registerQueue({
      name: 'mail',                         // 说明：队列名是生产者与消费者的唯一约定
      defaultJobOptions: {
        attempts: 4,                        // 结果：首次执行 + 3 次重试
        backoff: { type: 'exponential', delay: 1000 }, // 结果：重试间隔 1s、2s、4s
        removeOnComplete: 1000,             // 说明：只保留最近 1000 条完成记录
        removeOnFail: 5000,                 // 说明：保留失败现场，供排查与重放
      },
    }),
    BullModule.registerQueue({ name: 'mail-dead-letter' }),
  ],
  controllers: [MailController],
  providers: [
    MailService,
    MailProcessor,
    MailerService,
    MailReceiptRepository,
    PaymentService,
    { provide: 'MAIL_TRANSPORT', useClass: SmtpMailTransport },
  ],
  exports: [MailService],
})
export class MailModule {}

@Module({
  imports: [
    BullModule.forRoot({
      connection: {
        host: process.env.REDIS_HOST ?? '127.0.0.1',
        port: Number(process.env.REDIS_PORT ?? 6379),
      },
    }),
    MailModule,
  ],
})
export class AppModule {}
