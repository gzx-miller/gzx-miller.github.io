事务与并发控制

用并发报名模拟器展示事务边界、隔离级别、悲观锁与乐观锁对超卖的影响。

开场问题：课程只剩最后 1 个名额，报名逻辑已经包在 manager.transaction 里：先查 enrolled < capacity，再自增。可两个人同时点「报名」，两边都返回成功，课程却多卖了一个。事务不是应该保证「检查与写入一起完成」吗，为什么还是被并发击穿了？

事务边界与失败回滚

事务首先解决的是原子性：一组写操作要么全部提交，要么全部不发生。TypeORM 里可以用 DataSource.transaction(async (manager) => { ... }) 声明边界，回调内所有语句共用同一个事务管理器；也可以在需要精细控制时用 QueryRunner，手动 startTransaction、commitTransaction、rollbackTransaction。

两种写法的关键差别在「谁来收尾」。transaction 回调抛出异常时框架自动回滚，并让异常继续向上传播；QueryRunner 则必须自己写 try / catch / finally：catch 里回滚后要重新抛出，finally 里释放连接，否则连接会一直挂在池里。

因此事务只保证「一起成功或一起失败」，它不会自动让并发的检查与写入排队。这是后面所有问题的起点。

隔离级别与竞态窗口

隔离级别决定并发事务之间的可见性。标准定义了四种，越往上一致性越强、并发度越低：

  • READ UNCOMMITTED：能读到别的事务尚未提交的数据，即脏读，几乎不用于业务系统。
  • READ COMMITTED：只读已提交数据，避免脏读；但同一事务内两次读同一行可能得到不同结果，即不可重复读，范围查询也可能多出新行。
  • REPEATABLE READ：同一事务内重复读保持一致，避免不可重复读；标准定义下仍可能出现幻读——同一范围查询多出新的行。
  • SERIALIZABLE：让并发事务表现得像串行执行，三类异常都避免，代价是更多阻塞与重试。

要注意数据库实现会加码：InnoDB 默认是 REPEATABLE READ，普通 SELECT 走快照读，看到的是事务开始时的版本；而 SELECT ... FOR UPDATE 走当前读，会加锁并读到最新已提交数据。这也解释了为什么「把查询放进事务」并不等于「查询会看到最新数据」。

报名逻辑是典型的 check-then-act：读 enrolled、比较 capacity、再写入。三步之间有一个窗口，两个事务都可能在这个窗口里读到同一个旧值 0，都判断「还有名额」，然后各自写入。后写的覆盖先写的，或者两笔报名都落库，最终结果都比真实容量多。

提高隔离级别并不总是解药：REPEATABLE READ 下快照读依然可能让两个事务看到同一份旧数据；SERIALIZABLE 虽然能阻止，但会把大量并发变成串行，吞吐和死锁风险都要重新评估。真正对症的是让「读」也参与并发控制——悲观锁或乐观锁。

悲观锁：SELECT ... FOR UPDATE

悲观锁假设冲突一定会发生。在事务内用 lock: { mode: 'pessimistic_write' } 查询，TypeORM 会生成 SELECT ... FOR UPDATE，数据库对命中的行加排他锁：后到的事务必须等前一个事务提交或回滚，才能读到这一行。检查与写入因此被串成一条队列。

  • 锁的范围与查询条件相关：按主键等值查询只锁目标行；范围条件可能锁住更多行甚至间隙，必须看执行计划。
  • 锁一直持有到事务结束，事务越长，阻塞越久；要避免在锁内做网络请求、文件读写或等待用户输入。
  • 多个事务以不同顺序锁多行会形成死锁；统一加锁顺序，并给事务设置合理的超时与重试。

它适合冲突概率高、写入必须立刻成功的场景，比如抢最后一个名额、扣减库存。

乐观锁：版本号与条件更新

乐观锁假设冲突较少，不在读取时加锁，而是在写入时校验「这行数据还是我读到的那个版本吗」。实体上加 @Version() version，更新时带上 WHERE id = ? AND version = ?，并把 version 加一。

判断依据是受影响行数：affected === 0 说明版本已经被别人改过，本次更新失败。此时可以选择有限次重试（重新读取、重新计算、再次更新），也可以直接返回 409 让调用方决定。重试必须有上限和退避，否则高冲突下会变成无效的自旋。

乐观锁没有长时间持锁，读多写少时吞吐更好；代价是冲突时要多做一轮读与写。冲突率很高时，反复失败的成本可能超过悲观锁的等待成本，选型要看真实并发分布，而不是背结论。

事务纪律与执行边界

无论选哪种锁，事务都应该短、窄、可预测：

  • 把网络调用、消息发送、第三方接口放到事务之外。它们既无法回滚，又会拉长持锁时间。
  • 不要在事务里 catch 异常后继续执行，否则该回滚的错误会被吞掉；要么修正后重试，要么让异常冒泡触发回滚。
  • 同一个事务里的多条语句通常共用一个连接，不要用 Promise.all 并发执行，以免把同一连接上的语句交错。
  • 为唯一性约束、幂等键留好兜底：锁解决并发窗口，唯一索引解决重复写入，两者互补。
  • 关注连接池：事务等待锁时也占着连接，长事务堆积会先把池耗尽，再把整个服务拖慢。

并发报名模拟

三个常见误区：把「用了事务」当成「并发安全」——原子性不等于隔离性，先查后写仍需锁；以为提高隔离级别就能消灭竞态——快照读仍可能读到旧值，且吞吐代价很高；乐观锁只写 UPDATE 却不检查 affected，冲突被静默忽略，数据照样写错。
「事务与并发控制」事务用 DataSource.transaction 或 QueryRunner 圈定原子边界，任一步抛错整体回滚；隔离级别控制脏读、不可重复读与幻读的可见性，但不替代锁。「先查后写」存在竞态窗口，悲观锁用 pessimistic_write（SELECT ... FOR UPDATE）让读参与加锁，乐观锁用 @Version 加条件更新、以受影响行数判断冲突。事务要短，锁内不做网络请求，异常必须冒泡以触发回滚。

关键代码

TypeScript
// 课程报名并发控制：DataSource 事务边界、悲观锁与乐观锁的完整服务实现

import {
  BadRequestException,
  Body,
  ConflictException,
  Controller,
  Injectable,
  Module,
  NotFoundException,
  Param,
  ParseIntPipe,
  Post,
} from '@nestjs/common'
import { InjectRepository, TypeOrmModule } from '@nestjs/typeorm'
import {
  Column,
  DataSource,
  Entity,
  PrimaryGeneratedColumn,
  Repository,
  Unique,
  Version,
} from 'typeorm'

// ═══ 1. 实体：@Version 支撑乐观锁，唯一约束兜底重复报名 ═══
@Entity('courses')
export class Course {
  @PrimaryGeneratedColumn()
  id: number

  @Column({ length: 100 })
  title: string

  @Column({ default: 0 })
  capacity: number

  @Column({ default: 0 })
  enrolled: number

  @Version()
  version: number            // 说明：每次成功更新自动加一，作为乐观锁的版本号
}

@Entity('enrollments')
@Unique(['courseId', 'userId'])
export class Enrollment {
  @PrimaryGeneratedColumn()
  id: number

  @Column()
  courseId: number

  @Column()
  userId: string
}

// ═══ 2. 事务边界：检查、扣减、写报名记录三者原子 ═══
@Injectable()
export class EnrollmentService {
  constructor(
    private readonly dataSource: DataSource,
    @InjectRepository(Course)
    private readonly courseRepo: Repository<Course>,
  ) {}

  async enroll(courseId: number, userId: string) {
    return this.dataSource.transaction(async (manager) => {
      const course = await manager.findOne(Course, { where: { id: courseId } })
      if (!course) throw new NotFoundException('课程不存在')
      if (course.enrolled >= course.capacity) throw new BadRequestException('名额已满')

      await manager.increment(Course, { id: courseId }, 'enrolled', 1)
      await manager.insert(Enrollment, { courseId, userId })

      return { courseId, remaining: course.capacity - course.enrolled - 1 }
      // 结果：任一步抛错，increment 与 insert 一起回滚，不会留下半笔报名
    })
  }

  // ═══ 3. 悲观锁：让读取也排队，适合高冲突写入 ═══
  async enrollWithPessimisticLock(courseId: number, userId: string) {
    return this.dataSource.transaction(async (manager) => {
      const course = await manager.findOne(Course, {
        where: { id: courseId },
        lock: { mode: 'pessimistic_write' },   // 说明：生成 SELECT ... FOR UPDATE，锁持有到事务结束
      })
      if (!course) throw new NotFoundException('课程不存在')
      if (course.enrolled >= course.capacity) throw new BadRequestException('名额已满')

      await manager.increment(Course, { id: courseId }, 'enrolled', 1)
      await manager.insert(Enrollment, { courseId, userId })

      return { courseId, remaining: course.capacity - course.enrolled - 1 }
      // 结果：后到的事务被行锁挡住，读到的 enrolled 一定是前一个事务提交后的值
    })
  }

  // ═══ 4. 乐观锁：条件更新 + 受影响行数判断 ═══
  async enrollWithOptimisticLock(courseId: number, userId: string) {
    return this.dataSource.transaction(async (manager) => {
      const course = await manager.findOneByOrFail(Course, { id: courseId })
      if (course.enrolled >= course.capacity) throw new BadRequestException('名额已满')

      const result = await manager
        .createQueryBuilder()
        .update(Course)
        .set({ enrolled: () => 'enrolled + 1', version: () => 'version + 1' })
        .where('id = :id AND version = :version', {
          id: courseId,
          version: course.version,
        })
        .execute()

      if (result.affected === 0) {
        throw new ConflictException('课程已被其他请求修改，请重试')
        // 结果：版本不匹配，条件更新影响 0 行，不会覆盖别人的写入
      }

      await manager.insert(Enrollment, { courseId, userId })
      return { courseId, remaining: course.capacity - course.enrolled - 1 }
    })
  }

  // ═══ 5. QueryRunner：需要手动控制提交与回滚时使用 ═══
  async enrollWithQueryRunner(courseId: number, userId: string) {
    const runner = this.dataSource.createQueryRunner()
    await runner.connect()
    await runner.startTransaction()

    try {
      const course = await runner.manager.findOne(Course, {
        where: { id: courseId },
        lock: { mode: 'pessimistic_write' },
      })
      if (!course) throw new NotFoundException('课程不存在')
      if (course.enrolled >= course.capacity) throw new BadRequestException('名额已满')

      await runner.manager.increment(Course, { id: courseId }, 'enrolled', 1)
      await runner.manager.insert(Enrollment, { courseId, userId })
      await runner.commitTransaction()

      return { courseId, remaining: course.capacity - course.enrolled - 1 }
    } catch (error) {
      await runner.rollbackTransaction()
      throw error                              // 说明：回滚后继续抛出，交给全局异常过滤器
    } finally {
      await runner.release()                   // 说明：连接必须归还连接池，否则会耗尽池
    }
  }

  // ═══ 6. 调试辅助：读取当前落库状态，便于压测后核对 ═══
  async findCourse(courseId: number) {
    const course = await this.courseRepo.findOneBy({ id: courseId })
    if (!course) throw new NotFoundException('课程不存在')
    return {
      id: course.id,
      capacity: course.capacity,
      enrolled: course.enrolled,
      version: course.version,
      oversold: Math.max(0, course.enrolled - course.capacity),
    }
  }
}

// ═══ 7. 控制器：三种策略分别暴露接口，便于并发压测对照 ═══
@Controller('courses')
export class EnrollmentController {
  constructor(private readonly enrollmentService: EnrollmentService) {}

  @Post(':id/enroll')
  enroll(
    @Param('id', ParseIntPipe) id: number,
    @Body() body: { userId: string },
  ) {
    return this.enrollmentService.enroll(id, body.userId)
  }

  @Post(':id/enroll/pessimistic')
  enrollPessimistic(
    @Param('id', ParseIntPipe) id: number,
    @Body() body: { userId: string },
  ) {
    return this.enrollmentService.enrollWithPessimisticLock(id, body.userId)
  }

  @Post(':id/enroll/optimistic')
  enrollOptimistic(
    @Param('id', ParseIntPipe) id: number,
    @Body() body: { userId: string },
  ) {
    return this.enrollmentService.enrollWithOptimisticLock(id, body.userId)
  }
}

// ═══ 8. 模块装配：TypeORM 仓储与业务服务交给 DI 容器 ═══
@Module({
  imports: [TypeOrmModule.forFeature([Course, Enrollment])],
  controllers: [EnrollmentController],
  providers: [EnrollmentService],
  exports: [EnrollmentService],
})
export class EnrollmentModule {}
