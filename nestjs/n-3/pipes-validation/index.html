管道与数据校验：ValidationPipe 与 DTO

用课程报名表单展示 DTO + class-validator 装饰器 + ValidationPipe 的声明式校验，以及错误响应结构。

开场问题：报名接口的请求体里多塞了一个 role: 'admin' 字段，代码里没写它、也没校验它，它却一路透传到了业务逻辑——为什么框架不替我拦住这个「多出来的字段」？

请求数据合法性校验

课程报名接口收到一份表单：姓名、邮箱、年龄、课程 ID。任何一条不合规，都不该进入业务逻辑——姓名不能为空、邮箱要有格式、年龄得在 18 到 99 之间、课程 ID 必须是合法的 UUID。

如果在控制器里逐条 if 判断，会立刻遇到两个麻烦。第一是重复：同一个「邮箱格式」的规则，注册接口、报名接口、找回密码接口都要再写一遍，改一次漏一处。第二是穿透：请求体是个普通对象，前端多传一个业务没声明的字段，它会被原样带进后续流程。校验不只是「检查对错」，更是决定「哪些数据被允许进入系统」。

控制器内手工校验

最省事的做法：在控制器方法开头写一串 if。if (!dto.name) throw new BadRequestException('姓名不能为空')，一条条往下判，最后再调 Service。

它做对了一件事：把「非法数据」挡在了业务逻辑之外。数据对不对、能不能进，在一个地方就说清了，不靠调用方自觉。接口只有一两个、规则只有两三条时，这种方式完全够用。

校验与业务逻辑耦合

  • 规则散落在每个控制器里，同一个字段的规则被反复抄写，改一处就得同步改多处。
  • 校验与业务逻辑混在同一个函数里，控制器的核心业务被一堆 if 淹没。
  • 类型转换还得手写：age 从 JSON 到代码里可能是字符串，不显式转成数字就会带着错误类型往下走。
  • 请求体里的多余字段无人拦截，前端多传的参数会被静默带进业务，形成隐式的越权入口。

规则下沉到数据结构

不推翻「先把非法数据挡在门外」，而是把规则从代码里挪到数据结构上。先定义一个 DTO（数据传输对象），用装饰器把每个字段的规则写在字段旁边：

  • @IsNotEmpty 保证姓名非空，@MaxLength(20) 限制长度。
  • @IsEmail 校验邮箱格式。
  • @IsInt、@Min(18)、@Max(99) 约束年龄是整数且落在区间内。
  • @IsUUID('4') 要求课程 ID 是合法的 UUID。

规则写在 DTO 上，就与具体的控制器解耦了：同一份 CreateEnrollmentDto 可以被多个接口复用，改规则只改一处，所有引用它的地方一起生效。

接着让框架去执行这份规则。管道（Pipe）在数据进入处理器之前执行，负责转换与校验。全局启用 ValidationPipe 后，整个流程变成：

  1. 请求体 JSON 到达 POST /enrollments。
  2. ValidationPipe 先把这个普通对象实例化成 CreateEnrollmentDto 类的实例（背后是 class-transformer）。
  3. class-validator 按装饰器规则逐字段校验，任一规则失败即中断。
  4. 失败则返回 400，响应里的 message 数组一次性列出全部字段的失败原因；成功才进入控制器。

这套机制真正改变的是「规矩放在哪里」。过去规矩活在控制器的 if 里，只有写它的人知道；现在规矩写在 DTO 上，DTO 就成了接口对外的契约——请求体长什么样、每个字段有什么要求，一眼可见。校验发生在「数据刚进来」这一层，下游的业务、持久化都不必再重复防守，因为它们拿到的已经是一个通过了契约的数据。

顺带一提，管道不只服务 DTO。ParseIntPipe、ParseUUIDPipe 这类内置管道可以直接挂在某个参数上，把 GET /courses/42 里的字符串就地转成数字、或校验它是合法的 UUID，和 ValidationPipe 用的是同一套「进入处理器前先处理数据」的思路。

开关还有几档调节。whitelist: true 会自动剥离 DTO 里没有声明的多余字段，这正是拦住开头那个 role: 'admin' 的关键。与之配套的 forbidNonWhitelisted: true 更进一步，遇到多余字段直接判为 400，而不是静默丢弃——生产加固通常两个一起开。transform: true 则会让 age 这类数字字符串自动转成目标类型。若内置规则不够用，还可以用 @Validate(ConstraintClass) 或自定义装饰器扩展校验逻辑。

白名单不是可选项：未启用 whitelist 时，请求体里多余的字段会被原样透传到业务代码——前端传一个 role: 'admin'，就可能被写进用户记录，形成隐式的越权风险。DTO 校验必须配合白名单，校验的是「值对不对」，白名单防的是「字段该不该存在」。

表单校验响应结构

管道层统一校验

管道把「校验」从控制器代码里搬到了数据结构的定义上：用 DTO 加装饰器声明规则，用 ValidationPipe 在数据进入处理器前统一执行，规则得以复用、错误响应格式统一。再配上 whitelist 拦截多余字段，非法数据和越权字段就都进不来。

「管道与数据校验」管道（Pipe）在数据进入处理器前执行，负责转换与校验。ValidationPipe 基于 class-transformer 与 class-validator：先把请求体实例化为 DTO 类，再按 @IsEmail / @Min / @IsUUID 等装饰器规则逐字段校验，失败即返回 400 并附 message 数组。whitelist 剥离 DTO 未声明的多余字段，forbidNonWhitelisted 直接判 400，transform: true 自动转换类型。

TypeScript
// create-enrollment.dto.ts —— 数据传输对象，用装饰器声明规则
export class CreateEnrollmentDto {
  @IsNotEmpty({ message: '姓名不能为空' })
  @MaxLength(20, { message: '姓名最长 20 个字符' })
  name: string

  @IsEmail({}, { message: '邮箱格式不正确' })
  email: string

  @IsInt({ message: '年龄必须是整数' })
  @Min(18, { message: '年龄不能小于 18' })
  @Max(99, { message: '年龄不能大于 99' })
  age: number

  @IsUUID('4', { message: '课程 ID 必须是 UUID' })
  courseId: string
}

// main.ts —— 全局启用校验管道
async function bootstrap() {
  const app = await NestFactory.create(AppModule)
  // whitelist 自动剔除 DTO 之外的属性，forbidNonWhitelisted 则直接报错
  app.useGlobalPipes(new ValidationPipe({ whitelist: true }))
  await app.listen(3000)
}
