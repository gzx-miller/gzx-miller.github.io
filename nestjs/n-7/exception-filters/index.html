异常过滤器：统一错误响应

用三类典型异常展示 @Catch 过滤器如何把错误转换成统一的 JSON 响应结构。

开场问题：业务代码里只写了一句 throw new NotFoundException('课程 42 不存在')，客户端却收到了一份字段齐全、结构规整的 JSON——这句异常究竟是被谁接住、又是怎么变成响应的？如果换成一句普通的 Error，返回的又会是什么？

错误分类与响应形态

你在写课程接口，出错的情形有很多：ID 查不到课程，该回 404；参数不合法，该回 400；数据库连接断了，程序里抛出的却是一句普通的 Error。而前端只想要一件事：无论哪种错误，都给我一套稳定的结构（比如 { code, message, path, timestamp }），好统一弹提示。

如果不做统一处理，这些异常会各走各的路：业务里抛的 HttpException 和一句裸 Error 返回的格式并不一致，未捕获的异常甚至会被框架用默认格式吐出去。前端要针对不同格式写多套解析分支，维护成本高；更糟的是，默认的错误响应有时会带上堆栈，等于把内部细节暴露给了调用方。不解决它，你要付的代价是：错误响应的契约不稳定，且不受你控制。

逐方法异常捕获

最省事的做法，是在每个可能出错的方法里手动 try / catch：捕获到异常后，自己拼一个 JSON，res.status(404).json({ code: 404, message }) 返回出去。

它做对了一件关键的事：错误结构完全由自己掌控，返回的状态码与消息都是明确的。在只有一两个会出错的接口时，这个做法直截了当，写出来也看得懂。

异常分支与格式分散

  • try / catch 在每个方法里重复，异常类型一多，分支就越写越乱。
  • 总有漏网之鱼：某个没被包住的异常会抛出去，返回框架的默认格式，与其它接口不一致。
  • 状态码与响应体分散在各处，改一次结构要满项目搜，契约很难统一。
  • 管道做的参数校验也会抛异常（400），它们同样绕过你手写的 catch。
  • 既想区分「课程不存在」和「服务端崩溃」，又不想在每个 catch 里重复判断类型。

全局异常过滤器

不推翻「构造统一错误」，而是把这件事从每个方法里提到一个全局的收口点——这就是异常过滤器（Exception Filter）。它实现 ExceptionFilter 接口，用 @Catch() 声明捕获范围：@Catch(HttpException) 只处理 HTTP 异常，而空参数的 @Catch() 则捕获所有异常，正好用来兜底。

过滤器通过 ArgumentsHost 拿到响应对象，再把异常统一翻译成 JSON。核心逻辑只有几步：先用 instanceof HttpException 判断异常是否携带标准状态码，是就取 getStatus()，不是就当成 500 兜底；再从 getResponse() 里取出 message，最后 response.status(status).json(...) 输出：

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp()
    const status = exception instanceof HttpException ? exception.getStatus() : 500
    const message = exception instanceof HttpException ? exception.message : 'Internal server error'
    ctx.getResponse().status(status).json({ code: status, message, path: ctx.getRequest().url, timestamp: new Date().toISOString() })
  }
}

有了它，业务代码只需要抛出带语义的异常：查不到抛 NotFoundException，参数不对抛 BadRequestException，而响应格式一律交给过滤器。不同异常经同一条管道后，返回的结构完全一致：

异常类型HTTP 状态过滤器处理
NotFoundException404读取 getStatus() 与 message
BadRequestException400message 可为错误数组（校验场景）
Error（未包装）500兜底为 Internal server error

还有两点值得记住。其一，HttpException 本身携带标准 HTTP 状态码，自定义异常可以继承它，这样既能带上自己的语义，又能复用这套状态码；而且 catch 特定异常类型，还能为它定制响应字段。其二，过滤器是分作用域的：方法级 @UseFilters 优先于控制器级，控制器级优先于全局——越靠内越具体，可以在某个接口上临时覆盖全局的兜底行为。

别忘了管道：参数校验失败抛出的 400 同样是 HttpException，会被全局过滤器一并格式化成相同的结构。这正是统一过滤器的价值——不论错误来自业务、来自校验还是完全没预料到，API 契约在所有错误场景下都保持一致。

三类异常响应对照

响应格式单点收敛

异常过滤器把「错误长什么样」这件事从业务代码里抽离出来，收敛到一个全局的收口点。业务只管抛出语义化的异常，格式、状态码与兜底逻辑由过滤器统一负责。这样一来，无论错误来自校验、业务还是意外崩溃，前端看到的都是同一套结构，接口契约才真正稳定。

「异常过滤器」实现 ExceptionFilter，用 @Catch() 声明捕获范围（空参数捕获所有异常，@Catch(HttpException) 只捕获 HTTP 异常），从 ArgumentsHost 取响应对象统一输出 JSON。用 instanceof HttpException 区分标准状态码与 500 兜底，HttpException 可被自定义异常继承。作用域为方法级 @UseFilters > 控制器级 > 全局；管道校验的 400 也会被统一格式化。

关键代码

TypeScript
// all-exceptions.filter.ts —— 捕获全部异常并统一格式
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp()
    const response = ctx.getResponse<Response>()

    const status =
      exception instanceof HttpException ? exception.getStatus() : 500

    const message =
      exception instanceof HttpException
        ? (exception.getResponse() as any)?.message ?? exception.message
        : 'Internal server error'

    response.status(status).json({
      code: status,
      message,
      path: ctx.getRequest<Request>().url,
      timestamp: new Date().toISOString(),
    })
  }
}

// main.ts —— 全局注册
app.useGlobalFilters(new AllExceptionsFilter())

// 业务代码只需抛出语义化异常
throw new NotFoundException(`课程 ${id} 不存在`)
