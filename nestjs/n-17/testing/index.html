测试策略：单元、集成与 e2e

用课程服务展示 Test.createTestingModule、依赖替换与 supertest 端到端测试的分层策略。

开场问题：把课程接口的 capacity 改名为 seats，单元测试全绿，上线后 e2e 却整片失败。为什么那 24 个跑得飞快的单元测试没有拦住这次字段改名？三种测试到底各该负责什么？

一次字段改名暴露的分工问题

单元测试直接调用 CourseService.findOne(42)，断言它返回了对象、抛出了异常，它根本不知道 HTTP 层的字段叫什么。字段改名发生在控制器或 DTO 的序列化边界上，而这条边界从来没有被单元测试覆盖。

这说明问题不在「测试写得不够多」，而在每一层测试验证的东西不一样。用单元测试去覆盖 HTTP 契约，会写出一堆又慢又脆的用例；只靠 e2e 去覆盖每个分支，则每次改动都要等整条链路启动。测试策略的核心，是让每层只做它最擅长的事。

测试金字塔的三层职责

测试金字塔按数量与成本分层：底部是大量快速、隔离的单元测试，中部是少量验证模块装配的集成测试，顶部是极少数走真实链路的 e2e 测试。

层级启动范围替换边界主要验证速度
单元测试单个类或 Provider所有外部依赖分支、边界值、异常路径毫秒级
集成测试一个真实模块数据库、第三方服务依赖注入装配、路由映射、参数传递百毫秒到秒级
e2e 测试完整应用外部系统与测试数据库HTTP 契约、守卫、管道、过滤器组合行为秒级

数量应当自下而上递减：一个 Service 有十条分支，就该有十条单元测试；而「下单成功后能查到订单」这种跨层流程，一条 e2e 就够，不必为每个分支复制一份 HTTP 请求。

createTestingModule 与依赖替换

NestJS 的测试工具用 Test.createTestingModule 建一个独立的 DI 容器：传入与真实模块相同的 providers、controllers，再 compile()，就能得到可用的模块实例。测试里通过 moduleRef.get(CourseService) 取出被测对象。

关键是替换边界依赖。Nest 提供三种替换方式，按场景选择：

  • useValue：直接给一个现成对象，最适合手工构造的 mock，如 { findById: async () => null }。
  • useClass：用一个假类替换真类，适合需要复用同一套假实现的多个测试。
  • overrideProvider(CourseRepository).useValue(...)：在 imports 了真实模块之后，覆盖模块内部已经注册的 Provider，集成测试最常用。

只测一个类时，不要 imports 整个业务模块——那会把数据库连接、配置、其它服务全部拉起来。直接把被测类和一个假仓储放进 providers，测试就只依赖它真正需要的东西。

集成测试与 e2e 的边界

集成测试装配真实模块，验证「容器能不能把依赖接对」。例如 imports: [CourseModule] 之后覆盖掉仓储，再检查 CourseController 能否被解析、路由前缀是否与预期一致。它抓的是单元测试看不见的问题：Provider 漏注册、模块忘记导出、构造器参数顺序写错。

e2e 测试再往前走一步：moduleRef.createNestApplication() 启动完整应用，app.init() 之后用 supertest 的 request(app.getHttpServer()) 发真实 HTTP 请求。它验证的是整条链路的组合行为：路由匹配、守卫放行、管道转换、控制器返回、异常过滤器格式化、序列化字段名。开头那次字段改名，就应该由 e2e 拦下来。

mock 行为而非实现细节

测试最容易写坏的地方，是把断言绑在内部实现上：断言仓储的 findById 被调用了一次、断言私有方法按某个顺序执行。这样的测试在重构时必然失败，可生产行为其实没变，团队只能不断改测试，最后干脆不再信任它。

更稳的做法是只断言可观察的行为：输入什么、返回什么、抛了什么异常、对外部边界产生了什么副作用。例如「课程不存在时抛 NotFoundException」应当断言异常类型与消息，而不是断言仓储调用次数。mock 的返回值也要按真实契约构造，避免测试里返回一个生产环境不可能出现的形状。

同理，不要为了测试去暴露私有方法或添加仅测试可用的分支。测试应当通过公开接口驱动代码，这样它验证的是使用者真正依赖的行为。

测试数据库与事务回滚

涉及数据库的集成测试和 e2e 测试，需要解决用例之间的数据污染。最常见的做法是每个用例开始前开启事务，结束后回滚：

  1. 用 dataSource.createQueryRunner() 创建查询运行器，connect() 后 startTransaction()。
  2. 测试中的仓储操作统一使用这个运行器的 manager，所有写入都落在同一事务里。
  3. 用例结束后 rollbackTransaction() 并 release()，数据恢复原状。
  4. 无法共享事务的场景（如 e2e 通过独立连接访问数据库），改用独立测试库，并在每个用例前清空相关表。

事务回滚的前提是「测试代码和应用代码使用同一条连接」。如果 e2e 启动的应用自己建了连接池，事务隔离就失效了，此时应当给测试环境配置独立的数据库，而不是强行共享事务。

两个最容易踩的坑：其一，用 overrideProvider 覆盖了仓储却忘了它只对当前测试模块生效，e2e 启动 AppModule 时仍会连真实数据库；覆盖必须写在创建测试模块的链式调用里。其二，只断言 mock 的调用次数，重构内部实现后测试全红，却没有任何真实行为发生变化——这类测试维护成本高、保护价值低。
「测试策略」按测试金字塔分层：单元测试用 Test.createTestingModule 只装配被测类，边界依赖用 useValue / useClass 替换；集成测试 imports 真实模块并用 overrideProvider 替换外部依赖，验证依赖注入装配；e2e 用 createNestApplication 启动完整应用，通过 supertest 打真实 HTTP 链路。断言应针对可观察行为而非实现细节；数据库测试用事务回滚或独立测试库隔离数据。

TypeScript
// 场景：课程模块采用单元、集成、e2e 三层测试，验证业务分支、依赖装配与真实 HTTP 契约。
// 结构：CourseModule 装配 Controller 与 Provider，测试分别替换仓储、启动模块、启动完整应用。

// ═══ 1. 被测上下文：Module / Controller / Provider ═══
import { Body, Controller, Get, Injectable, NotFoundException, Param, ParseIntPipe, Post } from '@nestjs/common'
import { Module } from '@nestjs/common'
import { InjectRepository, TypeOrmModule } from '@nestjs/typeorm'
import { Repository } from 'typeorm'
import { Course } from './course.entity'
import { CreateCourseDto } from './create-course.dto'

@Injectable()
export class CourseRepository {
  constructor(
    @InjectRepository(Course)
    private readonly repo: Repository<Course>,
  ) {}

  findById(id: number) {
    return this.repo.findOneBy({ id })
  }

  save(dto: CreateCourseDto) {
    return this.repo.save(this.repo.create(dto))
  }
}

@Injectable()
export class CourseService {
  constructor(private readonly courseRepo: CourseRepository) {}

  async findOne(id: number): Promise<Course> {
    const course = await this.courseRepo.findById(id)
    if (!course) {
      throw new NotFoundException(`课程 ${id} 不存在`) // 结果：HTTP 层由异常过滤器转成 404
    }
    return course
  }

  async create(dto: CreateCourseDto): Promise<Course> {
    return this.courseRepo.save(dto)
  }
}

@Controller('courses')
export class CourseController {
  constructor(private readonly courseService: CourseService) {}

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.courseService.findOne(id)
  }

  @Post()
  create(@Body() dto: CreateCourseDto) {
    return this.courseService.create(dto)
  }
}

@Module({
  imports: [TypeOrmModule.forFeature([Course])],
  controllers: [CourseController],
  providers: [CourseService, CourseRepository],
  exports: [CourseService],
})
export class CourseModule {}

// ═══ 2. 单元测试：只装配一个类，边界用 useValue 替换 ═══
import { Test, TestingModule } from '@nestjs/testing'

describe('CourseService（单元测试）', () => {
  let service: CourseService
  const repoMock = {
    findById: jest.fn(),
    save: jest.fn(),
  }

  beforeEach(async () => {
    jest.clearAllMocks()
    const moduleRef = await Test.createTestingModule({
      providers: [
        CourseService,
        { provide: CourseRepository, useValue: repoMock }, // 说明：仓储被替换，测试不连数据库
      ],
    }).compile()

    service = moduleRef.get(CourseService) // 结果：拿到真实 CourseService 实例
  })

  it('课程不存在时抛 NotFoundException', async () => {
    repoMock.findById.mockResolvedValue(null)
    await expect(service.findOne(42)).rejects.toBeInstanceOf(NotFoundException)
  })

  it('课程存在时返回对应实体', async () => {
    repoMock.findById.mockResolvedValue({ id: 42, title: 'Vue3 实战', capacity: 30 })
    await expect(service.findOne(42)).resolves.toMatchObject({ id: 42 })
    // 说明：只断言返回值，不断言仓储被调用的次数，重构内部实现时测试仍然有效
  })
})

// ═══ 3. 其它替换方式：useClass 与 overrideProvider ═══
class InMemoryCourseRepository {
  private readonly rows = new Map<number, Course>()

  async findById(id: number) {
    return this.rows.get(id) ?? null
  }

  async save(dto: CreateCourseDto) {
    const course = { id: this.rows.size + 1, ...dto } as Course
    this.rows.set(course.id, course)
    return course
  }
}

it('useClass：用内存实现替换真实仓储', async () => {
  const moduleRef = await Test.createTestingModule({
    providers: [
      CourseService,
      { provide: CourseRepository, useClass: InMemoryCourseRepository },
    ],
  }).compile()

  const service = moduleRef.get(CourseService)
  await expect(service.findOne(1)).rejects.toBeInstanceOf(NotFoundException)
})

it('overrideProvider：导入真实模块后覆盖内部 Provider', async () => {
  const repoMock = { findById: jest.fn(), save: jest.fn() }
  const moduleRef = await Test.createTestingModule({
    imports: [CourseModule],
  })
    .overrideProvider(CourseRepository)
    .useValue(repoMock)
    .overrideProvider(DataSource)
    .useValue({}) // 说明：跳过真实数据库连接，只验证模块装配
    .compile()

  expect(moduleRef.get(CourseService)).toBeInstanceOf(CourseService)
})

// ═══ 4. 集成测试：验证模块装配与路由映射 ═══
import { PATH_METADATA } from '@nestjs/common/constants'
import { INestApplication } from '@nestjs/common'

describe('CourseModule（集成测试）', () => {
  let moduleRef: TestingModule
  const repoMock = { findById: jest.fn(), save: jest.fn() }

  beforeAll(async () => {
    moduleRef = await Test.createTestingModule({
      imports: [CourseModule],
    })
      .overrideProvider(CourseRepository)

      .useValue({}) // 说明：只验证装配关系，不真正建立数据库连接

  it('容器能解析 Controller 与 Service', () => {

// ═══ 5. e2e：启动完整应用，用 supertest 打真实 HTTP 链路 ═══
import request from 'supertest'
import { ValidationPipe } from '@nestjs/common'
import { AppModule } from '../app.module'

describe('课程接口（e2e）', () => {
  let app: INestApplication
  const repoMock = {
    findById: jest.fn(),
    save: jest.fn(),
  }

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({
      imports: [AppModule],
    })
      .overrideProvider(CourseRepository)
      .useValue(repoMock)
      .compile()

    app = moduleRef.createNestApplication()
    app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }))
    await app.init() // 结果：路由、守卫、管道、过滤器全部就位
  })

  afterAll(async () => {
    await app.close()
  })

  it('GET /courses/42 返回 200 与课程体', async () => {
    repoMock.findById.mockResolvedValue({ id: 42, title: 'Vue3 实战', capacity: 30 })
    await request(app.getHttpServer())
      .get('/courses/42')
      .expect(200)
      .expect(({ body }) => {
        expect(body).toMatchObject({ id: 42, title: 'Vue3 实战' })
      })
  })

  it('GET /courses/999 返回 404', async () => {
    repoMock.findById.mockResolvedValue(null)
    await request(app.getHttpServer())
      .get('/courses/999')
      .expect(404)
  })
})

// ═══ 6. 数据库集成测试：每个用例独立事务并回滚 ═══
import { DataSource, QueryRunner } from 'typeorm'

describe('CourseRepository（数据库集成测试）', () => {
  let dataSource: DataSource
  let queryRunner: QueryRunner

  beforeAll(async () => {
    dataSource = await new DataSource({
      type: 'postgres',
      url: process.env.TEST_DATABASE_URL,
      entities: [Course],
    }).initialize()
  })

  beforeEach(async () => {
    queryRunner = dataSource.createQueryRunner()
    await queryRunner.connect()
    await queryRunner.startTransaction() // 说明：用例内所有写入都落在同一事务
  })

  afterEach(async () => {
    await queryRunner.rollbackTransaction()
    await queryRunner.release() // 结果：用例之间互不污染，无需手工清表
  })

  it('写入课程后能在同一事务中读到', async () => {
    const repo = queryRunner.manager.getRepository(Course)
    await repo.save(repo.create({ title: 'Vue3 实战', capacity: 30 }))
    await expect(repo.count()).resolves.toBe(1)
  })
})
