模块与依赖注入：NestJS 的模块化架构

用课程管理模块展示 @Module 声明式组装：Controllers、Providers、Imports、Exports 与构造器注入。

开场问题：课程控制器里写着 this.courseService = new CourseService()，一开始跑得好好的，可一旦要给 CourseService 换一个测试用的假实现，你就得改遍每一处 new——为什么 NestJS 非要我把依赖写成构造器参数，而不是自己动手创建？

依赖注入调用链

你在写一个课程管理服务：CourseController 接收请求，交给 CourseService 处理业务，Service 再通过 CourseRepository 访问数据库。最直觉的写法是在控制器里直接 new CourseService()。可当你在另一个模块 UserService 里也要用到课程数据时，同样的 new 又得抄一遍。

麻烦会一层层叠加。CourseService 自己依赖 CourseRepository，而 Repository 又需要一条数据库连接——装配一个对象，得先知道它背后整条依赖链怎么拼。每一次使用的成本，都等于把整条依赖链重新走一遍。更糟的是单元测试：你想把一个假的 Service 塞进去，却因为它被 new 写死在类里而换不掉。这就是「不引入依赖注入」要付出的代价。

就地创建依赖

最省事的做法：谁用谁创建。控制器构造函数里直接 new CourseService()，用完即走，不欠人情。

这个方案做对了最基础的一件事：对象确实被造出来了，功能真的能跑。在一个只有一两个类、依赖只有一层的小脚本里，手动创建完全够用，不必上任何框架。问题只在规模变大之后才浮现——而工程里的代码几乎总会变大。

逐层重复拼装依赖

  • 依赖链一深，每个使用者都要重复拼装。同一段「造 Repository、造 Service」的逻辑会散落在控制器、别的服务、测试代码里。
  • 想替换实现做不到：测试要用假 Service、生产要用真 Service，可类名被 new 写死，无法在运行时替换。
  • 生命周期无人统一管理。每次 new 都产生一个新实例，连接池这类昂贵对象会被反复创建，彼此还不共享状态。
  • 模块边界不可见。「谁依赖谁」只能靠人肉读代码，架构一复杂就成了一团说不清的线。

创建使用职责分离

不推翻「对象需要被创建」这件事，而是把「创建」和「使用」拆开：使用方只声明「我需要一个 CourseService」，至于它从哪来、依赖谁、什么时候造，交给一个统一的容器负责。使用方不再伸手去造对象，而是等着对象被注入进来——这就是依赖注入（DI）。

NestJS 把这层声明做成了显式的模块。@Module 用四个数组把「谁依赖谁」画成一张地图：

数组职责
controllers注册路由处理器，接收请求并返回响应。
providers登记可被注入的依赖（服务、仓储等）。
imports引入其它模块，从而获得对方 exports 出来的 Provider。
exports决定哪些 Provider 对模块外部可见，可被其它模块复用。

接着把依赖写成构造器参数： constructor(private readonly courseRepo: CourseRepository) {}。启动时，DI 容器扫描每个模块的 providers，读取构造器的参数类型，再递归地去解析 CourseRepository 的依赖，自底向上把整棵依赖树实例化完成后注入进来。使用方从此只声明「要什么」，不再关心「怎么造」。

装配是分层的。根模块 AppModule 通常不做业务，只负责组装，它 imports 进来 CourseModule、UserModule 这些业务模块。业务模块内部再各自 controllers、providers；当一个模块希望把自己的服务给别人用时，就写进 exports，别的模块 imports 它之后即可注入。

两个最容易踩的坑：其一，@Injectable() 只是把类标记为候选，它还必须出现在某个模块的 providers 里，容器才会真正托管它——只在控制器里注入、却忘了登记，应用启动时会直接抛出 Nest can not resolve dependencies。其二，@Injectable() 与 providers 缺一不可，只写其中一个都不行。

还有三个进阶细节值得记住。模块默认是单例作用域（Singleton），整棵依赖树共享同一批实例，这既省去了重复创建，也让连接池这类对象得以复用。若两个模块互相依赖（A 依赖 B、B 又依赖 A），需要 forwardRef 显式处理这个循环。若某个模块的导出希望对所有模块可见，用 @Global() 声明为全局模块，它 exports 的内容就不必被每个模块逐一 imports。

模块配置四数组

容器接管与依赖地图

模块与依赖注入，本质是给「谁依赖谁」发一张显式的地图：@Module 的四个数组划清模块边界，构造器注入把「创建对象」的活儿从使用方手里收走、交给容器。代价是你要记住 @Injectable() 与 providers 缺一不可，换来的是可替换、可测试、可复用的对象关系。

「依赖注入」指由容器负责创建对象并把依赖注入给使用方，使用方只声明「需要什么」、不管「怎么造」。NestJS 中要注入的类必须同时带 @Injectable() 并登记到某个模块的 providers；容器启动时按构造器参数类型递归解析依赖，默认单例作用域；跨模块复用靠 exports / imports，循环依赖用 forwardRef，全局模块用 @Global()。

关键代码

TypeScript
// course.module.ts —— 模块是 NestJS 组织代码的基本单元
@Module({
  imports: [DatabaseModule],        // 引入其它模块，获得其导出的 Provider
  controllers: [CourseController],  // 路由处理器，接收请求并返回响应
  providers: [CourseService],       // 业务逻辑与数据访问，可被注入
  exports: [CourseService],         // 导出 Provider，供其它模块使用
})
export class CourseModule {}

// app.module.ts —— 根模块负责装配整个应用
@Module({
  imports: [CourseModule, UserModule],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}

// course.service.ts —— Provider 通过构造器注入
@Injectable()
export class CourseService {
  // Nest 会解析 CourseRepository 的实例并注入进来（DI 容器）
  constructor(private readonly courseRepo: CourseRepository) {}

  findAll() {
    return this.courseRepo.find()
  }
}
