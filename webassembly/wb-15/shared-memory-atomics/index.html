共享内存与原子操作

用点赞计数器体验 SharedArrayBuffer 与 atomicAdd 的并发安全。

开场问题：两个顾客各自拼命点「赞」，后台明明执行了 200 次自增，最终点赞数却停在 187——少的那些赞去哪儿了？多线程环境下，同一个计数器怎么就越加越少？

读改写三步拆分

你让多个 Worker 共享同一个计数器。问题的根子在「加一」这件事本身不是一步：普通写法是 load 读当前值、加一、再 store 写回，三步之间随时可能被另一个线程插进来。两个线程都读到 5，各自算成 6，又各自写回 6——一次点赞就这么丢了。读得越频繁、线程越多，丢得越狠，最终结果总是小于预期。

旧办法也都不趁手：靠加锁——可 JS 里没有原生的共享锁，自己用标志位拼一个同样会踩到同一类竞态；退成单线程——那等于直接放弃并行的意义。问题于是收敛成一句：怎么让多个线程安全地对同一块内存里的同一个位置做「读-改-写」，而不互相覆盖？

共享内存声明语法

有两件东西要一起用。第一件是共享内存：模块把内存声明成 (memory (export "memory") 1 1 shared)，它的 buffer 就是一个 SharedArrayBuffer，多个 Worker 看到的是同一块内存。第二件是原子指令：累加时不再用普通 load/store，改用原子的「读-改-写」。

这个方案做对了一件事：它让「读-改-写」在一条指令里一气呵成，中途不允许别的线程插进来。别的线程要么看到加之前的值，要么看到加之后的值，绝不会看到「加到一半」的中间状态。

原子指令适用边界

  • 普通 load/store 依旧会丢更新——原子性只属于原子指令，共享内存本身不会自动帮你加锁。
  • 光在模块里写 shared 还不够：页面必须启用跨源隔离（COOP/COEP 响应头），否则 SharedArrayBuffer 根本创建不出来，crossOriginIsolated 是 false。
  • 原子访问要求自然对齐：地址没落在 4 的倍数上，会直接 trap，而不是悄悄降级。
  • 共享内存不能增长：(memory 1 1 shared) 里最小值必须等于最大值，容量得在声明时就把上限定死。
  • 原子指令比普通读写慢，别把它当默认选项到处用。

不可中断累加

先补原子读-改-写。核心是 i32.atomic.rmw.add——即演示里的 atomicAdd：它原子地把某个地址上的 i32 加一。整条操作不可分割，正是它把「读、加、写」三步合成了一步，丢更新随之消失。

再补返回值语义，这一点最容易记反：rmw.add 返回的是操作前的旧值，不是加完之后的新值。所以想显示「当前点赞数」，不能拿它的返回值当读数——要么用 atomic.load，要么建一个 Int32Array 视图直接读这块共享内存，演示里就是用后者拿最终值的。

接着补常用的指令族：atomic.load / store / add / sub 覆盖了基本的原子读写与增减；再往上是 wait / notify，让一个线程能在某个地址上阻塞等待、由另一个线程把它唤醒——这是自己实现锁、以及线程间发信号的基础。

最后补两个必须先满足的环境前提，缺一不可：模块侧，memory 必须标 shared 且 min = max，buffer 才会是 SharedArrayBuffer；页面侧，必须处于跨源隔离状态（响应头带 COOP/COEP），SharedArrayBuffer 才可用。任一条件不成立，要么 buffer 不是 SAB，要么累加又退化成非原子，前面的功夫全白费。

两个高频误区：其一，以为「用了共享内存就并发安全」——不是，共享内存只负责「同一块」，安全靠的是你每一步都走原子指令；其二，以为 atomicAdd 返回的是自增后的值——它返回旧值，要读当前计数请用 atomic.load 或类型化数组视图。

可见性与原子性

多线程共享计数器会丢更新，是因为「读-改-写」三步可能被打断。共享内存（SharedArrayBuffer）只解决「同一块内存」，真正的安全来自原子指令：i32.atomic.rmw.add 把读改写合成一气呵成的操作。前提是模块声明 shared 且 min = max、页面启用 COOP/COEP 跨源隔离；并且要记住它返回的是旧值。

「原子读-改-写（atomic read-modify-write）」指在共享内存上以单条不可分割的指令完成「读值、修改、写回」，从而在多线程并发下不丢更新。Wasm 中以 i32.atomic.rmw.add 实现 atomicAdd，返回操作前的旧值。边界：共享内存需在模块声明为 (memory … shared) 且 min = max（不可增长），页面还必须启用 COOP/COEP 跨源隔离 SharedArrayBuffer 才可用；原子访问要求自然对齐，未对齐会 trap；普通 load/store 仍会丢更新；常用指令还包括 atomic.load / store / sub 以及 wait / notify，且原子指令比普通读写慢。

关键代码

WAT
;; 共享内存与原子操作
;; 共享内存需在模块声明 shared，页面启用 COOP/COEP 跨源隔离
(module
  ;; min=max=1 页（64KiB），且 shared：buffer 是 SharedArrayBuffer
  (memory (export "memory") 1 1 shared)

  ;; atomicAdd(addr)：原子地把该位置加一，返回操作前的旧值
  (func $atomicAdd (param $addr i32) (result i32)
    local.get $addr
    i32.const 1
    i32.atomic.rmw.add
  )

  (export "atomicAdd" (func $atomicAdd))
)

;; 常用原子指令：atomic.load / store / add / sub / wait / notify
;; 普通读写会"丢更新"，原子指令保证读-改-写一气呵成
