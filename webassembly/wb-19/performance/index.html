性能对比：Wasm 与 JS

对同一递归算法实测 Wasm 与 JS 耗时，理解各自的性能特性。

开场问题：你把 PDF 工具里的一段解析算法换成 Wasm，本地测执行快了 3 倍，于是安心上线。结果用户抱怨「第一次打开要转好几秒按钮才出来」——你打开 Network 面板，那个 .wasm 有 2.6 MB，而且下载完之后还有一段肉眼可见的「编译中」停顿。一个明明让执行更快的技术，为什么反而让页面的第一次可用变得这么慢？

下载编译执行三段

问题出在把「性能」当成了一个数。用户感知的性能其实是三段时间之和：下载 + 编译 + 执行。你量的只是最后一段，还被本地的高性能机器和缓存掩盖了前两段。旧认知的隐藏成本有三层：只在本地量执行耗时，忽略了用户第一次要先等下载、再等编译；以为「Wasm 快」就该全面替换 JS，却没分清哪些是一次性的启动成本、哪些是每次调用都要付的成本；也不知道优化等级和加载方式会同时改变体积与首屏时间。

于是问题收敛成一句：怎么把 Wasm 的体积和「从下载到可用」这段时间压下来，同时不牺牲真正跑起来之后的执行速度？

编译与实例化流程

最直接的写法：fetch 回一个 ArrayBuffer，交给 WebAssembly.instantiate 编译并实例化，然后调用导出的函数。

这个方案做对了一件事：它是一条完整、正确的链路——一段字节进去，一个可调用的实例出来，功能上没有任何缺口。后面所有优化都建立在它之上，也都要拿它当对照基线。

包体膨胀成因

  • 产出的 .wasm 可能比预估大得多：默认优化等级下，没被调用的函数、调试段、为通用性保留的代码都还在里面，几百 KB 到几 MB 都常见。
  • instantiate 必须等整个 ArrayBuffer 下载完才能开始编译，下载和编译两段时间是串行相加的，用户在中间干等。
  • 每次进页面都重新编译一遍同一份模块，而编译结果本身是不变的，等于把上一次的劳动白白扔掉。
  • 拿执行耗时选型会误导：一段算法跑得快，不代表用户第一次看到界面快；两笔账混在一起，就会做出「越快越慢」的上线决定。

优化等级与压缩

先补最上游、也最有效的一环——编译器的优化等级。C/C++ 用 -O3 让编译器把内联、循环优化、自动向量化都做上；Rust 则用 --release 并把 opt-level 调到 3（或按体积折中取 "s"）。这一步直接决定了产物的体积与执行速度取向，是后面所有手段的地基。

接着补在编译器之上再过一遍 wasm-opt（Binaryen）。它针对 .wasm 再做死代码消除、内联、常量折叠，能把用不到的导出和函数真正砍掉。同样用它，方向可以选：偏体积用 -Oz，偏速度用 -O3。首屏敏感的模块按体积优化，重计算的模块按速度优化，得分开定，不能一刀切。

再补裁剪导出与调试信息。Wasm 里「导出即保留」，所以只导出真正要从 JS 调用的那几个函数，其余留着就会一起被打包；上线构建把名称表和调试段 strip 掉，体积还能再降一截。

然后补改变加载方式：改用 WebAssembly.instantiateStreaming。它直接接受 fetch 回来的 Response，一边下载一边编译，让这两段本应相加的时间重叠起来，比「等 ArrayBuffer 下载完再 instantiate」明显要快。但它有个硬前提：服务器必须返回正确的 MIME application/wasm，否则它会直接拒绝，你就得回退到 instantiate——这也是很多人「以为用了流式、其实没有」的原因。

再补缓存编译结果。WebAssembly.compile 产出的 WebAssembly.Module 是不可变、且可结构化克隆的，可以放进 IndexedDB 缓存；用户再次访问时把它取出来直接 instantiate，整段编译跳过，首屏只剩下下载或读缓存。到这一步，「启动时间」这笔账基本就压到位了。

两个容易配错的地方：其一，别为了体积把重计算模块也一律改成 -Oz——有些模块在 -Oz 下执行会明显变慢，省下的几十 KB 换不回用户多等的计算时间，要按模块分别定位；其二，instantiateStreaming 对 MIME 非常敏感，服务器没配好 application/wasm 时它会静默回退或直接失败，务必在真实响应头下验证，而不是只看本地开发服务器。

最后回到「执行」这另一半账。前面解决的是「第一次要等多久」，而「跑起来之后快不快」是另一回事：Wasm 是预编译的字节码，执行路径接近机器码、更可预测；JS 依赖 JIT 对热点做内联和优化，需要预热。所以测量执行耗时要先预热、再多次取样取最小值，剔除 JIT 的波动，否则结论会被单次抖动带偏。还有一个每次调用都要付的成本别忘了：跨 Wasm/JS 边界有固定开销，小函数被高频调用反而更慢，所以优化的方向是尽量把计算留在模块内部，而不是频繁跨边界来回。

预热取样对比

启动优化全链路

性能不是「跑得多快」，而是「下载 + 编译 + 执行」三段时间之和。要压启动时间，从上游到下游依次是：-O3 或 Rust release 定基调，wasm-opt 消死代码并按 -Oz 或 -O3 定取向，裁剪导出与调试信息，再用 instantiateStreaming 把下载与编译重叠、用 WebAssembly.Module 加 IndexedDB 跳过二次编译。执行这一半则要预热取样、取最小值，并记住跨边界调用有固定开销——把计算留在模块内。

「流式实例化（WebAssembly.instantiateStreaming）」指直接接收 fetch 返回的 Response，在下载字节流的同时进行编译并实例化，使下载与编译两段时间重叠，优于「先等 ArrayBuffer 全部下载、再 instantiate」的串行方式。边界与例外：它要求响应头 Content-Type 为 application/wasm，否则会拒绝，需回退到 WebAssembly.instantiate；编译结果 WebAssembly.Module 不可变且可结构化克隆，可存入 IndexedDB 缓存以跳过后续编译；它只优化「加载与启动」，不影响执行速度，执行侧仍需预热取样，并注意跨边界调用的固定开销。

JavaScript
// 性能对比：同一递归算法分别用 Wasm 与 JS 实现，实测耗时
function fibJs(v) {
  if (v < 2) return v
  return fibJs(v - 1) + fibJs(v - 2)
}

// 预热 + 多次取样取最小值，排除 JIT 波动
function measure(v, fn) {
  fn(v) // 预热
  let best = Infinity
  let result = 0
  for (let i = 0; i < 5; i++) {
    const t0 = performance.now()
    result = fn(v)
    best = Math.min(best, performance.now() - t0)
  }
  return { result, ms: best }
}

const w = measure(30, (x) => wasm.exports.fib(x)) // Wasm 版本（预编译字节码）
const j = measure(30, (x) => fibJs(x))            // JS 版本（依赖 JIT 预热）
console.log(`Wasm ${w.ms.toFixed(2)}ms，JS ${j.ms.toFixed(2)}ms`)

// 结论：计算密集、热点稳定、可复用时选 Wasm；
// 跨边界调用有开销，小函数频繁跨界反而更慢，应让计算尽量留在模块内。
