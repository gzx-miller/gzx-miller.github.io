高级缩放与宽高比处理

掌握缩放算法选择、色彩空间感知缩放、HDR 内容缩放等高级缩放技术。

开场问题：同一段 480p 老素材，要放大到 1080p，你分别用 flags=neighbor、flags=bilinear、flags=lanczos 各导一版。目标分辨率一模一样，可 neighbor 那版人脸像马赛克方块，bilinear 那版糊成一团，lanczos 那版却明显更锐利。输出尺寸完全相同，画面凭什么差这么多？

新像素插值填充

缩放要回答的是一个很具体的问题：把一张小图铺成一张大图时，那些原本不存在的、夹在原像素之间的新像素，该填什么颜色？大图里绝大多数像素都不是原图里本来就有的，它们全靠「猜」，而怎么猜，就是缩放算法的全部内容。

旧办法是把这件事交给播放器：媒体文件保持原尺寸，让播放窗口自己拉伸。它有两个必须由人承担的隐藏成本：一是算法不可选，播放器通常只用最省 CPU 的双线性，放大出来天然发软，你没法换成更锐的算法；二是无法批处理，视频有一百个、还要顺手做别的处理时，你没地方插进去，也留不下可复现的参数。

所以真正的问题是：当画面被重新采样时，「缺失的像素」由谁来定、按什么规则定？而缩放又往往只是流水线上的一步，多步处理怎样串成一条可控的链条？

目标尺寸直接指定

最直接的写法是指定目标宽高：

ffmpeg -i input.mp4 -vf scale=1920:1080 output.mp4

它做对了一件事：能把画面拉到任意目标尺寸，并且这件事是可脚本化的。你写下的 1920×1080 就是最终成片的尺寸，一万个文件都能用同一行命令跑，结果一致。

双线性插值偏软

  • 它用的是默认插值算法（bilinear），放大时会把锐利的边缘摊平，越放大越软——这正是开场里那版「糊成一团」的来源。
  • 它只管尺寸，不管比例：源是 4:3、目标是 16:9 时，画面会被直接拉伸，人脸变胖、logo 变扁，而你并不知道该在哪里补上「保持比例」这一步。
  • 它不关心位深和色彩空间：把 10-bit 或 HDR 素材直接一缩，输出可能落回 8-bit 或丢掉色彩元数据，播放器按错的方式解析，画面发灰。
  • 真实需求往往不止一步——「先裁掉黑边，再等比缩到 720p，再补边到目标画布」——单个 scale 摆不平，你还得知道怎么把这些动作接成一条链。

滤镜图串联顺序

不推翻 scale，而是先补上「多步怎么串」这一层，因为它决定了后面每一个参数的落点。FFmpeg 把一串滤镜连成的处理链叫滤镜图（filtergraph），在 -vf 里用逗号分隔，前一个滤镜的输出就是后一个的输入，像水管一样依次流过：

ffmpeg -i input.mp4 -vf "crop=1920:800:0:140,scale=1280:720" output.mp4

这里先裁后缩，顺序不能反——反了就是在更小的画面上裁，结果完全不同。链条也可以给两端起名字，用方括号标出输入输出，这在后面接多路输入时会派上用场：[in]scale=1280:720[out]。理解「滤镜图是一条有方向的链」，你就知道每个滤镜该插在哪一步、参数作用在多大的画面上。

链条理顺之后，回到缩放本身，就要挑插值算法了。算法通过 flags 指定，它们其实是同一条权衡曲线上的不同档位：

  1. bilinear：默认，速度最快，放大时最软。
  2. bicubic：质量与速度平衡，是日常缩放的稳妥选择。
  3. lanczos：放大画质最好，锐度高，代价是慢，且在强对比边缘可能有轻微振铃。
  4. neighbor：最近邻，几乎不「猜」，直接把最近的像素复制过去，放大后是硬邦邦的方块——它恰好是像素风游戏最想要的锐利，却是实拍画面的灾难。
  5. spline：样条插值，画质接近 lanczos，是另一条可选路径。

选法的规律很简单：放大用 lanczos 或 bicubic，缩小用哪个差异都不明显（缩小本身就在丢信息，算法区分度小），像素艺术用 neighbor。想切身感受差别，就用同一段素材跑一遍对比：

ffmpeg -i input_480p.mp4 -vf "scale=1920:1080:flags=lanczos" lanczos.mp4

接着补上「不拉伸」这一层。想让画面保持原始比例、只缩不放，有两种写法：把其中一维写成 -2，让 FFmpeg 按比例算出另一维并取偶，例如 scale=1280:-2；或者用 force_original_aspect_ratio 显式约束：

ffmpeg -i input.mp4 -vf "scale=1280:720:force_original_aspect_ratio=decrease,pad=1280:720:(ow-iw)/2:(oh-ih)/2" output.mp4

最后是位深与色彩这一层。有一条容易想当然的边界必须说清：scale 本身不做色彩空间转换。它的 out_color_matrix / out_range 只是把「这段画面是 bt2020、是 tv 范围」的标记改掉，不会真的把颜色换算过去。所以处理 10-bit 或 HDR 素材时，保持位深靠输出端 -pix_fmt yuv420p10le，而真正的色彩转换要交给 colorspace 或 zscale 滤镜：

ffmpeg -i input_hdr.mp4 -vf "zscale=w=1920:h=1080:f=lanczos:m=bt2020:p=bt2020:r=tv,format=yuv420p10le" output.mp4

注意 zscale 是基于 zimg 库的另一套滤镜，参数名和 scale 不一样——缩放算法写 f=、矩阵写 m=、原色写 p=、范围写 r=，不能把 scale 的写法照搬过来。

两条最容易踩的边界：scale 的 out_color_matrix / out_range 只改写标记、不做换算，指望用它完成 HDR 到 SDR 的转换只会得到颜色错乱的结果，真正转换用 colorspace 或 zscale；HDR 素材缩放后一定要用 ffprobe 复查 color_space 与位深标记，元数据一旦缺失，播放器就会按 SDR 解析，画面整片发灰。

六种插值算法对照

插值算法选型

缩放真正要决定的，是「新像素按什么规则猜出来」。把滤镜图理解成一条有方向的链，先想清楚是哪一步在做缩放、作用在多大的画面上；再按用途挑插值算法——放大用 lanczos / bicubic，缩小随便，像素风用 neighbor；最后记住 scale 只管尺寸、不改色彩，位深和 HDR 得用 -pix_fmt 与 zscale 另外照料。

「插值算法（flags）」指 scale 在重采样新像素时采用的数学规则，由 flags 指定：bilinear（默认，最快最软）、bicubic（质量速度平衡）、lanczos（放大画质最好）、spline（接近 lanczos）、neighbor（最近邻，保留硬边，适合像素艺术）、gaussian（模糊效果）。边界与例外：放大时算法差异明显、缩小时几乎无差别；neighbor 对实拍画面是灾难、对像素画是优点；flags 只影响像素如何插值，不负责色彩空间转换，HDR/10-bit 要另配 -pix_fmt 或 zscale。

关键代码

BASH
# 使用 lanczos 算法缩放（放大首选）
ffmpeg -i input.mp4 -vf "scale=1920:1080:flags=lanczos" output.mp4

# 使用 bicubic 算法（质量与速度平衡）
ffmpeg -i input.mp4 -vf "scale=1280:720:flags=bicubic" output.mp4

# 10-bit 内容缩放（保持位深）
ffmpeg -i input.mkv -vf scale=1920:1080 -pix_fmt yuv420p10le output.mkv

# HDR 内容缩放（指定色彩空间）
ffmpeg -i input_hdr.mp4 -vf "scale=1920:1080:flags=lanczos:out_color_matrix=bt2020nc:out_range=tv" -pix_fmt yuv420p10le output_hdr.mp4

# 使用 zscale 滤镜（专业级色彩处理）
ffmpeg -i input_hdr.mp4 -vf "zscale=w=1920:h=1080:f=lanczos:m=bt2020:p=bt2020:r=tv,format=yuv420p10le" output.mp4
