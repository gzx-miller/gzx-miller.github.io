流媒体与 RTMP 推流

使用 FFmpeg 进行 RTMP 推流、HLS 切片和 DASH 流式传输，掌握直播和点播的流媒体技术。

开场问题：你用 -i input.mp4 -f flv rtmp://... 推流，服务器日志显示连接建立成功，可三秒钟后推流就结束了；观众端只看到画面一闪而过，像是播了个开头就没了。

实时推流场景

你想做的其实是「直播」：一边产生画面一边送出去，而不是先转好一个文件再让人下载。旧办法在这个场景下全都不顺手——把文件传到服务器再让观众下载，根本没有实时性可言；自己写程序到网络层去分包，得先吃透整套流媒体协议；而只把文件转成另一种格式，也解决不了「持续、按时」这件事。

这些麻烦背后是三笔必须由你承担的成本：文件是按磁盘速度读的，不是按播放速度读的，直接推会被瞬间灌完；网络需要一条均匀的码流，忽快忽慢会让观众端反复缓冲；播放端还希望边下边播、按带宽切换码率，单一路码流满足不了。所以要回答的是：怎么让 FFmpeg 持续、稳定地把码流送到远端，并让播放端能跟得上？

RTMP推流命令

最短的一条推流命令只比转码多两个开关：ffmpeg -re -i input.mp4 -c copy -f flv rtmp://server/live/stream。

它做对了两件关键的事。-re 让 FFmpeg 按原始帧率读取输入，把「磁盘速度」压成「播放速度」，于是 1 分钟的片子就用 1 分钟推完，而不是几秒；-f flv 把输出指定成 RTMP 需要的 FLV 封装。-c copy 不重新编码，CPU 几乎不动，是最省的一版。前提是源编码必须是这套协议认的——H.264 视频配 AAC 音频。

节流参数与编码前提

  • 忘了 -re：文件瞬间被读完、瞬间推完，直播变成「点播闪现」，服务器端连接只活了几秒。
  • -c copy 推流要求视频是 H.264、音频是 AAC；源若是 HEVC 或 Opus，直接推会被服务器拒掉，你却在本地看不到任何画面问题。
  • 它只解决了「推」。观众端要么装 RTMP 播放器，要么靠服务器再转成浏览器能播的协议。
  • 单路码流没法适配手机和电脑不同的带宽，弱网用户只能一直卡。
  • 直播完想留一份回看，还得另想办法切片存档。

源兼容与协议匹配

不推翻这条命令，而是先把「实时」拆成输入端与输出端两件事：输入端节流，输出端匹配协议，然后一层层补齐。

第一层补「源不兼容」的情况。源编码不是 H.264/AAC 时，就得重新编码，用低延迟预设压住延迟：-c:v libx264 -preset ultrafast -c:a aac -f flv。ultrafast 编得快、延迟低，代价是同等画质文件更大。

第二层补「让浏览器直接能播」。把流切成一段段小文件，再配一份播放列表，就是 HLS：-hls_time 10 -hls_list_size 0 -f hls output.m3u8。观众端只需要普通的 HTTP 和一份 .m3u8 列表，兼容性最好。

第三层是关键，也是很多人第一次做 HLS 会踩的坑：切片点并不由 -hls_time 精确决定，而由关键帧决定。如果源的关键帧间隔（默认可能长达 250 帧）远大于你想要的片段时长，切片会被硬生生拉到下一个关键帧那里，实际片长和 -hls_time 对不上。要让两者对齐，得主动压关键帧间隔：以 30fps 想要 2 秒一片为例，用 -g 60 -force_key_frames "expr:gte(t,n_forced*2)" -hls_time 2，让「每 2 秒必有一个关键帧」成为硬约束。

第四层补「点播还是直播」。-hls_list_size 0 表示列表保留所有片段，是点播，列表末尾会带 #EXT-X-ENDLIST；直播则把 -hls_list_size 设成一个正数只保留最近 N 个片段，再加 -hls_flags delete_segments 边推边删旧片段，列表末尾没有 #EXT-X-ENDLIST。

最后一层补「自适应码率」。把源用 -map 和不同的 -b:v 拆成多路，各自切片，再写一份 master playlist 指向各变体的 .m3u8，播放器就能按带宽自动切换。想要开放标准，同样的思路换成 -f dash 生成 MPD 即可。

切片生成后，用 hls.js 或本地播放器实际播一遍 .m3u8，确认列表和片段都能拉取、能正常播放，再交付。

一个安全习惯：推流地址里的流密钥不要直接写死在命令、脚本或仓库里，生产环境用环境变量注入，并限制访问来源，避免密钥泄露被人盗推。

三种推流协议切换

输入输出与切片对齐

流媒体这件事只有三步：输入端用 -re 把速度压成实时，输出端用 -f flv、-f hls 匹配协议，切片时让关键帧间隔与目标片长对齐。记住最后一条，你就不会再遇到「-hls_time 写了 2 秒，切片却都是 8 秒」这种怪事。

「GOP（图像组）」指从一个 I 帧（关键帧）到下一个 I 帧之间的帧序列，其长度就是关键帧间隔。HLS、DASH 这类切片协议只能从关键帧处切开，所以 GOP 长度直接决定了切片的精度与直播延迟。-g 设定的是最大间隔，场景切换时还可能插入额外的关键帧；GOP 太长会让切片变粗、拖动进度变慢。

关键代码

BASH
# RTMP 推流（从文件，按原始帧率 -re）
ffmpeg -re -i input.mp4 -c copy -f flv rtmp://server/live/stream

# RTMP 推流（重新编码，超低延迟预设）
ffmpeg -re -i input.mp4 -c:v libx264 -preset ultrafast -c:a aac -f flv rtmp://server/live/stream

# HLS 切片（10 秒片段，点播）
ffmpeg -i input.mp4 -c copy -hls_time 10 -hls_list_size 0 -f hls output.m3u8

# HLS 直播流（保留最近 6 个片段）
ffmpeg -re -i input.mp4 -c copy -hls_time 6 -hls_list_size 6 -hls_flags delete_segments -f hls live.m3u8

# DASH 切片
ffmpeg -i input.mp4 -c copy -f dash output.mpd

# 推流到 YouTube Live
ffmpeg -re -i input.mp4 -c:v libx264 -preset veryfast -b:v 3000k -c:a aac -b:a 128k -f flv rtmp://a.rtmp.youtube.com/live2/STREAM_KEY
