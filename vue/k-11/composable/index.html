组合式函数与自定义指令

把有状态逻辑抽成可复用的 composable，再用自定义指令封装自动聚焦等底层 DOM 行为。

开场问题：「发送验证码」的倒计时逻辑，登录页要用、报名页也要用，但两处界面长得不一样——难道只能把这段逻辑复制一份？

验证码倒计时逻辑

你在做一个多页面的产品：登录、报名、找回密码，处处都有「点击发送验证码，然后 60 秒内不能重发」的功能。共同点很清楚——一个剩余秒数、一个「是否结束」的判断、一个启动方法、一个重置方法；不同点也很清楚——每个页面把它渲染成的样子不一样。

真正要复用的是那段有状态的逻辑，而不是那一块界面。可状态一旦散落在组件里，就只能连着 UI 一起复制，问题随之而来。

就地重复实现

最省事的做法：哪个页面要用，就把这段倒计时逻辑在组件里重新写一遍——定义秒数、开 setInterval、判断归零、清理定时器。

这个方案做对了一件基础的事：逻辑就放在它被使用的地方，不用抽象，改起来一眼能定位。

跨组件逻辑漂移

  • 同一段逻辑在多个组件里各存一份，修一个 bug 得改很多处，久而久之就漂移了。
  • 定时器清理这类细节靠人肉复制，漏一处就是一次泄漏。
  • 逻辑和 UI 混在同一个组件里，想单独验证倒计时行为几乎无从下手。
  • 组件体积越滚越大，最后又变回「什么都往里塞」的大杂烩。

组合式函数封装

不推翻「就地写逻辑」，而是把它抽成一个普通函数：把响应式状态、派生值、方法和生命周期钩子一起封装进去，在外面看只暴露一组可以直接使用的状态与行为。这样的函数就是组合式函数（composable）。

  1. 组件调用 useCountdown，并传入初始秒数。
  2. 函数内部管理 seconds、isFinished 以及 start、reset 等方法。
  3. 组件只负责渲染倒计时、触发按钮动作，不再关心计时细节。
  4. 把它接到第二个组件上，验证逻辑无需复制就能复用。

它能成立的关键在于：组合式函数借助组合式 API 的运行时上下文，内部创建的 ref 与副作用会自动挂载到调用它的那个组件实例上。所以同一份函数被两个组件调用，得到的是两份互不干扰的独立状态——这正是它替代旧 mixin 的地方：复用逻辑，而不复用 UI，也不制造隐式的命名冲突。

两条纪律：其一，函数内的 ref 与生命周期钩子依赖调用上下文，必须在 setup 的同步阶段调用，不能塞进异步回调或事件里延后执行；其二，返回值要少而明确，把状态和方法收窄成清晰的接口，别让调用方又拿到一袋什么都有的东西。

命名上也藏着一层约定：以 use 开头，等于告诉读代码的人「这里可能用到响应式和生命周期能力」。逻辑一旦被抽出来成为独立单元，就应当优先为它补上单元测试——这正是复用带来的额外红利。

同一逻辑重复调用

状态逻辑抽取复用

组合式函数把「一段有状态的逻辑」打包成一个普通函数：状态、派生值、方法和生命周期钩子都在里面，组件调用它就能拿到一组可直接使用的行为。它复用的是逻辑而非 UI，是 mixin 的现代替代方案。

「组合式函数」是以 use 开头、把响应式状态、派生值、方法与生命周期钩子封装起来的普通函数。借助组合式 API 的运行时上下文，函数内的 ref 与副作用能挂载到调用它的组件实例上，因此多个组件调用同一函数会得到各自独立的状态。它须在 setup 同步阶段调用，用于复用逻辑而非 UI。
承接上文：五个搜索框都要「一进页面就自动聚焦」，难道每个组件里都写一遍 ref 加 onMounted？这套样板代码能不能只写一次？

输入框自动聚焦

你在做一个课程搜索页，输入框希望打开就自动获得焦点，用户不用手动点一下。类似的小需求还有很多：点击输入框外部就关闭下拉、列表项滚动到可视区时淡入、长按时弹出菜单、拖拽某个卡片。这些需求的共同点是——它们都必须作用在一个具体的真实 DOM 元素上，读它的属性、调它的方法、给它挂一个原生监听。

而这个动作出现得非常频繁。搜索框、评论框、登录表单，五处都要自动聚焦；三个下拉都要「点击外部关闭」。每次都用「拿 ref，在 onMounted 里操作元素」的套路复制一遍，代码会迅速被这类底层细节淹没，而且清理逻辑经常被漏掉。

组件内模板引用

最省事的做法：在每个需要聚焦的组件里，声明一个 ref，绑定到输入框，然后在 onMounted 里调用 el.focus()。

这个方案做对了一件必要的事：它直击真实 DOM，没有绕弯。聚焦、监听、观察尺寸这类操作本来就属于 DOM 层，绕开它反而做不成。只要场景只有一两处，这么写清清楚楚，无可厚非。

行为逻辑重复代价

  • 同一个行为要在多个组件里重复写一遍，五处聚焦就是五份几乎一样的代码。
  • 逻辑散落在各处，规则一改（比如聚焦后还要全选文本）要同步好几处，容易漏。
  • 涉及事件监听的场景（点击外部关闭），取消监听的清理逻辑常常被忘掉，留下内存泄漏和幽灵行为。
  • 想把它抽成一个普通函数复用，可函数里拿不到那个具体的 el——元素在组件模板里，不在函数手里。

自定义指令与元素

不推翻「直接操作 DOM」，而是给这种行为找一个能拿到 el 的复用位置。这就轮到自定义指令登场：它直接把逻辑绑在真实 DOM 元素上，在元素挂载时把 el 交给你。

  1. 定义一个指令对象，在 mounted 钩子里接收绑定到它的 DOM 元素。
  2. 钩子里调用 el.focus()，完成聚焦动作。
  3. 组件模板里用 v-focus 一个词声明这个行为，不再写 ref 与 onMounted。
  4. 把 v-focus 从元素上移除，聚焦行为随之消失，没有残留副作用——这说明它确实和元素绑定在一起。

换个角度理解：组件和组合式函数擅长表达的是业务状态与 UI 结构，而指令擅长的是低层 DOM 行为。自动聚焦、点击外部关闭、权限显隐、滚动观察、拖拽、长按，这些当业务能落到一个具体 DOM 节点上的需求，用指令比用组件更轻量也更直接。判断的分界线在于：如果你要封装的是「一段视图 + 状态」，用组件；如果只是「给某个元素加一种行为」，用指令。

两条必须守住的纪律：其一，涉及事件监听的指令，一定要在 unmounted 里把监听器清理掉，否则元素被移除后监听仍然挂在那里，既漏内存又可能触发意外逻辑；其二，指令应该尽量小而专注，只封装一件 DOM 级的事，别把业务规则也塞进去。

指令的参数也会随绑定更新：传给它的 value 以及 v-focus.once 这样的修饰符，都可能在运行时变化，在 updated 钩子里能读到最新的值，于是可以做到「数值变了就重新对齐」「开关变了就启停监听」。这让指令不只是一个一次性动作，而是能响应数据变化的 DOM 行为。

自动落点与聚焦

底层行为与视图分离

自定义指令把「重复的底层 DOM 行为」从组件里抽出来，用一个可复用的词——比如 v-focus——声明在元素上。它适合落在具体 DOM 节点上的需求：自动聚焦、点击外部关闭、权限显隐、滚动观察、拖拽、长按。但业务状态和 UI 结构仍应交给组件或组合式函数，指令保持小而专注，并在 unmounted 里清理好自己挂上的监听。

「自定义指令」是作用在真实 DOM 元素上的复用单元，适合封装自动聚焦、点击外部关闭、权限显隐、滚动观察、拖拽、长按等低层 DOM 行为；当需求能落到一个具体 DOM 节点时，它比组件更轻量。使用 mounted 拿到 el，在 updated 里读取最新的 value 与修饰符，并在 unmounted 中清理事件监听器。

关键代码

Vue
<script setup lang="ts">
import { useCountdown } from '../composables/useCountdown'

const { seconds, isFinished, start, reset } = useCountdown(5)
</script>

<template>
  <div class="demo-card">
    <h3>验证码倒计时</h3>
    <strong>{{ isFinished ? '可以重新发送' : `${seconds} 秒后可重发` }}</strong>
    <button @click="start">发送验证码</button>
    <button @click="reset">重置</button>
  </div>
</template>
