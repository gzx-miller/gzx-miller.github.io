人机交互：interrupt 中断与恢复

用退款审批展示 interrupt 挂起、checkpointer 保存现场、Command 从断点恢复。

开场问题：退款 Agent 上线了：自动校验订单、自动执行退款，全程无人值守——直到一位用户申请退款 880 元，超过了财务规定的审批线。Agent 爽快地打了钱。你后知后觉：有些决定，机器不该自己拍板。

全自动流程的决策边界

前几课一直在给 Agent 加自主性：自己调工具、自己分支、自己循环。但自主性有个天花板——涉及钱的、不可逆的、合规要求留痕的决定，必须留一个人工关卡。天真的做法是「流程跑到临界点就抛异常退出，等人处理完再从头跑」：状态丢了、前面的步骤白跑、两次执行的输入还可能不一致。

要回答的是：怎样让流程在关键节点主动「停住」，把决定权交给外部的人，人从断点处继续——而不是推倒重来？

无状态中断的两个断点

  • 停不住：普通函数一路执行到底，「跑到一半等人」在没有状态持久化的前提下根本无法表达。
  • 接不上：就算手动保存了上下文，恢复时用什么把新的决定「送回」到原来那个节点，没有标准答案。
  • 接错人：中断时抛出的问题如果只是一段日志，审批人看不到结构化选项，恢复时的回传值也没有类型约束。
  • 丢现场：从异常退出到恢复之间，程序可能重启、刷新、换实例，内存里的中间结果全部蒸发。

中断、检查点、恢复三件套

不推翻「流程要停」，而是把「停」变成框架的一等公民。LangGraph 给出三个配套机制。

  1. interrupt 主动中断：在节点里调用 interrupt({ question, options })，流程在这里挂起——不是抛异常，而是暂停。函数的参数就是抛给外部的问题描述，结构化的选项让前端能直接渲染成审批按钮。
  2. checkpointer 保存现场：编译图时挂上 checkpointer（如 MemorySaver），每次状态变更都按 thread_id 存档。挂起期间的现场不在内存里，而在检查点里——进程重启也不丢。
  3. Command 恢复执行：审批人做出决定后，用 new Command({ resume: 'approved' }) 再次 invoke 同一个线程。框架从检查点重建状态，把 resume 的值作为 interrupt 的返回值注入节点，从断点继续往下跑。
同一个节点两种命运：金额在阈值内时，interrupt 根本不会被调用，节点顺势往下走——「自动通过」与「人工审批」不是两条链路，而是同一个节点的两个分支。中断的条件留给业务逻辑，框架只管「停了能接回来」。

退款审批中断与恢复演示

把决定权交还给人的价值

人机交互解决的是「流程何时不该自动」：用 interrupt 在关键节点挂起，用 checkpointer 保住现场，用 Command(resume) 从断点接回。Agent 的自动化程度并没有降低——只是把不可逆的决定，停在了需要人的那一格。

「Human-in-the-Loop（HITL）」指在自动流程的关键节点插入人工决策：节点内调用 interrupt(问题) 暂停执行，checkpointer 按 thread_id 保存完整状态，外部用 Command({ resume }) 传回决定并恢复。要记住的边界：没有 checkpointer 就没有中断能力（挂起即丢失）；resume 的值会原样成为 interrupt 的返回值，写法不同会错位；同一 thread 上不允许多个中断同时悬而未决。

关键代码

TypeScript
// 人机交互：用 interrupt 中断执行，等人批准后从断点恢复
// 场景：退款审批——金额超过 500 元时必须人工审批，批准后继续执行
import { StateGraph, StateSchema, START, END, interrupt, Command, MemorySaver } from '@langchain/langgraph'
import { z } from 'zod/v4'

const OrderState = new StateSchema({
  orderId: z.string(),
  amount: z.number(),
  decision: z.enum(['approved', 'rejected']).nullable().default(null),
  result: z.string(),
})

// 示例1: 审核节点里调用 interrupt 暂停执行
// interrupt 的参数会成为「等待人工输入」时暴露给前端的问题描述
async function reviewNode(state: typeof OrderState.State) {
  if (state.amount <= 500) {
    return { decision: 'approved', result: '金额在阈值内，自动通过' }
  }

  const decision = interrupt({
    question: `订单 ${state.orderId} 申请退款 ￥${state.amount}，是否批准？`,
    options: ['approved', 'rejected'],
  })

  return { decision, result: '' }
}

// 示例2: 执行节点根据人工决定继续跑
async function executeNode(state: typeof OrderState.State) {
  const result =
    state.decision === 'approved' ? `订单 ${state.orderId} 已退款 ￥${state.amount}` : `订单 ${state.orderId} 退款被驳回`
  return { result }
}

const graph = new StateGraph(OrderState)
  .addNode('review', reviewNode)
  .addNode('execute', executeNode)
  .addEdge(START, 'review')
  .addEdge('review', 'execute')
  .addEdge('execute', END)

// 示例3: 编译时必须挂 checkpointer——中断时的状态保存全靠它
const app = graph.compile({ checkpointer: new MemorySaver() })

const config = { configurable: { thread_id: 'order-20261013-001' } }

// 示例4: 第一次 invoke——流程在 interrupt 处挂起，返回 __interrupt__ 字段
const first = await app.invoke({ orderId: 'A-1001', amount: 880 }, config)
console.log('挂起等待审批:', JSON.stringify(first.__interrupt__))

// 示例5: 检查点里保留了完整状态快照，随时可以查「走到哪了」
const snapshot = await app.getState(config)
console.log('当前节点:', snapshot.next) // ['review']

// 示例6: 用户在前端点「批准」——用 Command({ resume }) 从断点恢复
const resumed = await app.invoke(new Command({ resume: 'approved' }), config)
console.log('恢复后结果:', resumed.result) // 订单 A-1001 已退款 ￥880

// 若审批被驳回：new Command({ resume: 'rejected' }) → 退款被驳回
// 同一 thread_id 可再次发起新订单，历史检查点都在
