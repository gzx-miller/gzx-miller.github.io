上下文工程：State、Store 与 Runtime

区分三层上下文：图内状态、运行时注入参数、跨会话档案的职责与读取方式。

开场问题：推荐节点上线后越来越臃肿：学生水平从环境变量读、浏览历史从数据库查、会话状态从参数传——同一个节点里三种取数方式混在一起。测试时想造一个「进阶水平」的用例，得同时改三个地方；上线后才发现，环境变量在某个实例上根本没配。

数据来源没有分工的混乱

上一课的记忆分成了两层，但「数据从哪来、节点怎么拿」还没有统一的约定。现实中节点要读取的东西至少有三类，它们的生命周期完全不同：这次运行才有的中间结果、每次调用注入的外部参数、跨会话常驻的用户档案。混在一起用全局变量传递，会带来两种典型事故：

  • 串数据：用模块级变量盛放「用户水平」这类每次请求都可能不同的参数，并发一上来就互相污染。
  • 测试难：节点直接依赖外部的数据库、环境变量，想单测只能整套环境一起搬。

要回答的是：三类上下文各放哪里、节点按什么规矩读，才能既不出错又容易测试？

三层上下文各就各位

LangGraph 的答案是把数据按生命周期分配进三个明确的容器，节点拿到手的读取方式各不相同。

  1. State——这一次运行的共享白板：随每次 invoke 创建，节点之间读写流转。放流程的临时结果：问题、草稿、中间日志。特点：会随检查点保存，因此别放密钥、别放超大对象。
  2. Runtime Context——这一次调用的注入参数：用 Schema 声明形状（如 grade、locale），invoke 时传入，节点只读。放用户身份、环境配置、功能开关这类「外部决定、流程内消费」的参数——不参与状态流转，也就不受 reducer 与检查点的干扰。
  3. Store——跨越所有运行的长期档案：节点通过 runtime.store 读写，和 thread 无关。放用户画像、偏好、可检索的知识补充。

三条数据线在节点里各走各的门：State 在第一个参数 state，Context 与 Store 在第二个参数 runtime（runtime.context / runtime.store）。看着取数代码就知道数据的生命周期——这是上下文工程最直接的收益。

它们最终汇合在模型输入里：无论来源是哪一层，进入模型前都会被「装配」成消息文本——Context 的水平、Store 的浏览记录拼进 system 消息，State 的问题作为 human 消息。上下文工程的全部功夫，就是在装配这一步让该出现的信息出现、不该出现的绝不出现。

三层上下文组装演示

按生命周期分层取数

上下文工程解决的是「数据放哪里、怎么读」：State 管一次运行的共享状态，Context 管一次调用的只读注入，Store 管跨会话的长期档案。节点按生命周期取数，装配成模型输入——职责清晰了，测试和并发问题自然消失。

「三层上下文（State / Context / Store）」按生命周期分工：State 随单次运行创建、节点间读写、随检查点保存；Context 由调用方注入、节点只读、不参与状态合并；Store 跨运行持久、按命名空间存取。要记住的边界：把每次请求变化的参数放进模块级变量会串数据，应走 Context；把用户档案塞进 State 会撑大每个检查点，应走 Store；三层最终都要「装配」进模型消息，装什么、不装什么，是效果与成本的第一道闸门。

关键代码

TypeScript
// 上下文工程：分清 State、Store 与 Runtime 三种上下文
// 场景：课程推荐智能体——图内状态、跨会话记忆、运行时注入三层分工
import { StateGraph, Annotation, START, END, InMemoryStore } from '@langchain/langgraph'
import { ChatOpenAI } from '@langchain/openai'
import { createMiddleware } from 'langchain'
import { HumanMessage, SystemMessage } from '@langchain/core/messages'
import { z } from 'zod'

const model = new ChatOpenAI({ model: 'gpt-4o-mini', temperature: 0 })

// 示例1: 第一层——State 是「图内状态」：跟着这次运行走，节点间共享读写
const RecState = Annotation.Root({
  query: Annotation<string>,
  answer: Annotation<string>,
  logs: Annotation<string[]>({
    reducer: (left, right) => left.concat(right),
    default: () => [],
  }),
})

// 示例2: 第二层——Context 是「运行时配置」：外部注入、节点只读
// 用 Zod 声明上下文结构，invoke 时通过 context 传入
const ContextSchema = z.object({
  grade: z.enum(['beginner', 'advanced']).describe('学生水平，决定内容深度'),
  locale: z.string().default('zh-CN'),
})

// 示例3: 第三层——Store 是「跨会话长期数据」：不受 thread 限制
async function recommendNode(state: typeof RecState.State, runtime: any) {
  // 从运行时上下文读取注入参数
  const { grade } = runtime.context
  // 从 Store 读取长期偏好
  const history = await runtime.store.get(['learning', 'student-01'], 'viewed')
  const viewed = history?.value?.topics?.join('、') || '无'

  const response = await model.invoke([
    new SystemMessage(`学生水平：${grade}；最近浏览：${viewed}`),
    new HumanMessage(state.query),
  ])

  return { answer: response.content, logs: [`按 ${grade} 难度推荐，参考浏览记录（${viewed}）`] }
}

const graph = new StateGraph(RecState)
  .addNode('recommend', recommendNode)
  .addEdge(START, 'recommend')
  .addEdge('recommend', END)

const store = new InMemoryStore()
const app = graph.compile({ store })

// 示例4: invoke 时同时传入「图输入」和「运行时上下文」，两者互不干扰
await store.put(['learning', 'student-01'], 'viewed', { topics: ['组合式 API', '响应式原理'] })

const result = await app.invoke(
  { query: '接下来该学什么？' },
  { context: { grade: 'beginner', locale: 'zh-CN' } },
)
console.log('推荐:', result.answer)
console.log('过程日志:', result.logs)

// 示例5: 中间件同样能读到 context——用它给模型动态注入系统提示
const contextualPrompt = createMiddleware({
  name: 'ContextualSystemPrompt',
  wrapModelCall: async (request, handler) => {
    const grade = (request.runtime.context as any)?.grade ?? 'beginner'
    const system = new SystemMessage(`当前学生水平：${grade}。请据此调整讲解深度。`)
    return handler({ ...request, systemPrompt: system })
  },
})

// 示例6: 三层上下文的分工口诀
// State   —— 单次运行的共享白板：临时结果、流程数据
// Context —— 每次调用的注入参数：用户身份、环境配置，节点只读
// Store   —— 跨运行的长期档案：偏好、历史，可读可写可检索
console.log('State 管一次运行，Context 管一次调用，Store 管长期记忆')
