流式界面：事件流驱动的对话前端

messages 与 updates 两类事件流经 SSE 到前端，驱动打字机与步骤条。

开场问题：Agent 后端跑得挺流畅，前端却在「转圈」：用户点下发送，要等整个过程跑完——检索几秒、生成几秒——十几秒后答案整段蹦出来。用户盯着空白的对话区，以为程序死掉了，刷新键按了三次。

批式响应与实时感的落差

前面的课程都在解决「后端怎么把事做对」，这一课解决「结果怎么让用户看见」。invoke 是批式的：等整张图跑完才返回最终结果。但图的执行其实是一系列有条理的中间步骤——检索开始、检索完成、开始生成、逐 token 输出——这些中间步骤白白浪费了。

要回答的是：怎么把图执行过程中的中间状态「实时吐出来」，让界面从「等结果」变成「看过程」？

两种流模式：进度与内容

把 invoke 换成 stream，并指定关心的模式，LangGraph 就能把执行过程一条条交出来：

  1. messages 模式——逐 token 的“内容流”：模型每生成一段就产出一条 token 事件，附带 langgraph_node 元信息标明出自哪个节点。前端拿它做打字机效果，用户立刻看到「它在思考、在写」。
  2. updates 模式——节点级的“进度流”：每个节点完成时产出「节点名 + 该节点的状态更新」。前端拿它做步骤条：「正在检索课程库 → 正在生成回答」。它也是调试时最好用的一双眼睛。
  3. 交付到浏览器——SSE：服务端把事件循环写成 SSE（text/event-stream），前端用 EventSource 或 fetch 流读取，一条条消费。协议很朴素：每个事件一行 data:，断线由浏览器自动重连。
前端把事件映射成状态，而不是直接拼 DOM：推荐先定义 UI 状态（步骤条当前节点、气泡累计文本、是否生成中），再把事件翻译成状态变更——token 事件改变气泡文本，updates 事件改变步骤条。两种流交错到达时，状态机保证界面永远自洽。
三个必须处理的边界：停止生成（用 AbortController 中断读取，服务端也要终止图执行，否则 token 照样在烧）；断流降级（网络中断时把已收到文本保留，提示重试）；错误事件（图内节点抛错要以事件形式送达，UI 才能从「生成中」态退出，而不是永远转圈）。

事件流驱动界面演示

把执行过程还给用户

流式界面解决的是「执行过程的可视化」：messages 流给内容、updates 流给进度，经 SSE 送到前端，由状态机翻译成打字机与步骤条。首字即反馈、过程即进度——用户等的每一秒都能看见意义。

「流式输出（Streaming）」指用 stream 替代 invoke，按模式消费执行过程：messages 逐 token 输出内容（打字机），updates 逐节点输出状态更新（进度条），服务端经 SSE 推送、前端按状态机消费。要记住的边界：停止生成要同时中断前端读取与后端执行；断流时保留已收文本并支持重试；错误要以事件送达，别让 UI 停在「生成中」；token 事件可能早于/晚于节点事件到达，界面状态要写成可乱序的。

// 流式界面：把图的执行事件接到前端 UI
// 场景：Vue 聊天页——token 边生成边显示，节点进度实时可见
import { createReactAgent } from '@langchain/langgraph/prebuilt'
import { ChatOpenAI } from '@langchain/openai'
import { tool } from '@langchain/core/tools'
import { HumanMessage } from '@langchain/core/messages'
import { z } from 'zod'

const agent = createReactAgent({
  llm: new ChatOpenAI({ model: 'gpt-4o-mini', temperature: 0, streaming: true }),
  tools: [
    tool(async ({ keyword }) => `检索到 3 门「${keyword}」课程`, {
      name: 'search_courses',
      description: '搜索课程库',
      schema: z.object({ keyword: z.string() }),
    }),
  ],
  prompt: '你是课程助手，回答前先检索课程库。',
})

// 示例1: messages 模式——逐 token 输出模型生成内容，接打字机效果
const tokenStream = await agent.stream(
  { messages: [new HumanMessage('推荐三门 Vue3 课程')] },
  { streamMode: 'messages' },
)

for await (const [messageChunk, meta] of tokenStream) {
  // meta.langgraph_node 标注这段 token 出自哪个节点
  if (meta?.langgraph_node === 'agent' && typeof messageChunk.content === 'string') {
    process.stdout.write(messageChunk.content)
  }
}

// 示例2: updates 模式——节点级进度，适合渲染「正在检索…」这类步骤条
const updateStream = await agent.stream(
  { messages: [new HumanMessage('推荐三门 Vue3 课程')] },
  { streamMode: 'updates' },
)

for await (const chunk of updateStream) {
  const [nodeName, update] = Object.entries(chunk)[0] as [string, any]
  const hasToolCall = (update.messages ?? []).some((m: any) => m.tool_calls?.length)
  console.log(`[进度] ${nodeName} ${hasToolCall ? '→ 决定调用工具' : '→ 产出消息'}`)
}

// 示例3: 两种模式同时订阅——LLM 只要一份输出，UI 可以两路都用
// （真实项目用 stream 组合模式数组，这里演示各自用法）

// 示例5: 前端状态设计——把事件映射成三种 UI 状态
type UiEvent =
  | { kind: 'nodeStart'; node: string } // 步骤条：点亮节点
  | { kind: 'token'; text: string } // 气泡：追加文字
  | { kind: 'done' } // 收尾：移除「停止」按钮

function toUiEvent(nodeName: string, update: any): UiEvent[] {
  if (nodeName === 'tools') return [{ kind: 'nodeStart', node: '检索课程库' }]
  const token = (update.messages ?? []).map((m: any) => m.content).join('')
  return token ? [{ kind: 'token', text: token }] : []
}

// 示例6: 边界处理
// - 停止生成：AbortController 中断 stream 迭代，避免用户等完
// - 错误事件：try/catch 包住 for await，断流时降级为整段轮询
// - 顺序保证：两种流可能交错到达，UI 用同一事件序号时间线对齐
console.log(toUiEvent('tools', {}))
