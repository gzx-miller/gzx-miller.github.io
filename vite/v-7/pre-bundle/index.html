依赖预构建

理解 Vite 使用 Esbuild 预构建 node_modules 依赖的原因和配置方式。

开场问题：你 npm install lodash 后写下 import debounce from 'lodash/debounce'，本地一刷新直接白屏，控制台甩出一句 require is not defined——浏览器明明支持 ESM，为什么一个正常安装的包会当场崩掉？

依赖格式转换

浏览器只认 ESM，而 npm 上大量包是用 CommonJS/UMD 写的——它们内部用的是 require 和 module.exports，浏览器不认识。麻烦还不止格式：很多包内部被拆成了成百上千个小模块（比如 lodash-es 一个函数一个文件），就算格式没问题，浏览器也得为它们发起成百上千次请求。

如果退回「把依赖整体打包」的老办法，人要付出的隐藏成本是：每次冷启动都要重新打包整个依赖图，项目越大启动越慢；任何一个文件改动都要重新构建，热更新的延迟随依赖规模一起增长。于是问题变成：能不能既保留原生 ESM 的按需加载，又同时避开 CommonJS 和模块碎片这两个坑？

启动期依赖转译

最直接的想法：启动时先把 node_modules 里的依赖统一「翻译」一遍，用极快的 esbuild 把 CommonJS/UMD 统统转成 ESM。

这个方案做对了一件事：让浏览器有办法加载任何来源的包，无论它是 CommonJS 还是 UMD，转换之后都能当作标准 ESM 被 import 进来。

模块碎片化请求

  • 只转格式不够：lodash-es 内部几百个文件转完还是几百个，浏览器仍要发几百次请求，Network 面板像瀑布一样往下排，首屏照样慢。
  • 每次启动都跑一遍，冷启动并没有变快，只是把代价从「打包业务源码」转移到了「处理依赖」。
  • 动态 import() 的路径是运行时拼出来的，静态扫描发现不了，运行时才报 404。
  • 有些包本就是规整 ESM、模块又少，硬走一遍预构建反而多此一举。

合并与缓存复用

先补「格式化」。预构建的第一件事确实是格式转换：esbuild 把 CommonJS/UMD 转成浏览器能直接加载的 ESM，require is not defined 就此消失。

接着补「合并」。光转格式治不了模块碎片，于是预构建会把一个依赖的众多内部模块合并成单个文件——lodash-es 的几百个文件被打成一个 lodash-es.js，浏览器一次请求就拿到全部。这正是「100+ 次请求变成 1 次」背后的机制。

再补「缓存」。每次都重新合并显然是浪费，于是 Vite 把预构建产物带 hash 缓存在 node_modules/.vite/deps/。启动时它算一遍依赖指纹，与缓存里的元数据比对，一致就直接复用，跳过预构建。指纹会覆盖依赖与配置的变化，任一变动即整份失效重算：

  • package.json 里的依赖列表变化。
  • lockfile（package-lock.json / yarn.lock / pnpm-lock.yaml）变化。
  • vite.config.ts 中 optimizeDeps 配置变化。
  • NODE_ENV 变化。

需要手动放弃缓存时，删掉 node_modules/.vite 或启动时加 vite --force 即可强制重建。

再往下补「谁来预构建」。默认 Vite 会扫描源码里的 import 自动发现依赖，但动态 import() 的路径是拼出来的，扫不到——这类依赖要手动加进 optimizeDeps.include 强制预构建，否则运行时 404。反向地，本来就是规整 ESM、模块又少的包，可以用 optimizeDeps.exclude 排除，省掉一次没必要的预构建。

两条边界：预构建只处理第三方依赖，业务源码不参与，所以 include 里绝不能写 src 下的路径；产物是带 hash 的缓存，依赖升级或行为诡异时，先把 node_modules/.vite 删掉再重启，能排除一大半「改了没生效」的怪问题。

预构建动机与配置

开发期依赖预处理

依赖预构建是开发服务器为第三方依赖做的一次性「预处理」：用极快的 esbuild 把 CommonJS 转成 ESM、把碎片模块合并成单文件，再把结果按 hash 缓存起来供后续启动复用。它只服务于开发阶段的加载效率，业务源码不参与，生产构建也不走这条路。

「依赖预构建」指首次启动时用 esbuild 把 node_modules 中的依赖转成 ESM 并合并成单个文件，产物缓存在 node_modules/.vite。它既解决了 CommonJS/UMD 无法被浏览器加载的问题，也压掉了海量模块请求。边界：只处理第三方依赖、不处理业务源码；缓存随依赖与配置的 hash 失效，异常时用 --force 或删除缓存强制重建。

关键代码

TypeScript
// vite.config.ts - 依赖预构建配置
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  optimizeDeps: {
    // 强制预构建的依赖
    include: [
      'lodash-es',
      'dayjs',
      // 子模块也要预构建
      'lodash-es/debounce',
      // 自定义包
      '@my-org/utils'
    ],
    
    // 排除不预构建的依赖
    exclude: ['vue-demi'],
    
    // 预构建时的 esbuild 配置
    esbuildOptions: {
      // 目标环境
      target: 'es2020',
      // 插件
      plugins: []
    },
    
    // 是否在开发服务器启动时强制预构建
    force: false
  }
})

// ====================
// 为什么需要预构建？
// ====================

// 1. CommonJS / UMD 兼容性
// 浏览器只支持 ESM，预构建将 CommonJS 转换为 ESM
import lodash from 'lodash' // CommonJS → ESM

// 2. 减少 HTTP 请求数
// 一个包有上百个模块 → 预构建为单个文件
import { debounce, throttle } from 'lodash-es'
// 原本可能发起 100+ 请求 → 预构建后只发 1 个

// ====================
// 缓存机制
// ====================

// 预构建产物缓存在:
// node_modules/.vite/deps/

// 缓存失效条件:
// - package.json 的 dependencies 变化
// - 包管理器 lockfile 变化 (package-lock.json, yarn.lock, pnpm-lock.yaml)
// - vite.config.ts 中 optimizeDeps 配置变化
// - NODE_ENV 变化

// 手动清除缓存并强制重新预构建:
// rm -rf node_modules/.vite
// 或启动时: vite --force

// ====================
// 自动依赖发现
// ====================

// Vite 会自动扫描源码中的 import 语句
import axios from 'axios'           // 自动发现
import { ref } from 'vue'          // 自动发现
import dayjs from 'dayjs'          // 自动发现

// 但动态导入可能无法被自动发现
const module = await import(someDynamicPath)
// 这种情况需要手动加到 include 中
