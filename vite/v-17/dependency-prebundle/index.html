依赖预构建与缓存优化

理解 Vite 使用 esbuild 预构建依赖的原理，掌握缓存优化和配置。

开场问题：你把某个依赖升级了一个版本，package.json 和 lockfile 都改过了，重启开发服务器——行为还是旧的。你翻遍业务代码也找不到线索，最后抱着试试看的心态删掉整个 node_modules/.vite，一重启，新版本生效了。明明依赖变了，Vite 为什么没察觉？

缓存复用成本

上一课你已经知道：预构建把依赖转成 ESM 合并成单文件，是为了让开发服务器快。但「快」是有代价的——它把结果缓存下来复用，而不是每次启动都重算。缓存一旦存在，就必须回答一个问题：这份产物还代表当前的依赖吗？

如果每次启动都重算，冷启动永远慢，「预构建」的意义也就没了；如果永远信任缓存，依赖升级了却读到旧产物，就会像开场那样「改了没生效」。于是核心问题不是「怎么预构建」，而是怎么判断一份预构建缓存还能不能用。

指纹比对机制

最直接的想法：把产物写进 node_modules/.vite，同时记一份说明，启动时比对说明和当前情况，一致就跳过预构建。

这个方案做对了一件事：它让第二次启动不必重算。开销被一次性付掉，后续启动直接读现成的文件。

动态导入漏判

  • 比对用的「说明」覆盖不全就会漏判：动态 import() 的依赖静态扫描发现不了，它压根不在缓存清单里，运行时才报 404。
  • 缓存是「要么整份有效、要么整份重算」，一条输入变了就全废，看不出是哪条引起的。
  • 既然缓存能长期有效，人就会误以为「改了就会生效」——手工改过的 node_modules、本地 link 的包根本不在比对范围内。
  • 启动变慢时，人第一反应是怀疑 CPU 或磁盘，很少想到是缓存失效后被反复重算。

失效条件构成

先补「缓存里到底存了什么」。node_modules/.vite/deps/ 下每个依赖一个 .js 加一份 .js.map，另有一份 _metadata.json，记录当时的依赖列表与 hash、以及配置的指纹。启动时 Vite 拿当前情况算出指纹，和这份元数据一比：相同就跳过预构建，不同就整份重建。

接着补「什么会让指纹变化」。这组输入就是缓存失效的条件，任一条变动都会作废整份缓存：

  • package.json 里的依赖列表变化。
  • lockfile（package-lock.json / yarn.lock / pnpm-lock.yaml）变化。
  • vite.config.ts 中 optimizeDeps 配置变化。
  • NODE_ENV，以及配置文件里用到的 VITE_ 环境变量变化。
  • 显式设置 force 或启动时加 --force。

那为什么开场里依赖变了却还读到旧行为？因为指纹只覆盖它算进去的输入。手工改过的文件、本地 link 进来的包不在其中，这时唯一的办法就是强制重算。手动控制缓存有三种等价手段：删掉 node_modules/.vite、启动时 vite --force、或配置 optimizeDeps.force = true。

再补「排障清单」。既然预构建的问题大多能归到「缓存」或「哪些依赖参与」两类，可以照症状对症：

  1. 某个包运行时 404：多半是动态 import() 没被扫到，把它加进 optimizeDeps.include 强制预构建。
  2. CommonJS 包报 require is not defined：通常 esbuild 能自动转，个别包仍出错就加进 include 再试。
  3. 启动太慢：先确认缓存是否有效（无效会被反复重算），再减少 include 里不必要的项。
  4. 依赖更新没生效：优先 --force 或删缓存，先排除缓存因素再怀疑代码。

最后补「monorepo 场景」。本地 link 的包不在依赖指纹的自然覆盖里，建议加入 include 强制预构建，并配上 resolve.dedupe，避免同一个依赖被打出多份实例。

两条容易踩的线：include 里只能写第三方依赖，绝不能写 src 下的业务路径——预构建压根不处理业务源码；遇到「改了没生效」这类诡异现象，先 --force 重算一次，能排除一大半缓存问题，再回头看代码。

排障与重建策略

预构建快，是因为它把结果缓存了下来；缓存可信，是因为它记了一份指纹来比对。理解「哪些输入会让指纹失效」以及「哪些变化根本不在指纹里」，就握住了 optimizeDeps 的大部分排障钥匙——多数「改了没生效」，答案都是清缓存或 --force。

「缓存失效（cache invalidation）」指判断一份缓存是否还能代表当前真实输入的过程：命中就复用，失效就重建。Vite 用依赖列表、lockfile、optimizeDeps 配置、NODE_ENV 等一组输入来判定预构建缓存是否有效。边界：失效判断只覆盖它算进去的输入，手工改动的 node_modules、本地 link 的包都不在其中，所以「改了没生效」时强制重算才是第一诊断手段。

TypeScript
// vite.config.ts - 依赖预构建详细配置
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  optimizeDeps: {
    // 强制预构建的依赖
    include: [
      // 完整的包
      'lodash-es',
      'dayjs',
      // 子模块（如果未被自动发现）
      'lodash-es/debounce',
      'lodash-es/throttle',
      // 作用域包
      '@vueuse/core',
      // monorepo 内部包
      '@my-org/utils'
    ],
    
    // 排除不预构建的依赖
    exclude: [
      // Vue 插件通常不需要预构建
      'vue-demi',
      // 纯 ESM 且模块少的包
      'nanoid'
    ],
    
    // esbuild 转换选项
    esbuildOptions: {
      // 目标环境
      target: 'es2020',
      // 支持的平台
      platform: 'browser',
      // 插件
      plugins: [
        // 自定义 esbuild 插件
      ]
    },
    
    // 是否强制重新预构建（忽略缓存）
    force: false,
    
    // 预构建的入口文件
    entries: ['index.html']
  }
})

// ====================
// 缓存机制详解
// ====================

// 缓存位置:
// Linux/Mac:  node_modules/.vite/deps/
// Windows:    node_modules\.vite\deps\

// 缓存文件:
// - vue.js              # 预构建后的 Vue
// - vue.js.map          # sourcemap
// - _metadata.json      # 元数据（依赖列表、hash 等）

// 缓存失效条件:
// 1. package.json 的 dependencies 变化
// 2. 包管理器 lockfile 变化 (package-lock.json / yarn.lock / pnpm-lock.yaml)
// 3. vite.config.ts 中 optimizeDeps 配置变化
// 4. VITE_ 前缀的环境变量变化（如果配置文件用到了）
// 5. NODE_ENV 变化
// 6. force: true 或 vite --force

// ====================
// 手动控制缓存
// ====================

// 清除缓存并强制重新构建:
// 1. 删除目录: rm -rf node_modules/.vite
// 2. 启动参数: vite --force
// 3. 配置选项: optimizeDeps.force = true

// 缓存预热（开发服务器启动时）:
// server.warmup 可以提前转换常用模块

// ====================
// 常见问题与解决方案
// ====================

// 问题 1: 某个包找不到（动态 import 的依赖）
// 解决: 手动添加到 include
optimizeDeps: {
  include: ['some-dynamic-dep']
}

// 问题 2: CommonJS 包报错
// 解决: esbuild 通常能自动转换，如不行则:
optimizeDeps: {
  include: ['problematic-cjs-package']
}

// 3. 升级 esbuild
