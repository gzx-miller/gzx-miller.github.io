动态内存管理：new/delete 与内存布局

理解栈、堆与全局区的内存布局，掌握 new/delete 的配对使用与常见内存错误。

开场问题：一个数组的长度要等运行起来读到配置才知道，栈上定长的 int arr[10] 显然不够用；于是用 new int[n] 在运行时向堆申请，程序跑起来看着完全正常，可跑久了内存越吃越多，最后被系统杀掉——明明每次都分配成功了，为什么内存却像凭空消失了一样？

内存的地图：全局区、栈区与堆区

先捋清楚程序把变量放在哪里。抛开具体实现，一个运行中的程序可以粗略看成三块存储区，它们最本质的差别是生命周期由谁决定。

  • 全局区：全局变量与静态变量住在这里，程序启动时建立、结束时才回收，生命周期与整个进程一致。
  • 栈区：函数内的局部变量与函数调用现场放在这里，随函数进入而分配、随函数返回而自动回收，由编译器负责，快而不用管。
  • 堆区：一块供程序自由取用的内存池，容量比栈大得多，生命周期完全由程序员自己掌握——申请时建立，释放时回收，编译器不会替你做任何事。

栈的优点是省心，缺点是容量有限、生命周期被函数边界框死；堆的优点是灵活，容量大、长度可到运行时确定、还能跨函数存活，缺点就一个字：累。谁申请、谁释放、什么时候释放，全部要自己记账。

new 与 delete：一次分配必须对应一次释放

要在堆上拿一块内存，用 new；要还回去，用 delete。朴素写法是：

  • int* p = new int;：分配一块 int 大小的内存，内容未初始化。
  • int* p = new int(42);：分配并直接把内容初始化为 42，返回值是这块内存的地址。
  • delete p;：释放 p 指向的那块内存，把使用权还给系统。

new 做对的事有两件：一是让长度可以到运行时才确定，二是给出一个可传递的地址，让这块内存在函数之间流转。代价是它把「什么时候还」这个责任一并交了出来。只 new 不 delete，那块内存就一直被占着，程序再也拿不回来，这就是内存泄漏。

一个合适的判断标准是：每个 new 都应在代码里找到一处对应的 delete，而且执行路径上恰好走到一次。做不到这一点，多半就要出问题。

new[] 与 delete[]：数组是另一本账

申请数组要写成 new int[n]，释放时必须用 delete[] arr，而不是 delete arr。这对符号看起来只差一对方括号，却是两条独立的规则。

  • int* arr = new int[5]{1, 2, 3, 4, 5};：分配 5 个 int 并逐个初始化。
  • delete[] arr;：告诉运行时「这是一整个数组，请把每个元素都按数组的方式回收」。

为什么不能混用？因为 new[] 申请时，运行时会额外记录数组长度（实现上常藏在首个元素之前），delete[] 才知道该回收多大一块、该调用多少次元素的析构函数。写成 delete arr 等于只回收了一个元素，其余长度信息被忽略——分配器的记账与释放时的记账对不上，后续再申请内存就可能踩到那块没被正确归还的区域，产生难以复现的内存错乱。

简记一句话：单个对象的 new 配 delete，数组的 new[] 配 delete[]，两者不可互换。

三类高频事故：泄漏、悬垂与重复释放

掌握了配对规则，剩下的错误基本集中在三种情形上，它们各自对应指针生命周期的不同阶段。

  • 内存泄漏：new 之后因为提前 return、抛异常或单纯忘记，迟迟没有 delete。它表现得最安静——程序照常跑，只是占用慢慢涨上去。
  • 悬垂指针：delete p 之后再通过 p 读写。此时 p 里存的地址仍指向那块已经归还的内存，但内容随时可能被别处覆盖，*p 取到什么完全无法预料，这类行为在标准里属于未定义行为。
  • 重复释放：同一块内存 delete 两次（或经两条指针路径各释放一次）。分配器会认为这块内存被归还了两次，内部结构被破坏，往往在后续某次 new 时才突然崩溃，离现场很远。

对付它们的共同习惯很朴素：指针一旦 delete，立刻把它置为 nullptr。delete nullptr 是安全的空操作，置空之后即使误判、误删也能被挡住，悬垂与重复释放这两类事故的概率会大幅下降；再把「谁拥有这块内存」写进代码结构里（谁申请谁负责释放），则能从源头减少泄漏。

越界访问：编译器看不见的边界

还有一类错误与 new/delete 无关，却同样致命。数组 new int[n] 之后，合法下标只有 0 到 n - 1，可 C++ 出于性能考虑不做运行时越界检查：arr[n] 或 arr[-1] 在语法上完全合法，编译器不拦，运行时也不报，只是悄悄写坏了相邻的内存——可能是别的变量，也可能是分配器的记账数据。

越界是不可移植、不可预测的：同一份代码在不同编译器、不同优化级别下表现可能完全不同，定位成本极高。预防手段是明确的：用常量或变量守住循环上界，把数组长度与访问边界放在一起维护；更稳妥的做法是改用 std::vector 这类自带长度、能用 at() 做边界检查的容器。

把释放交给析构函数

一路看下来，栈与堆的根本差别，其实就是释放这件事由谁负责：栈交给编译器，堆交给程序员。裸 new/delete 的根本痛点是「人可能忘」。既然如此，能不能让「释放」也变回自动的？答案是把资源托付给一个对象的生命周期：在构造函数里 new，在析构函数里 delete。这样不论函数是正常返回还是中途抛异常，只要对象离开作用域，析构函数就一定被调用，释放就一定会发生——这正是 RAII 的思路雏形，也是智能指针能把裸指针取而代之的基础。

「堆」指程序运行期间可动态申请与释放的内存区域，其生命周期手动管理；「内存泄漏」指已申请的内存在失去所有指针引用前未被释放，程序无法再回收；「悬垂指针」指指向已释放内存的指针，解引用它属于未定义行为；「RAII」即「资源获取即初始化」，把资源的取得放在构造、释放放在析构，借助对象作用域实现自动管理。

关键代码

C++
// ═══════════════════════════════════════════
// 1. 三种存储区：全局区、栈区与堆区
// ═══════════════════════════════════════════

#include <iostream>

int gCounter = 0;                          // 全局区：整个程序生命周期都存在

void stackScope() {
    int local = 10;                        // 栈区：进入函数时分配
    gCounter += local;                     // 传给全局变量，退出后仍保留
}                                          // local 在此自动销毁，无需手动释放

int main() {
    stackScope();
    std::cout << gCounter << std::endl;    // 输出：10
    int* heapValue = new int(20);          // 堆区：由 new 分配，生命周期自行管理
    std::cout << *heapValue << std::endl;  // 输出：20
    delete heapValue;                      // 必须手动释放，否则泄漏
    return 0;
}

// ═══════════════════════════════════════════
// 2. new 与 delete：一次分配对应一次释放
// ═══════════════════════════════════════════

int* makeCounter(int start) {
    int* p = new int(start);               // 分配后直接初始化，值为 start
    return p;                              // 所有权移交给调用方
}

int main() {
    int* p = makeCounter(7);
    std::cout << *p << std::endl;          // 输出：7
    *p = 8;                                // 通过指针修改堆上的值
    delete p;                              // 释放，与前面一次 new 配对
    p = nullptr;                           // 置空，避免悬垂指针
    return 0;
}

// ═══════════════════════════════════════════
// 3. new[] 与 delete[]：数组是另一本账
// ═══════════════════════════════════════════

int main() {
    int* arr = new int[5]{1, 2, 3, 4, 5};  // 动态数组，长度可在运行时决定
    int sum = 0;
    for (int i = 0; i < 5; ++i) {
        sum += arr[i];                     // 下标 0 到 4，越界不会被检查
    }
    std::cout << sum << std::endl;         // 输出：15
    delete[] arr;                          // 数组必须用 delete[]，与 new[] 配对
    arr = nullptr;
    return 0;
}

// ═══════════════════════════════════════════
// 4. 三类事故：泄漏、悬垂与重复释放
// ═══════════════════════════════════════════

int main() {
    int* leaked = new int(1);              // 若始终不 delete，就是内存泄漏
    std::cout << *leaked << std::endl;     // 输出：1
    delete leaked;                         // 补上释放，修正泄漏
    leaked = nullptr;

    int* dangling = new int(2);
    delete dangling;
    dangling = nullptr;                    // 释放后立即置空，堵住悬垂指针
    if (dangling != nullptr) {             // 使用前判空，防御性写法
        std::cout << *dangling << std::endl;
    }

    int* twice = new int(3);
    delete twice;                          // 只释放一次
    twice = nullptr;                       // 置空后再删也安全，避免重复释放
    return 0;
}

// ═══════════════════════════════════════════
// 5. RAII 雏形：把释放交给析构函数
// ═══════════════════════════════════════════

class IntBuffer {
public:
    explicit IntBuffer(int n) : data(new int[n]), size(n) {}   // 构造即取得资源
    ~IntBuffer() { delete[] data; }                            // 析构即释放资源
    int& operator[](int i) { return data[i]; }                 // 边界由调用方保证
private:
    int* data;
    int size;
};

int main() {
    IntBuffer buf(3);
    buf[0] = 100;
    std::cout << buf[0] << std::endl;      // 输出：100
    return 0;                              // 离开作用域，析构自动 delete[]
}
