智能指针：unique_ptr、shared_ptr、weak_ptr

掌握 C++11 智能指针的用法，理解独占所有权、共享所有权和弱引用的语义及适用场景。

开场问题：你写了个函数，new 出一个对象，中间几条分支各有各的提前 return。上线后，进程的内存占用随着这个函数的调用次数一路往上爬——你回头数了数，每一处 new 明明都配了 delete，那内存到底是怎么漏出去的？

堆对象创建与释放

你要在运行时按需创建对象——大小、数量、时机都要等程序跑起来才知道，所以只能在堆上 new，并且得在想清楚「用完了」时把这块内存还回去。最朴素的老办法就是手动 new / delete 配对。它能跑，但代价全压在人身上：

  • 释放点分散：每一处提前 return、每一次抛出异常、每一个中途分支，都可能跳过那行 delete，函数正常跑没问题，一旦走上别的路径就漏了。
  • 释放时机靠记忆：哪儿申请、哪儿释放，得靠人记住并保证一定走到，代码一长就没人敢打包票。
  • 容易重复释放：两个对象各自持有一份浅拷贝的指针，析构时都去 delete 同一块内存，就是 double free。
  • 所有权不明：一个函数返回裸指针，调用方根本看不出「这块内存该我 delete，还是别人管」。

所以要问的是：能不能让「释放」这件事不再依赖你手写的那几行，而是自动地、在所有退出路径上都发生？

手动配对申请释放

最直接的做法是继续 new / delete 配对，或者用 try / catch 把 delete 保证执行一遍。

这个方案做对了一件事：它把「申请」和「释放」都摊在了明面上，你完全掌控时机，看得见每一次分配和回收。问题只在于——它把「保证每一步都成对」这个责任，整个交还给了人，而人恰恰是最不可靠的一环。

提前返回释放漏洞

  • 任意一条提前 return 或者中途抛出的异常，都能让那行 delete 彻底走不到。
  • 默认的拷贝是浅拷贝，两个对象析构时对同一块内存各 delete 一次，直接双重释放崩溃。
  • 如果拿同一个裸指针去构造两个 shared_ptr，会生成两个各自独立的控制块，对象会被释放两次。
  • 函数交了裸指针出来，所有权归属完全靠文档和口头约定，调用方一不小心就漏删或者错删。

RAII与所有权划分

第一层要补的不是「更小心地写 delete」，而是换一个思路：让某个对象来替你看管那块堆内存，靠它自己的析构自动释放。这就是 RAII，而 unique_ptr 是它在动态内存上的最基本形态。你把 unique_ptr 当成一个栈对象来持有，它内部存着真正的堆指针；无论函数是正常返回、提前 return，还是抛异常退出，栈对象都会被析构，析构函数里替你 delete。释放时机从此挂在对象生命周期上，不再挂在某一行代码上。

unique_ptr 体现的是独占所有权：同一时刻只能有一个 unique_ptr 拥有那个对象，所以它不能拷贝、只能移动。把所有权交出去要显式写 std::move，转移之后原来那个 unique_ptr 变成 nullptr，再去用它就是访问空指针。它的体积和裸指针一样，没有任何额外开销——所以它是默认首选。用 std::make_unique<T>(args)（C++14）创建最省事。

第二层要补的是「确实有多个地方要共享同一个对象」。这就轮到 shared_ptr，它体现共享所有权：多个 shared_ptr 可以指向同一个对象，靠一份共享的控制块里的引用计数来记「现在有几个持有者」。每拷贝一个计数加一，每销毁一个计数减一，减到零时才真正释放对象。用 std::make_shared<T>(args) 创建（C++11），它会把对象和控制块一次分配出来，比其他写法更高效。

但共享所有权会引出一个经典死角——循环引用。假如对象 A 里有个 shared_ptr 指向 B，B 里又有个 shared_ptr 指回 A，那么它俩的引用计数永远至少是 1，谁都降不到零，最后谁都释放不掉，整块内存静静地泄漏。补这个洞的是 weak_ptr：它是 shared_ptr 的弱引用，指向同一个对象却不增加引用计数，因此不会阻止对象被释放。要用的时候通过 lock() 把它「提升」成一个临时的 shared_ptr——对象还活着就拿到一个非空的 shared_ptr，已经销毁了就拿到空的。于是双向引用、父子互相引用这类结构，就把其中一侧改成 weak_ptr，环就断开了。

补充几条日常写法上的安全边界。创建时始终用 make_unique / make_shared，或从已有的智能指针构造，绝不用同一个裸指针去构造多个 shared_ptr。unique_ptr 作为函数返回值时不需要显式 std::move（编译器会处理），作为参数要转移所有权时才写 std::move。shared_ptr 的引用计数增减是原子的、线程安全的，但要注意——它只保护计数本身，被指向的对象并不是线程安全的，多线程读写那个对象仍然得你自己加同步。

两个高频陷阱：其一，unique_ptr 允许带自定义删除器（比如关闭文件句柄、断开网络连接），而删除器是类型的一部分（模板的第二个参数），所以 unique_ptr<T, D1> 和 unique_ptr<T, D2> 是两个不同的类型，不能随意互相赋值。其二，在类内部想把 this 变成 shared_ptr 时，千万不要用 this 裸指针去构造（会凭空多出一个独立控制块，最终双重释放），正确做法是让这个类继承 std::enable_shared_from_this<T>，再调用 shared_from_this()。

顺着这套逻辑，现代 C++ 的内存策略可以一句话概括：优先用栈对象（本来就不需要手动释放）；确实需要堆对象时用 unique_ptr；确实需要共享所有权时才升级到 shared_ptr；共享里出现了环，就用 weak_ptr 打断。而原始指针退回它该待的位置——只做「不拥有、只观察」的引用，几乎不再用它来管理资源。

引用计数与指针置空

所有权归属判定

智能指针把「释放内存」从你手写的某一行，搬到了对象的生命周期上，于是所有退出路径都被自动覆盖。默认用栈对象；需要堆对象就用 unique_ptr；确实要共享所有权才用 shared_ptr；共享里一旦成环，就用 weak_ptr 断环。原始指针从此只负责「看」，不负责「管」。

「引用计数」是 shared_ptr 用来管理共享所有权的一门记账方式：一份共享的控制块记录着「当前有多少个 shared_ptr 指向这个对象」，每拷贝一个就加一、每销毁一个就减一，减到零时自动析构并释放对象。边界：计数的增减是原子的、线程安全，但被指向的对象本身不是线程安全的，并发读写仍需自行同步；更要当心循环引用——两个对象互相持有 shared_ptr 会让计数永远降不到零、内存无法回收，此时应把其中一侧改为 weak_ptr（它不计入引用计数，需要时才用 lock() 提升为 shared_ptr）。

关键代码

C++
#include <iostream>
#include <memory>

int main() {
    // unique_ptr：独占所有权
    std::unique_ptr<int> up = std::make_unique<int>(42);

    // shared_ptr：共享所有权
    std::shared_ptr<int> sp1 = std::make_shared<int>(100);
    {
        std::shared_ptr<int> sp2 = sp1;  // 引用计数 +1
    }  // sp2 析构，引用计数 -1

    // weak_ptr：弱引用
    std::weak_ptr<int> wp = sp1;  // 不增加引用计数
    if (auto sp3 = wp.lock()) {  // 提升为 shared_ptr
        std::cout << *sp3 << std::endl;
    }

    return 0;
}
