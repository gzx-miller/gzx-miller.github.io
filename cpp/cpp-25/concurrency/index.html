并发编程：std::thread、mutex、lock 与 async

理解 C++11 引入的并发支持，掌握线程创建、互斥锁、条件变量和异步任务的基本用法。

开场问题：你开了十个线程，每个线程只做一件事——把同一个计数器加一。十次加法，结果当然是十。可反复运行，结果在 7 到 10 之间跳，偶尔还会是 8——同一个程序、同一份输入，为什么每次的答案都不一样？

非原子自增成因

多线程的目的是让几件事真的同时进行。但一旦两个线程访问同一块内存，事情就变了：++counter 在你眼里是一条语句，在机器眼里却是三步——读出来、加一、写回去。两个线程各自读到 7，各自算出 8，各自写回 8，于是一次加法凭空消失了。

在 C++11 之前，想用线程只能直接用平台 API，三笔成本都压在写代码的人身上：

  • 平台各异。类 Unix 上是 pthread，Windows 上是另一套接口，同一份逻辑要写两遍、分平台编译。
  • 锁没有 RAII。手动 lock / unlock，中间一旦抛出异常或提前返回，锁就永远不解开，其他线程全部陪葬。
  • 编译器和语言对线程一无所知。它不认为这段代码会被并发执行，也不会帮你发现共享数据的访问冲突。
  • 线程自身的生死要人管。一个线程该等它结束还是让它自己跑，忘了处理就是崩溃。

所以问题是：能不能让「开一个线程」「保护一块共享数据」「等某个条件成立」都有类型安全、能自动清理的语言级原语？

线程对象生命周期

最朴素的做法：std::thread t(func, args...); 启动一个线程，然后在主线程里 t.join(); 等它跑完。

这个方案做对了一件关键的事：它把「线程」变成了一个普通的对象。既然是个对象，就能用对象的那套办法管它——这条思路和前面几课的 RAII、移动语义是同一个方向。

数据竞争与线程收尾

  • 两个线程同时执行 ++counter，读到同一个旧值再各自写回，一次自增被覆盖掉，十次加法只加出了 7 或 8。
  • 一个 std::thread 对象如果既没 join 也没 detach 就被销毁，析构函数会直接调用 std::terminate，整个进程当场结束。
  • 手动 mtx.lock() / mtx.unlock() 时，中间抛出异常就永远不解锁，其它等这把锁的线程会无限期阻塞——这是最难排查的一类 bug。
  • 一个线程要等「队列里来数据了」，用 while (queue.empty()) {} 空转轮询，CPU 被它一个人跑满，白白耗电。
  • 想让后台任务算完并把结果拿回来，std::thread 根本没有「取结果」这个接口。

互斥锁与条件变量

不推翻「用对象管线程」，而是承认线程最大的危险在于共享数据的访问顺序，然后一个一个问题去补。

第一件要补的是互斥。用 std::mutex 保护共享数据：访问前加锁，访问后解锁。但手写 lock / unlock 会重蹈 RAII 课里的覆辙，所以应该用 std::lock_guard——它在构造时加锁、析构时解锁，即使临界区里抛异常也保证解锁。std::unique_lock 更灵活：可以手动 lock / unlock，因此能用于条件变量和下面要说的 std::lock。

第二件要补的是线程对象的收尾。每个 std::thread 在销毁前必须在 join()（等它跑完）和 detach()（放它自己跑）之间二选一，而几乎所有场景都应该选 join：你需要知道它跑完了、需要它别在你还用着共享数据时就消失。忘了处理就会 std::terminate。

第三件要补的是同时锁多把锁时的死锁风险。线程 A 先锁 m1 再锁 m2，线程 B 先锁 m2 再锁 m1，两边各持一把、都在等对方放手，谁也走不了。正确做法是用 std::lock(m1, m2) 一次性把多把互斥量锁住，它内部使用能避免死锁的算法；已经锁住之后再交给 lock_guard 接管，用 std::adopt_lock 告诉它「锁已经上过了，你只负责到时候解锁」。

第四件是让线程能等待，而不是空转。这就是条件变量 std::condition_variable 的用途：一个线程在条件不满足时 wait 挂起，另一个线程改变状态后 notify_one() 或 notify_all() 唤醒它。等待的表达方式是关键——必须放在循环里反复检查条件：

  1. 先判断条件是否已经成立，成立就直接往下做，不必等待。
  2. 不成立才调用 wait，它会原子地释放锁并挂起当前线程。
  3. 被唤醒后重新检查条件，仍不满足就继续等——所以外面要套 while，或直接使用 cv.wait(lock, pred) 这个自带循环的重载。
  4. 另一个线程修改完共享状态，再调用 notify_one / notify_all 唤醒等待者。

为什么非要循环？因为存在虚假唤醒：即使没有任何人调用 notify，等待的线程也可能被系统莫名其妙地唤醒。如果只写一次 if (queue.empty()) wait(lock);，被虚假唤醒后它会在队列还是空的时候继续往下跑，直接崩溃。

第五件是带返回值的异步任务。开线程干活常常是为了「算一个东西并拿回来」，而这正是 std::thread 做不到的。std::async 补上了这一块：auto fut = std::async(std::launch::async, func, args...); 立刻启动（或按调度启动）任务并返回一个 std::future，调用 fut.get() 时阻塞等待结果。它还顺手把上一课的异常传播接了过来——如果任务内部抛了异常，这个异常会被存进 future，并在你 get() 的那一刻重新抛出，跨线程也能正常报错。

最后两个边界要记清楚。std::future 的 get() 只能调用一次，调用之后这个 future 就失效了；如果确实需要多个地方读到同一个结果，改用 std::shared_future。另外，C++20 又补了一批并发原语——信号量（std::counting_semaphore、std::binary_semaphore）、闩（std::latch）、屏障（std::barrier），它们解决的是「多个线程互相等对方到某个点」这类更复杂的问题。

三条最容易踩的线：没有任何同步就并发读写同一块内存，是数据竞争，在标准里属于未定义行为；别把耗时操作放进临界区，锁内的每一毫秒都在让其他线程排队；std::lock_guard 不能在作用域中途手动 unlock，需要这种灵活性就换 std::unique_lock。

锁守卫保护范围

共享数据同步

并发的难点从来不是「怎么开线程」，而是多个线程碰到同一块内存时，谁先谁后由不得你。C++11 的答案是把这件事交给几个各有分工的 RAII 原语：用 std::mutex 配 lock_guard 圈出临界区，用 std::lock 一次性锁多把锁避免死锁，用条件变量带循环地等条件，用 std::async 拿回带异常的返回值。剩下的规矩就三条：有共享就有同步、别忘了 join、别在锁里干重活。

「数据竞争」指两个及以上线程同时访问同一内存位置，其中至少有一个是写操作，且它们之间没有任何同步关系。在 C++ 标准里这是未定义行为——不是「结果可能不对」这么轻，而是编译器可以做任何假设、优化出任何结果。边界：只读的并发访问不算数据竞争；用互斥量或原子操作建立起 happens-before 关系才能消除它。要特别注意的是，加了锁并不等于就没竞争，必须保证该内存的所有访问路径都被同一把锁覆盖。

关键代码

C++
#include <iostream>
#include <thread>
#include <mutex>
#include <vector>
#include <future>

int main() {
    // 创建线程
    std::thread t1([]() {
        std::cout << "线程 1 正在执行" << std::endl;
    });
    t1.join();

    // 使用 async 异步任务
    std::future<int> result = std::async([]() {
        return 42;
    });
    std::cout << "结果：" << result.get() << std::endl;

    return 0;
}
