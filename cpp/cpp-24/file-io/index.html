文件 I/O：ifstream、ofstream 与字符串流

掌握 C++ 文件输入输出流的使用，以及字符串流（stringstream）在文本处理和类型转换中的应用。

开场问题：你写了个往日志文件追加内容的程序，每轮跑完都检查「写成功了吗」，全都成功。可跑了几轮之后打开文件一看，里面只剩最后一轮的记录，前面几轮凭空消失了——明明每一轮都写成功了，是谁把文件清空的？

外部设备不可控性

从文件读数据、往文件写数据，本质上是在跟一个外部设备打交道：它可能不存在、可能没权限、可能读到一半就到头了。这些情况都必须被感知和处理，否则你拿到的是「看起来正常、其实早就失败」的数据。

在流抽象之前，用 C 的 fopen / fread / fclose 这一套也能干活，但代价同样落在人身上：

  • 每个文件句柄都要显式 fclose，中途 return 或抛异常就漏掉了，句柄一路泄漏到耗尽。
  • 打开模式靠拼字符串 flag（"w"、"a"、"r+"），拼错不会立刻报错，要等运行期行为不对才发现。
  • 类型安全为零：fprintf(fp, "%d", x) 里格式串和实参对不上，编译器完全不拦，运行起来才读出垃圾。
  • 解析文本全靠格式串，读一个整数要先 fscanf 再判返回值，格式稍有偏差整段逻辑就崩。

所以问题是：能不能让文件读写拥有和内存操作一样的类型安全，并且让文件的打开与关闭自动跟着对象的生死走？

文件流读写统一

最省事的做法：用 std::ifstream 打开文件读、std::ofstream 打开文件写，读取用 >>，写入用 <<，用完就让对象自然离开作用域。

这个方案做对了一件很漂亮的事：它让文件读写的语法和操作屏幕完全一样。<< 能写 std::cout，也能写文件；>> 能从 std::cin 读，也能从文件读。因为屏幕、键盘、文件在背后都是同一个抽象——流。类型安全和格式化也随这套抽象一起带了过来，不用再和格式串对赌。

截断模式清空文件

  • 默认的 std::ofstream 用的是 trunc（截断）模式：每次打开都会把原文件清空。开场那个「只剩最后一轮」就是它干的——你想要的是追加，它给你的是覆盖。
  • 忘了检查是否真的打开了：文件不存在时打开失败，后面的 << 全部静默丢弃，程序不报错、不崩溃，你写到一半才发现一个字节都没落盘。
  • >> 读字符串时遇到空白就停。"Hello, C++!" 读进来只剩 Hello,，后半截还留在流里，等着污染下一次读取。
  • 格式化读取失败时，>> 不抛异常，只是把流置为失败状态，目标变量保持原值不变——你以为读到了新数据，其实是一份脏值。
  • 「读到文件尾」和「真的读失败」是两件不同的事，想分清楚就得去看流的状态，光看变量看不出来。

打开模式与流状态

不推翻「用流读写文件」,而是把这套抽象的各个角落补齐。第一件要补的是打开模式，因为开场那个 bug 就出在这：std::ios::in 读、std::ios::out 写（默认带截断）、std::ios::app 追加、std::ios::ate 打开后定位到末尾、std::ios::trunc 截断、std::ios::binary 二进制。写日志要在后面接着写，就必须显式用 app。

第二件是流状态。每个流对象内部维护着一组状态标志：good() 一切正常、eof() 到达文件尾、fail() 格式化操作失败（比如期望数字却读到字母）、bad() 严重错误（比如磁盘故障）。流对象还能隐式转换成 bool，所以判断成败可以直接写 if (fs)。这一步的意义是：失败不再沉默，你有了一个统一的、随时可查的失败信号。

第三件是读取方式要按数据形状选。>> 会跳过前导空白、读到下一个空白为止，适合读一个个「词」；要读一整行（可能含空格）就用 std::getline(fs, line)。二者不能混着乱用来跳行，混用时要留意残留的换行符。逐行读的惯用写法是 while (std::getline(inFile, line))——它同时完成了「读一行」和「判断是否还有输入」。

第四件是生命周期。文件流是 RAII 类型（上一课刚讲过）：打开在构造时，关闭在析构时，所以正常路径上根本不用写 close()。当然你也可以显式调用 close() 提前关闭并检查关闭是否成功，但默认交给析构就够了。

第五件是二进制与非文本文件。读写图片、音频这类数据要用 binary 模式，配合成员函数 read / write，并把数据指针用 reinterpret_cast<const char*> 转成字节视图。

到这里文件读写已经很顺了，但还有一类需求它不覆盖：我其实不需要文件，只想在内存里拼字符串或解析字符串。为此标准库把同一套流抽象搬进了内存，这就是字符串流：

  1. std::istringstream 从字符串读，用来解析文本，替代 sscanf：把字符串倒进去，然后像用 std::cin 一样逐个提取。std::istringstream iss(data); int num; double pi; std::string word; iss >> num >> pi >> word; 就把 "42 3.14 Hello" 拆成了三份。
  2. std::ostringstream 向字符串写，用来格式化，替代 sprintf：<< 进去的东西最后用 .str() 取出来。它比 std::to_string 更灵活，因为能控制格式、能拼接多种类型。
  3. std::stringstream 同时支持读写，适合需要来回改的场景。

最后两个边界值得记住。其一，文件流对象不能拷贝（拷贝构造和拷贝赋值都被删除了），但可以移动——用 std::move 把所有权转移给另一个流对象，这是第 21 课那套语义在标准库里的又一次落地。其二，C++17 起文件流的 open 可以接受 std::filesystem::path（来自 <filesystem>），对 Unicode 文件名的支持更好。

三类读写接口对照

流抽象与类型安全

文件 I/O 的核心不是那几个类，而是流这个统一抽象：屏幕、键盘、文件、内存字符串，统统是流，所以同一套 << / >> 能通用的地方就通用，类型安全也就一并带上了。要用好它，只需盯住三件事——打开模式选对（追加别用成覆盖）、流状态随时查、生命周期交给 RAII。

「流状态位」指每个流对象内部维护的一组失败标志：goodbit 一切正常、eofbit 到达文件尾、failbit 格式化操作失败（如期望数字却读到字母）、badbit 严重错误（如磁盘故障）。它可以用 good() / eof() / fail() / bad() 查询，流对象也能隐式转成 bool。边界：>> 失败时不抛异常，只置位且目标变量保持原值，容易读到脏数据；而 failbit 一旦置位，在显式 clear() 之前，该流上的后续操作都会直接失败。

关键代码

C++
#include <iostream>
#include <fstream>
#include <sstream>

int main() {
    // 写入文件
    std::ofstream outFile("example.txt");
    outFile << "Hello, C++!" << std::endl;
    outFile.close();

    // 读取文件
    std::ifstream inFile("example.txt");
    std::string line;
    while (std::getline(inFile, line)) {
        std::cout << "读取: " << line << std::endl;
    }

    // 字符串流
    std::string data = "42 3.14 Hello";
    std::istringstream iss(data);
    int num;
    double pi;
    std::string word;
    iss >> num >> pi >> word;
    std::cout << num << ", " << pi << ", " << word << std::endl;

    return 0;
}
