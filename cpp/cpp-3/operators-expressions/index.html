运算符、表达式与类型提升

理解 C++ 各类运算符的优先级、结合律、求值顺序，以及整数提升和算术转换规则。

开场问题：你想判断变量 a 里某些二进制位是否全为 0，写下 if (a & mask == 0)，结果不管 a、mask 取什么，这个分支要么永远不进、要么永远进——代码看着像「先按位与、再比较」，编译器却按另一套理解执行。

运算符优先级规则

一行表达式里可以塞进很多运算符：a + b * c、p && q || r、x << 1 & 3。人读的时候靠直觉——从左到右、按数学习惯来；但机器必须有一套毫不含糊的规则，否则同一行代码在不同编译器下能算出不同结果。

这套规则的第一层是优先级：谁来先结合。第二层是结合律：优先级相同时从左还是从右。光这两层还不够，因为 C++ 还有两件事会让结果进一步偏离直觉：计算时数值用多少位（类型），以及子表达式谁先被真正求值（求值顺序）。你在脑子里默认「从左到右、位宽不变、谁先写谁先算」，可语言的默认并不是这样。

旧办法（凭直觉写表达式、不加括号）要人承担的成本很具体：你得把整张优先级表背下来；就算背下来，位运算和相等运算谁高谁低也常常记反；即便优先级对上了，整数提升和求值顺序仍可能让同一个式子算出你没想到的值。

所以问题落到：一行复杂表达式里同时出现算术、比较、位、逻辑、赋值，到底按什么顺序算成什么类型？哪些写法干脆是「没定义结果」的？

默认读法失效

最省事的做法：相信从左到右、相信数学直觉来读。a & mask == 0 读起来就像 (a & mask) == 0；1/2 读起来就该是 0.5。

这个方案确实做对了一件事：对于只用算术和关系、并且都加了括号的简单表达式，从左到右读是没问题的。大部分日常代码也确实落在这个范围内，所以「凭直觉」在小规模时够用。

问题在于，一旦把位运算符、逻辑运算符和比较运算符混在一行，「直觉」会和真正的规则悄悄错开，而且错得毫无提示。

位运算优先级

  • a & mask == 0 实际等价于 a & (mask == 0)——因为 == 的优先级高于 &。mask == 0 先算出一个 0 或 1，再和 a 按位与，判断的语义就彻底变了味。
  • char c1 = 100, c2 = 200; char sum = c1 + c2;，sum 得不到 300——因为 c1 + c2 先被提升成 int 得到 300，再赋回 char 时才截断溢出，报错的位置和你以为的不一样。
  • i = i++; 的结果是未定义：同一个表达式里既读 i 又改 i，编译器怎么排都合法，不同编译器给出不同的值。
  • int x = INT_MAX + 1; 是未定义行为（有符号溢出），并不是「温和地回绕成负数」。
  • 1 << 32 对一个 32 位的 int 是未定义，因为位移位数超过了类型的位宽。

显式括号分组

不推翻「表达式能一行写完」，而是把这几条规则一层层补上，让每一层各自管住一类意外。先补的第一层是分组，因为它决定了后面两层在讨论什么。

用括号把分组意图钉死。优先级从高到低大致是：::、成员与调用 () [] -> . 与后缀自增、前缀运算符、* / %、+ -、<< >>、关系 < <= > >=、相等 == !=、&、^、|、&&、||、?:、赋值、逗号最低。但你不需要背它——只要记住一条操作性的规则：只要位运算、逻辑运算、比较混在一行，就一律加括号。把 a & mask == 0 写成 (a & mask) == 0，括号是给你自己看的，不是给编译器看的。

补完分组，接着要理解位宽会被悄悄改写，否则你加对了括号也算不对值。C++ 规定：小整数类型（bool、char、short）在参与表达式时先做整数提升，升成 int（只要 int 装得下原类型的全部取值），所以 char + char 的实际类型是 int。两个操作数类型不同时，再按算术转换统一到更高的那个类型，大致顺序是 int → long → long long → float → double → long double。这一层正好解释了 c1 + c2 为什么不会当场溢出——溢出发生在赋回 char 的那一刻；也解释了 1/2 为什么是 0 而不是 0.5（两个 int 相除，结果还是 int）。

最后一层，也是唯一无法靠加括号解决的：求值顺序。C++17 起，只有少数运算符明确了左操作数先于右操作数求值——赋值、复合赋值、&&、||、?:、逗号。其余多数运算符的子表达式谁先算，标准没有规定。所以「别在同一表达式里既改一个变量又读它」不是风格建议，而是避免未定义行为的硬要求：把 i = i++; 拆成单独一行 i++;。

把这些零碎规则串起来，还有几个在写表达式时天天用到的行为值得一起记住。&& 和 || 是短路的——左操作数已经能定结果，右边就不评估，所以 if (p != nullptr && p->ok()) 才安全，判空之后才解引用。前缀 ++i 返回自增后的值，后缀 i++ 返回自增前的旧值，对迭代器来说后缀还要多复制一份，性能上有差别。逗号运算符顺序求值，整个表达式的值和类型取最右边那一项，正好适合放在 for 里做多重初始化或更新。

位移的两个硬约束：<< 和 >> 的操作数必须是整数类型，且右操作数必须非负、并且小于左操作数的位宽。违反这两条（例如对 32 位 int 写 1 << 32）都是未定义行为，不是「结果为零」。

四类陷阱对照

表达式求值要素

一行表达式的结果由三件事共同决定：优先级决定怎么分组、整数提升与算术转换决定用多少位算、求值顺序决定谁先真的执行。别背优先级，混用场景一律加括号；别去依赖没被规定的求值顺序，同一个变量不要在一行里又读又改。

「未定义行为」（undefined behavior，UB）指标准没有规定结果、编译器可以做任何事的代码，例如 i = i++ 或有符号整数溢出。它不等于「结果随机」也不等于「回绕」——优化器甚至可以据此删掉整段分支。与之相近的是「未指定行为」，如多数运算符的求值顺序，结果由具体实现决定但不算非法。记住：能不写就不写，用括号和拆行消灭歧义。
