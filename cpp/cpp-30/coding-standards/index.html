C++ 编码规范与工程最佳实践

掌握现代 C++ 编码规范、常见陷阱规避，以及构建、测试、持续集成等工程实践要点。

开场问题：一段代码你反复读过，new 出来的指针在函数结尾老老实实 delete 了，挑不出毛病。可压测时进程的内存却一直在涨——问题不在你看到的那条 delete，而在它上面几行你没太在意的地方。

释放语句位置

那段代码大概是这个形状：先 int* p = new int[100];，紧接着做几步可能失败的检查，最后 delete[] p;。看起来对称，其实中间只要有一条提前返回或抛出异常的路径，后面的 delete 就走不到，这块内存就再也回不来了。这正是「编码规范」真正要对付的东西：它不是审美偏好，而是人靠自觉永远守不住的一类错误。

把这类错误拆开看，会发现它们有共同点——都靠「记得做某件事」来保证正确：记得 delete、记得别写窄化转换、记得给宏的参数加括号、记得别漏掉某个分支。可人的记忆在分支一多、路径一长时就不可靠。所以要问的其实是：能不能把「必须记得做的事」，改成「机制替你保证、工具替你检查」？

代码评审与人工复核

最朴素的补救：写代码时更小心——每个 new 都配上 delete，每条提前返回之前都记得释放，然后靠 code review 互相盯。

这个方案做对了一件事：它承认了「资源必须被释放」这个约束。有了这个意识，简单函数里经常真的能写对——在没有异常、没有多条返回路径的情况下，对称的 new/delete 也确实工作正常。

异常展开遗漏

  • 异常一抛，delete 就没机会执行。中间那步检查抛出异常时，栈会向上展开，函数末尾的 delete[] 根本不会运行——你读代码时看到的「释放」，在异常路径上并不存在。
  • 多条返回路径各有各的漏洞。函数里有三个 if 提前 return，你就得在四处各写一次释放；漏掉任何一处，都是只在特定输入下才暴露的泄漏。
  • 靠 review 抓不住全部。这类错误在正常路径上完全不显形，评审时看到的是一段干净、对称的代码，问题要等某条边界输入或异常才被触发。
  • 「记得」这种事还会在别处重复。窄化转换、宏的副作用、忘记初始化的变量，全都是同一类「忘了就出事、还特别难查」的坑——对着清单逐条背，成本高且不可靠。

类型与工具链接管

不推翻「资源要释放」，而是换一个思路：不再让人的记忆负责，改让类型系统和工具链负责。一层层补。

  1. 先把资源交给对象管（RAII）。这是 C++ Core Guidelines 里排在最前面的建议 R.1：把资源的获取与释放绑定在对象的构造与析构上，函数无论从哪条路径退出——正常返回还是抛异常——栈上对象的析构函数都会执行。原先那段代码只要把 new 的结果直接存进智能指针（例如成员里放一个 std::unique_ptr<int[]>），就再也不用写 delete 了。
  2. 再把「所有权」写进类型。换成 std::unique_ptr/std::shared_ptr 之后，「谁拥有这块资源」从注释里的约定变成了类型上的一部分：unique_ptr 独占、shared_ptr 引用计数共享，转移所有权要显式 std::move。所有权一目了然，就不用再靠「我记得这里该由谁释放」。
  3. 把意图写进签名（const 正确）。承诺「我不改这个参数」就写 const 引用，承诺「这个成员函数不改对象」就在函数后面加 const。const 不只是自文档，它还是编译期约束：真有一次误改，编译会直接拦下，而不是留到运行时。传参也遵循 F.15——按 const 引用传入、按值返回，避免无谓拷贝。
  4. 能不用宏就不用宏。宏是文本替换，没有类型、没有作用域，参数还可能被意外求值多次。多数需求都有更好的替代：常量用 constexpr、限定取值用 enum class、需要泛化用 template。
  5. 把「靠人检查」换成「靠工具检查」。静态分析工具 clang-tidy（基于 LLVM/Clang，可查现代规范、性能与正确性）、Cppcheck 能在不运行程序时就指出问题；运行期则用 sanitizer 按住：AddressSanitizer 抓内存错误、UndefinedBehaviorSanitizer 抓未定义行为、ThreadSanitizer 抓数据竞争。这一步的关键转变是——前面那些规范不再靠你记住，而是由工具强制发现。
  6. 最后把这一切固化进工程流程。用 CMake 统一构建、用 Google Test 或 Catch2 写测试、用 vcpkg/Conan 管依赖，再让 CI（如 GitHub Actions）在每次提交时自动跑构建、测试、静态分析与 sanitizer。规范只有进了流程，才不会随某个人的疏忽而失效。

走到这里就能看清「编码规范」的本质了：那些条款（RAII、const 正确、避免宏）不是要你去背诵的规矩，而是把约束从「人的自律」搬进「类型系统加工具加流程」的手段。C++ 提供的正是这种能力，它管这叫零开销抽象：用模板、内联这些东西把高层写法编译成和手写底层代码一样快的机器码，而且你不需要的抽象不会带来任何运行期开销。

别把这些当成「老规矩」：C++ 的抽象还在持续变强，C++11、17、20 各自是一次大更新（结构化绑定、if constexpr、折叠表达式、文件系统库、模块、概念、协程、范围库等），C++14/23 是较小的补充，跟着新标准更新工具链本身就能消掉一批旧坑。另外跨平台时还要单独留心：字节序用 <bit> 里的 std::endian 判断，字符编码用 u8"" 字面量、std::u8string 与 std::filesystem::path 处理，尽量使用标准特性，只对确有的编译器差异用预定义宏兜底。

好坏写法对照

内存责任转移

那段压测下持续上涨的内存，根子不是某个 delete 写错了，而是「释放」这件事交给了人的记忆去保证。C++ 的办法是把约束前移：用 RAII 与智能指针让释放随对象析构自动发生，用 const 让误改在编译期被拦下，用 constexpr/enum class/模板替掉有副作用的宏，最后用 clang-tidy、sanitizer 和 CI 把这些规则变成每次提交都自动执行的检查。规范的价值不在于「写得好看」，而在于让正确性不再依赖你记不记得。

「零开销抽象」C++ 的核心设计原则之一，指面向抽象写出的代码不该比人手写的底层代码慢，并且没用到的特性不产生任何运行期开销（只可能影响编译期）。模板、内联、constexpr 都是实现它的工具。边界要分清：它承诺的是「不额外变慢」，不是「一定更快」；而且这种优化依赖编译器真的把抽象看穿（内联、常量折叠等），一旦抽象边界挡住了优化，收益就不一定兑现。

关键代码

C++
#include <iostream>
#include <memory>
#include <vector>

// 好的做法：使用 RAII 和智能指针
class Resource {
    std::unique_ptr<int[]> data;
public:
    Resource() : data(std::make_unique<int[]>(100)) {}
    void use() { data[0] = 42; }
};

// 不好的做法：裸指针
void badPractice() {
    int* p = new int[100];
    // 如果这里抛异常，内存泄漏
    delete[] p;
}

int main() {
    Resource r;  // 自动管理内存
    r.use();
    
    // 使用 const 正确
    const std::vector<int> vec = {1, 2, 3};
    // vec.push_back(4);  // 编译错误：vec 是 const
    
    return 0;
}
