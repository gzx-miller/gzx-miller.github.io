编译期计算：constexpr、consteval、constinit

理解 C++ 编译期计算机制，掌握 constexpr、consteval、constinit 的用法与限制，将计算从运行期移到编译期。

开场问题：你写了一个递归计算阶乘的函数，然后拿它的结果当数组长度：int arr[factorial(10)];。编译器一口答应，程序运行时你也查不出任何「计算」的痕迹——这个递归到底在哪跑过？

编译期常量位置

有些值必须在程序跑起来之前就定下来：数组的长度、模板的非类型参数、编译期就想建好的查找表。这些位置只接受「常量表达式」，运行期算出来的结果再对也填不进去。

可普通函数给不了这个保证。编译器看一个普通函数，只知道「调用它会发生点什么」，无法确定它有没有副作用、能不能被提前算出来，于是只能把调用老实留到运行期。这样一来，你想在编译期算的东西全落空，还多背了三笔成本：

  • 性能落在运行期。本该编译期算完的常量，每次启动都要重新算一遍。
  • 常量位置用不了。想拿它当数组长度或模板参数，编译直接报错。
  • 没有「算错就编译不过」的把关。#define 宏能当常量用，但它没有类型、没有作用域，写错时编译器也无从检查。

所以问题是：能不能让编译器明确知道「这个函数的结果可以在编译期算出来」，从而放心地提前求值？

常量表达式标记

最朴素的答案：给函数和变量加 constexpr。函数写成 constexpr int factorial(int n)，变量写成 constexpr int N = 1024;，就等于向编译器声明「如果参数都是编译期常量，你可以在编译期把它算完」。

这个方案做对了一件事：它给了函数一张「可以编译期求值」的资格证。有了这张证，factorial(10) 就能填进需要常量表达式的位置，编译期直接把结果烧进去；constexpr 变量同时也天然是 const，数值不可改。

运行期值退化

  • constexpr 只是「可以」，不是「必须」：把运行期读到的值传进去，同一个函数就悄悄退回运行期调用——你以为算好了，其实没有。
  • C++11 的 constexpr 函数体限制很死，基本上只能是一条 return，想用循环就得改写成递归，写起来别扭。
  • 反过来，constexpr int x = f(input); 里若 input 是个运行期变量，编译器会直接报「不是常量表达式」，逼你改写法。
  • 想强制「这个函数只能在编译期跑」，constexpr 做不到——它拦不住运行期调用。

语义收紧与放宽

不推翻 constexpr，而是把它「可以」的语义按需求往两头收紧，再把不该塞进 constexpr 的场景单独分出去。

  1. 先放宽函数体。C++14 起 constexpr 函数可以声明局部变量、写循环、用条件和 switch，几乎和普通函数一样，factorial 终于能用循环写。但底线仍在：函数里不能有 new/delete、goto、静态或局部静态变量这些会引入副作用、无法在编译期完成的操作（关于 throw 还有一处细微差别，见下面的提示）。
  2. 再收紧成「必须」。当一段逻辑（元编程、反射这类）只能在编译期完成时，用 C++20 的 consteval。它声明的是「立即函数」：任何让它在运行期求值的写法都是编译错误，把「确保编译期执行」从愿望变成了硬约束。
  3. 最后处理初始化时机。全局或静态变量有个老问题——不同翻译单元的静态变量初始化顺序没有保证，A 的构造函数里用到 B，B 却可能还没初始化，这就是「静态初始化顺序问题」。constinit 要求变量的初始化必须在编译期完成，把这个顺序依赖按死在编译前；但它只管初始化，变量本身在运行期照样可以改。

把三者摆在一起，各自的分工就清楚了：constexpr 是「能编译期也能运行期」的宽松承诺，consteval 是「只能在编译期」的硬要求，constinit 管的是「初始化必须发生在编译期」、与变量可变性无关。拿这把握尺度，就不用再纠结「这里到底该不该加 constexpr」。

编译期能算出来的东西也远不止整数。C++20 起 std::vector、std::string 的部分操作被标成 constexpr，配合 constexpr 构造函数，编译期就能构造出真正的容器对象；std::bit_cast（C++20）还能在编译期做位级别的类型重解释，比如把 float 的位表示原样看成 int。这些能力让「编译期计算」从只会算数学题，扩展到能在编译期搭出数据结构。

一个常见误解：constexpr 函数里并不是完全不许出现 throw——C++14 起函数体可以包含 throw 语句和运行时才能判定的分支，但只要这次求值真的走到抛异常，它就不再是常量表达式，编译期求值失败。所以不是「写法不允许」，而是「这次求值不合法」。另外，constexpr 并不等于「一定被优化掉或内联」，它约束的是可求值性，而不是说这段代码一定在编译期执行。

三种求值职责

求值时机类型化

编译期计算的关键不是「多写一个关键字」，而是把「这次求值能不能在编译期完成」显式地写进类型系统。constexpr 说「可以」，consteval 说「必须」，constinit 说「初始化必须在编译期」。先想清楚你要哪一种保证，剩下的交给编译器。

「立即函数（consteval）」C++20 引入，指每一次调用都必须在编译期求值的函数：任何让它落到运行期的用法都是编译错误。它与 constexpr 的区别在于 constexpr 是「能编译期求值」，传运行期参数时允许退回运行期；consteval 断了这条退路。边界：consteval 函数不能在被取地址后当作运行期函数指针调用，也不能递归调用普通（非立即）函数，否则编译期求值链会断裂。

关键代码

C++
#include <iostream>

constexpr int factorial(int n) {
    return (n <= 1) ? 1 : n * factorial(n - 1);
}

consteval int alwaysCompileTime(int x) {
    return x * 2;
}

int main() {
    constexpr int result = factorial(10);
    std::cout << "10! = " << result << std::endl;
    
    int x = 21;
    int y = alwaysCompileTime(x);
    std::cout << "alwaysCompileTime(21) = " << y << std::endl;
    
    return 0;
}
