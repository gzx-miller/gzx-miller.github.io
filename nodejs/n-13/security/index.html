服务端输入与路径安全

防止路径穿越、注入、超大请求和敏感信息泄漏。

开场问题：文件下载接口只做了一件事——把用户传来的文件名拼到上传目录后面，再去读它。有人把文件名填成 ../../../etc/passwd，服务器就把系统账号文件当成「上传目录里的文件」读了回来。目录明明是你自己定的，问题究竟出在哪一步？

把文件名当成了可信数据

你在写一个下载接口：前端把要下载的文件名交给后端，后端在固定的 uploads/ 目录里找到它、读出来返回。这个设计看起来天经地义——目录是你自己指定的，用户顶多挑个文件名而已。

漏洞就出在你把「文件名」当成了可信数据。用户交上来的字符串里可以合法地包含 ../，而它在路径里的含义是「回到上一层目录」。多写几层，就能从 uploads/ 一路退回系统根目录，把本该严禁访问的文件，变成一颗看起来「规规矩矩待在允许目录里」的文件。这类攻击叫作路径穿越。

更要紧的是，危险并非孤例。请求体大小、字段类型、数据库查询——只要外部输入被直接喂给某个「有解释权」的系统（文件系统、SQL 引擎、Shell），就有被劫持的可能。所以真正该问的是：服务端应当在哪些位置、依据什么原则，把不可信的输入拦下来？

黑名单：只挡你想到的写法

最省事的补法是黑名单：看到文件名里带 .. 就拒绝。一行判断，能挡掉开场那个案例，也第一次把「校验」放进了请求进入的位置。方向是对的，问题出在「黑名单」这种形式本身就不牢靠——它的规则由「你想到的坏写法」界定，而攻击面由「攻击者能变出的写法」界定。

  • 换个写法就漏：把 .. 写成 URL 编码的 %2e%2e，甚至编码两次，同一次穿越就绕了过去。
  • 绝对路径也没被拦住：文件名填 /etc/passwd 时，前面的目录可能被整个覆盖，拼接形同虚设。
  • 平台差异兜不住：Windows 上还有 ..\ 与盘符写法，同一段代码在 Linux 拦得住、到 Windows 就漏。
  • 长度不限也会出事：一个超长的参数或路径，足以先把解析和日志拖垮。
  • 只校验文件名也没用——数据库查询若仍靠拼字符串，注入这条路照样敞着。

白名单：只放行确定的形态

与其枚举所有坏输入，不如反过来只放行你确定安全的那一类。文件名就限定为字母、数字、点、下划线与短横线，并限制长度；字段的类型与取值范围也一次校验到位。确定的形态只有一种，其余一律拒绝——这就是白名单。

先做白名单，是因为它成本最低、覆盖面最广，能把绝大多数畸形输入挡在门外。但单靠它还不够：规则写得再细也总会有缝，于是必须紧接着补上路径层面的判断。

规范化之后再确认前缀

只靠字符串层面的检查并不足以守住目录边界。更可靠的做法，是让路径先变成它最终的样子，再回头确认它没有跑出允许范围：

  1. 用 path.resolve(base, name) 把拼接结果规整成一条绝对路径——.. 会在这一步被真正「走出去」。
  2. 确认这条规范化后的路径，其前缀仍然是 base（也就是仍在允许目录内），否则拒绝。
  3. 把校验放在真正使用路径之前，而不是「读不到再补救」。
两处最容易记反的判断：其一，「拼完」不等于「安全」——必须先 path.resolve 规范化、再校验前缀仍在 base 目录内，不能只做一次朴素拼接；其二，前端校验永远只是体验优化，绕过它易如反掌，服务端绝不能把它当成防线。

其余边界各守一类事故

路径之外，还有几类完全不同的事故，各有各的防线，分开来守：

  • 资源耗尽：为请求体设置最大体积上限，别让一个超大上传先把内存或磁盘撑爆。
  • 注入：数据库访问一律用参数化占位符（? / $1）传值，绝不把用户输入拼进 SQL 字符串。
  • 越权范围：进程以最小权限账户运行，即便某层被突破，能造成的破坏也被限制住。

为什么强调「分开守」？因为多层、独立的防线意味着即使某一层被绕过，整体也不会立刻失守——这就是纵深防御的价值。

错误响应与依赖面

还有一条常被忽视的收尾：错误响应本身也是信息泄漏面。把内部路径、堆栈、依赖库版本原样返回给客户端，等于给攻击者递了一份地图。出错时对外只给稳定的错误码和一句人话，细节留在服务端日志里。

依赖项也要纳入同一条防线：定期审计、及时升级含漏洞的版本。你信任的那些库，同样可能成为攻击者的入口——安全没有终点，它是一套持续运行的机制。

亲手验证拦截边界

一切外部输入皆不可信

服务端安全有一条地基式的判断：所有外部输入都不可信。落到实现上就是两句话——用白名单只放行确定的形态，用「规范化后再校验前缀」确认路径没跑出允许目录；其余的体积上限、参数化查询、最小权限各守一类事故。防线要独立分层，才经得起单点被绕过。

「路径穿越」指攻击者利用文件名或路径参数里的 .. 等片段，让程序访问到允许目录之外的文件。防护的做法是先用 path.resolve 规范化、再校验结果仍以 base 目录开头，并配合字段白名单（限制字符与长度）。注意 URL 编码与双重编码可能绕过朴素的字符串黑名单，且前端校验不能替代服务端校验。

关键代码

JavaScript
// ═══════════════════════════════════════════
// 1. 危险拼接：把文件名当可信数据
// ═══════════════════════════════════════════

import { readFile } from 'node:fs/promises'
import path from 'node:path'

async function unsafeRead(name) {
  const file = path.join('uploads', name)                     // 危险：name 可含 ../../
  return readFile(file, 'utf8')                               // 结果：可读到允许目录之外的文件
}

// ═══════════════════════════════════════════
// 2. 用白名单只放行确定安全的形态
// ═══════════════════════════════════════════

const SAFE_NAME = /^[a-z0-9][a-z0-9._-]*$/i                   // 字母数字点下划线短横线，且非 . 开头

function isSafeName(name) {
  return typeof name === 'string'
    && name.length <= 128                                     // 限制长度，防超长拖垮解析
    && SAFE_NAME.test(name)
}

// ═══════════════════════════════════════════
// 3. 规范化后确认仍在允许目录内
// ═══════════════════════════════════════════

const BASE = path.resolve('uploads')

function resolveInsideBase(name) {
  const target = path.resolve(BASE, name)                     // .. 在这一步被真正走出去
  if (target !== BASE && !target.startsWith(BASE + path.sep)) {
    throw new Error('路径穿越被拒绝')                          // 结果：规范化后再校验前缀
  }
  return target
}

async function safeRead(name) {
  if (!isSafeName(name)) throw new Error('文件名不合法')
  return readFile(resolveInsideBase(name), 'utf8')            // 双重防线都通过才读
}

// ═══════════════════════════════════════════
// 4. 其余边界各守一类事故
// ═══════════════════════════════════════════

const MAX_BODY = 1_000_000                                    // 请求体上限：防资源耗尽

function guardBody(body) {
  if (body.length > MAX_BODY) throw new Error('请求体过大')
  return body
}
