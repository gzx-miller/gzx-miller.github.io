Express 与 Fastify 路由对比

对比 Express 中间件链和 Fastify Schema 验证两种路由模式。

开场问题：你把日志中间件写在所有业务路由后面，跑起来一条业务日志都没打；同事又从别处抄来「洋葱式」写法，以为 next() 之后还能在响应外面收尾——同样都调了 next()，为什么写在哪、由谁承载，直接决定了它到底生不生效？

请求进入业务之前要过几道关

你在写一个用户服务。每个接口在真正干活之前，其实都要先过几道和业务无关、却每次都得做的关卡：请求体先解析成对象、调用者身份先确认、最好再留一条访问日志，最后才轮到「查库、拼返回值」这些真正的业务。

它们有一个共同的名字——横切关注点：不属于某一个接口，而是对每个接口都成立。也正因为如此，人们很容易把它们和业务揉在一起写，心里想的是「反正每个处理函数都得做这几步」。可这份「都得做」一旦只靠人记，漏一处就是一个真实缺口。真正该问的是：能不能把这类逻辑从处理函数里提出来，交给框架在确定的时机统一执行？

最省事的写法与它埋下的隐患

最直接的做法，是干脆不借助任何框架机制，把这几步写进处理函数：进函数先 if (!req.headers.authorization) return res.status(401).end()，紧接着 console.log(req.method, req.url)，然后才开始查库。

它做对了一件实实在在的事：逻辑就摆在业务旁边，谁读这个函数都看得明明白白，没有额外的框架知识要学。接口只有三五条、维护的人只有一个时，这样写最快也最直观。

  • 同一段鉴权、日志代码在几十个处理函数里复制，改一条规则就要改几十处，漏一处就留下缺口。
  • 顺序全靠人记忆：日志本该排在鉴权之后、业务之前，谁写反了行为就悄悄变了，而代码里看不出任何异常。
  • 没有统一切面，就没法「一次声明、处处生效」，这类通用逻辑也很难被单独拿出来验证。
  • 出错的收尾各写各的，返回结构五花八门，客户端拿到的错误格式都不统一。

Express：按注册顺序串起来的中间件链

Express 给的答案是中间件（middleware）。一个中间件就是一个接收 (req, res, next) 的函数，负责请求处理链路中的一段：可以读改 req / res，处理完调用 next() 把控制权交给链条上的下一个，最终命中某个路由并返回响应。于是鉴权、日志这类通用逻辑，就能从处理函数里提出来，各站一段。

规则其实只有一条：中间件按注册顺序执行。所以鉴权、日志必须用 app.use() 注册在业务路由之前，否则请求早被路由处理完了，根本轮不到它们——开场那条「日志一条没打」，就源于此。错误则走向另一头：错误处理中间件要写成四个参数 (err, req, res, next)，并注册在所有路由最后，前面任何一环抛出的异常都会一路传到它这里统一收口。

当路由多到一份文件放不下时，用 express.Router() 按前缀分组：把用户相关的接口收进一个 router，再整体挂到 /api/users 上，文件和职责就都清爽了。

一处很容易搞混的地方：Express 的中间件是线性 next 传递，请求一条道走到头；那种「请求先穿进来、响应再穿出去」的洋葱模型属于 Koa，别安到 Express 头上。另外，注册顺序就是执行顺序，写反了行为就错，没有任何中间机制会替你纠正。

Fastify：生命周期钩子与 Schema 驱动的路由

Fastify 换了组织方式，用生命周期钩子取代无限延伸的中间件链。请求进来会依次经过 onRequest、preHandler 等固定阶段，鉴权挂到 preHandler、日志挂到 onRequest，时机由框架承诺，不必再靠注册顺序去保证。往上一层是插件：一段封装好的逻辑注册进某个作用域，作用域内的路由共享它，作用域之外互不打扰，比「全局中间件」更适合按模块拆分。

它最有特色的是Schema 驱动路由。你给路由声明一份 JSON Schema，写清 body / querystring 的形态和响应该带哪些字段；框架在启动阶段就把 Schema 编译成校验函数与序列化函数。请求进来先校验输入，不合法直接返回 400，业务函数根本不会被调用；返回时再按响应 Schema 序列化输出，没声明的字段被丢弃——这既是它比逐字段手写更快的原因，也顺手堵住了「内部字段被一并带出去」这类泄漏。

日志也内置好了：Fastify 借 pino 输出结构化 JSON 日志，每个请求带上标识，收集与检索都比到处 console.log 省事得多。

选型与迁移：先对齐接口，再换内部

到底选谁没有绝对答案，看两个坐标：团队熟悉度和接口约束强度。生态成熟、要求最大灵活度、团队本来就用 Express 的，Express 更顺手；接口契约要求严格、想要 Schema 带来的输入校验与序列化加速、还想开箱即得结构化日志，Fastify 更合适。

真要换框架，稳妥的路径是先让行为对齐，再动内部实现：保持所有路由路径与响应格式完全不变，只把框架换掉，对外表现一模一样；确认没有回归后，再逐步用上 Schema、钩子这些新能力。否则接口行为一变，你分不清是框架的问题，还是接口本身的问题。

两种框架的路由对照

分歧在「请求处理怎么组织」

两个框架的差别，说到底落在「请求处理如何组织」上：Express 用一条按注册顺序执行的中间件链，把鉴权、日志排在业务路由之前，把错误收在末尾的四参数中间件里，路由可用 Router 分组；Fastify 用生命周期钩子与插件把时机固定下来，再用 JSON Schema 把输入校验与输出序列化变成启动期编译、运行时执行的声明，日志交给内置的 pino。怎么选，看团队熟哪一套、接口约束有多严；迁移时先对齐路由与响应格式，是唯一不会把水和泥沙一起搅起来的做法。

「中间件（middleware）」是签名形如 (req, res, next) 的函数，负责请求链路中的一段：读改 req / res，处理完调用 next() 把控制权交给下一个。边界：Express 中间件按注册顺序执行，鉴权、日志必须排在业务路由之前，错误处理中间件要用四个参数 (err, req, res, next) 并注册在最后，路由可用 express.Router() 按前缀分组；「请求穿入、响应穿出」的洋葱模型属于 Koa，不是 Express。Fastify 则以生命周期钩子与插件替代中间件链，用 JSON Schema 在启动期编译校验与序列化函数。

关键代码

JavaScript
// ═══════════════════════════════════════════
// 1. Express：顺序执行的中间件链
// ═══════════════════════════════════════════

import express from 'express'

const app = express()
const chain = []                                        // 说明：记录请求实际流经的中间件
app.use((req, res, next) => { chain.push('日志'); next() })     // 说明：注册顺序即执行顺序
app.use((req, res, next) => { chain.push('鉴权'); next() })     // 说明：通用逻辑排在业务路由之前
app.get('/api/users', (req, res) => {
  chain.push('路由')                                    // 结果：最终 ['日志', '鉴权', '路由']
  res.json([])                                          // 结果：命中路由后返回响应
})

// ═══════════════════════════════════════════
// 2. Express：错误处理中间件与 Router 分组
// ═══════════════════════════════════════════

const findUser = async (id) => ({ id, name: '栗子' })   // 说明：示意用的数据访问
const router = express.Router()                         // 说明：把用户相关路由归到一组
router.get('/:id', (req, res, next) => {
  findUser(req.params.id)
    .then((user) => res.json(user))                     // 结果：命中后返回
    .catch(next)                                        // 说明：异常交给错误中间件
})
app.use('/api/users', router)                           // 说明：整组挂载到子路径
app.use((err, req, res, next) => {                      // 说明：四个参数才是错误处理中间件
  res.status(500).json({ error: err.message })          // 结果：统一错误响应
})

// ═══════════════════════════════════════════
// 3. Fastify：生命周期钩子与插件
// ═══════════════════════════════════════════

import fastify from 'fastify'

const fast = fastify({ logger: true })                  // 说明：内置 pino 结构化日志
const db = { users: { findMany: async () => [] } }      // 说明：示意用的数据访问
fast.addHook('onRequest', async (req) => {
  req.startedAt = Date.now()                            // 说明：请求进入即打点，供后续钩子使用
})
fast.register(async (instance) => {
  instance.decorate('db', db)                           // 说明：插件把能力装配到实例上
})

// ═══════════════════════════════════════════
// 4. Fastify：Schema 声明并在启动期编译
// ═══════════════════════════════════════════

const userSchema = {
  type: 'object',
  properties: { id: { type: 'integer' }, name: { type: 'string' } },
  required: ['name']                                    // 说明：缺 name 时直接返回 400
}
fast.post('/api/users', {
  schema: { body: userSchema, response: { 201: userSchema } },  // 结果：启动期编译为校验与序列化函数
  handler: async (req, reply) => {
    reply.code(201)
    return { id: 1, name: req.body.name }               // 结果：只输出 Schema 声明的字段
  }
})

// ═══════════════════════════════════════════
// 5. 选型与迁移
// ═══════════════════════════════════════════

const chooseBy = { contractStrength: 'fastify', teamFamiliarity: 'express' }  // 说明：按约束强度与熟悉度选型
const builtInLogger = 'pino'                            // 结果：Fastify 内置结构化日志
const migrationRule = '先保持路由与响应格式不变，行为对齐后再做内部优化'  // 说明：避免把框架变更与接口变更混在一起
