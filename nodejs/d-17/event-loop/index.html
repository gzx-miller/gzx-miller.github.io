事件循环与宏微任务

理解 Node.js 事件循环的六个阶段，以及微任务（nextTick、Promise）和宏任务（setTimeout、setImmediate）的执行顺序。

开场问题：同一个脚本里，setTimeout(() => log('timer')) 写在 setImmediate(() => log('immediate')) 前面，直接跑，两次运行输出顺序居然不一样；可把这两行塞进一个 fs.readFile 的回调里，immediate 就每次都赢。为什么顺序会「看心情」？

宏任务微任务局限

在浏览器那套事件循环里，你已经学过「同步先跑、微任务清空、再取一个宏任务」。可到了 Node.js，光有「宏任务 / 微任务」两层，有些现象就解释不了：同样是宏任务，为什么 setTimeout(fn, 0) 和 setImmediate 的先后会翻转？为什么 process.nextTick 排得比 Promise.then 还靠前？又为什么你写 setTimeout(fn, 10)，它却可能过了一百毫秒才响？

根子在于：Node 作为服务端，要同时照看定时器、网络 I/O、文件 I/O、子进程退出、连接关闭这么多类事情，它的事件循环就不是「一个队列轮着取」，而是一圈一圈扫过的若干阶段。只按宏 / 微两层去套，必然会卡住。

浏览器结论移植

最省事的做法：把浏览器那套结论原样搬过来——「微任务优先于宏任务，Promise.then 总排在 setTimeout 前面」。

这个结论做对了一件事：它抓住了「插队」这个核心。不管是浏览器还是 Node，微任务都会抢在「下一个定时器回调」之前执行。如果只让你记一句话，这句仍然管用。

阶段顺序失配

  • 它解释不了阶段顺序：timers 和 check 都是宏任务，为什么 setTimeout(0) 和 setImmediate 的先后会翻转？
  • 它解释不了 process.nextTick 为什么总比 Promise.then 还早——那说明微任务里还分等级。
  • 它解释不了「定时器不按时」：setTimeout(fn, 0) 并不是延迟 0 毫秒执行，它只是「尽快排进 timers 阶段」。
  • 它解释不了为什么放进 I/O 回调后 setImmediate 就一定赢——它看起来像「另一个定时器」，其实不是。

事件循环六阶段

不推翻「微任务优先」，而是先把事件循环拆成六个阶段，一圈一轮地走：

  1. Timers（定时器）：执行已经到期的 setTimeout / setInterval 回调。
  2. Pending callbacks（待处理回调）：处理上一轮遗留的系统级回调，比如某些 TCP 错误。
  3. Idle / Prepare：Node 内部使用，业务代码基本不碰。
  4. Poll（轮询）：核心阶段。取回并执行 I/O 回调；队列空了就在这里等一会儿。
  5. Check（检查）：执行 setImmediate 的回调。这是 Node 特有的一站，浏览器里没有。
  6. Close callbacks（关闭回调）：处理 close 这类事件，比如 socket.on('close')。

光有阶段还不够，还有「每条回调之间的插队规则」：在每个阶段结束前，先清空 process.nextTick 队列，再清空 Promise 微任务队列。这就是为什么 nextTick 永远跑在 Promise 前面——它是一条独立、且优先级更高的队列。

现在回头看开场那个反复横跳的例子。顶层脚本刚进入事件循环时，能不能在第一个 Timers 阶段就命中等价于 setTimeout(fn, 0) 的定时器，取决于「脚本本身跑了多久」——跑得快就命中，跑得慢就错过，于是 setTimeout(0) 与 setImmediate 谁先谁后并不确定。但把这两行放进 fs.readFile 的回调里，情况就固定了：I/O 回调发生在 Poll 阶段，而 Poll 的下一站正是 Check，所以 setImmediate 必然先执行；setTimeout(0) 得再等一整圈回到 Timers。决定顺序的不是写在前后，而是它们落在环形阶段里的哪一站。

一个能把服务搞死的坑：不要在 process.nextTick 里再调度一个 process.nextTick。它会在「本阶段结束前」被反复清空，形成一个永远填不满的队列，事件循环被饿死，I/O 和定时器再也轮不上。需要让出控制权时，改用 setImmediate，把后续丢到下一个 Check 阶段。

还有一个容易背错的事实：setImmediate 是 Node.js 特有的 API，浏览器里根本不存在，别指望把这段代码原样拷进前端。至于「定时器不按时」，也是阶段模型的自然结果——setTimeout(fn, 10) 只保证「至少 10 毫秒后进入可执行状态」，真正执行还要等前面各阶段和微任务队列都走完。

微任务清空时机

回调阶段判定

Node 的事件循环不是一层「宏任务队列」，而是 Timers、Pending、Poll、Check、Close 等阶段首尾相接的一圈；每走过一个阶段，先清空 nextTick 队列、再清空 Promise 微任务队列。看懂阶段之后，setImmediate 与 setTimeout(0) 的顺序之谜、定时器为何不守时，都变成了一个「它落在哪一站」的问题。

「process.nextTick 队列」是 Node 在事件循环每个阶段之间优先清空的一条微任务队列，优先级高于 Promise 微任务，因此 process.nextTick(fn) 总排在 Promise.then 之前。它的边界在于：nextTick 里递归调度 nextTick 会无限清空、饿死事件循环；要「让出一次执行权」让 I/O 有机会推进，应改用 setImmediate。

//  │       挂起的回调          │  pending callbacks

//  └─────────────┬─────────────┘
//                │
//  ┌─────────────▼─────────────┐
//  │        空闲/准备          │  idle, prepare
//  │       内部使用             │
//  └─────────────┬─────────────┘
//                │
//  ┌─────────────▼─────────────┐
//  │         轮询             │  poll  ← 最常用、最重要
//  │  I/O 回调，定时器检测     │
//  └─────────────┬─────────────┘
//                │
//  ┌─────────────▼─────────────┐
//  │        检查              │  check
//  │     setImmediate          │
//  └─────────────┬─────────────┘
//                │
//  ┌─────────────▼─────────────┐
//  │      关闭回调             │  close callbacks
//  │  socket.on('close', ...)  │
//  └─────────────┬─────────────┘
//                │
//                └──── 循环 ────┘

// ───────── 宏任务 (Macrotasks) ─────────
// 每个阶段的回调都是宏任务
// 一个阶段执行完，才进入下一个阶段

// 常见宏任务：
// - setTimeout / setInterval     (timers 阶段)
// - setImmediate                 (check 阶段)
// - I/O 回调 (fs.readFile 等)     (poll 阶段)
// - network 请求回调
// - close 事件回调               (close 阶段)

// ───────── 微任务 (Microtasks) ─────────
// 在每个宏任务执行完后，立即执行所有微任务
// 微任务比宏任务优先级高

// 常见微任务（优先级从高到低）：
// 1. process.nextTick()         ← 最高优先级
// 2. Promise.then/catch/finally
// 3. queueMicrotask()
// 4. MutationObserver (浏览器)

// ───────── 执行顺序示例 ─────────

console.log('1. 同步代码开始')

// 微任务
process.nextTick(() => {
  console.log('3. process.nextTick 回调')
})

Promise.resolve().then(() => {
  console.log('4. Promise.then 回调')
})

queueMicrotask(() => {
  console.log('5. queueMicrotask 回调')
})

// 宏任务
setTimeout(() => {
  console.log('6. setTimeout 回调')

  process.nextTick(() => {
    console.log('8. setTimeout 内的 nextTick')
  })

  Promise.resolve().then(() => {
    console.log('9. setTimeout 内的 Promise')
  })
}, 0)

setImmediate(() => {
  console.log('7. setImmediate 回调')
})

console.log('2. 同步代码结束')

// 1. 同步代码开始
// 2. 同步代码结束
// 3. process.nextTick 回调
// 4. Promise.then 回调
// 5. queueMicrotask 回调
// 6. setTimeout 回调  ← 或者 setImmediate 先，取决于事件循环时机
// 7. setImmediate 回调
// 8. setTimeout 内的 nextTick
// 9. setTimeout 内的 Promise

// 重要规则：
// - 同步代码先执行
// - 每个宏任务执行完后，清空所有微任务队列
// - nextTick 比 Promise 微任务先执行
// - 微任务中添加的微任务，也要等当前微任务队列清空后？
//   不！微任务执行过程中新加入的微任务，会在同一次清空

// ───────── nextTick vs setImmediate ─────────

// process.nextTick:
// - 在当前操作完成后，下一个事件循环阶段前执行
// - 不是事件循环的一部分
// - 优先级比 Promise 还高
// - 可以递归调用，会阻塞事件循环（要小心！）

// setImmediate:
// - 在 check 阶段执行
// - 是事件循环的一部分
// - 每次事件循环只执行一个（如果在回调中再调用，下一轮才执行）
