child_process 子进程

对比 exec、execFile、spawn、fork 四种创建子进程方案的能力与安全性。

开场问题：你把用户上传的视频转码写成一行 exec('ffmpeg -i ' + filename + ' out.mp4')。小文件测试通过，上线后大文件一律报 maxBuffer exceeded；更吓人的是，有一天用户把文件名改成 a.mp4; rm -rf ~，命令竟然照单全收。

字符串命令隐患

在 Node 里跑外部命令是很常见的需求：调用 git、ffmpeg、系统脚本，或者干脆把一段重活丢给另一个程序去扛。这本身没错，错在你把所有外部调用都当成「传一个命令字符串」。这条路藏着几笔你必须自己承担的账：

  • 字符串里一旦拼进用户输入，;、&&、|、$(...) 都会被 shell 当成语法执行——这就是命令注入。
  • 那种「跑完一次性拿输出」的接口会把整个 stdout 缓冲在内存里，默认上限约 1 MB，长输出直接超限报错或被截断。
  • 它拿不到实时输出，进度条、增量日志这类需求根本做不了。
  • 子进程崩了、卡死了没人管，父进程可能悄悄留下一个僵尸进程。

执行外部命令到底有几种姿势，该怎么按场景选？

完整命令字符串

最直接的是 exec(command, callback)：扔进去一条完整的 shell 命令字符串，回调里拿到 (error, stdout, stderr)。

它对在了一件事：对「一条短命令、小输出、只关心最终结果」的场景，它是最顺手的一行代码。你不必关心流、不必自己拼事件，命令跑完，结果就摆在回调里。

命令注入与缓冲上限

  • exec('convert ' + userInput)，用户把 userInput 传成 a.jpg; rm -rf ~，后半句就被 shell 执行了——注入成立。
  • exec 默认把 stdout 攒到 1 MB 上限，git log 全量或 ffmpeg 的滚动日志一超就报错，你只看到一句 maxBuffer exceeded。
  • 要做实时进度，exec 的一次性回调结构天生给不了，只能整段等完。
  • 用 spawn 时 stdout / stderr 是流，data 事件给你的是 Buffer，直接当字符串用会出乱码。
  • 忘了监听 error 和 exit，命令根本不存在时父进程毫无察觉，任务静默消失。

四个API取舍

不推翻 exec，而是按「走不走 shell」和「输出是一整段还是流」这两个维度，把 API 拆成四种，各管一段：

  1. exec：走 shell，参数是一整条命令字符串，输出被缓冲（受 maxBuffer 限制）。适合短命令、小输出。命令串里绝不能拼用户输入。
  2. execFile：绕过 shell，直接执行一个可执行文件，参数以数组形式传入。因为没有 shell，天然躲开注入，参数是数组，安全首选。
  3. spawn：不经 shell，stdout / stderr 是流，边产边读，适合长输出、大文件、实时日志（要 shell 得显式加 shell: true，并慎用）。
  4. fork：专为 Node.js 脚本设计，自带一条 IPC 通道，父子进程用 child.send() 和 child.on('message') 双向对话，最重但也最灵活。

选型顺着这两条轴走就很清楚：短命令用 exec；参数里带用户输入、或要更强的可控性，用 execFile；输出长、要流式读取，用 spawn；要跑一段 Node 模块并且双方来回通信，用 fork。

再补上运维侧的生命周期：给子进程设超时，到点 kill() 兜底，防止它挂死；error 事件管「启动失败」，exit 事件管「退出码」，两个都要监听；需要 Promise 风格就用 node:child_process/promises。此外要清醒一件事：每个子进程都有独立的内存与事件循环，它解决的是「执行外部程序」和「隔离崩溃」，而「把一台机器的多核吃满」不是它的强项——那是下一课 cluster 要干的事。

安全底线：只要命令里可能掺进外部输入，就不要用 exec 做字符串拼接，改用 execFile / spawn 的「可执行文件 + 参数数组」形式；如果非要用 shell，也必须对参数做严格白名单校验，而不是靠转义字符去赌。

三种跑法输出形态

外壳与缓冲取舍

child_process 的价值是把「执行外部程序」这件事拆成四种可控的姿势：exec 顺手但走 shell、缓冲输出，execFile 绕过 shell 最安全，spawn 流式读长输出，fork 靠 IPC 跑 Node 模块。选型的核心只有两条：要不要经过 shell、输出是一整段还是流；再配上超时与 error / exit 监听，子进程才不至于变成脱缰的野马或僵尸。

「IPC 通道」指 fork 在父子进程之间自动建立的一条双向通信管道，父进程用 child.send(msg)、子进程用 process.send(msg)，双方各监听 message 事件接收；cluster 的工作进程分发也建立在它之上。它的边界是：消息必须可序列化（同样走结构化克隆），不能传函数、类实例方法或文件句柄，且消息往返有可感知的延迟，不适合当作高频共享内存来用。
