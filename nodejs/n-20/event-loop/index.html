事件循环与宏微任务

理解 Node.js 事件循环的六个阶段，以及微任务（nextTick、Promise）和宏任务（setTimeout、setImmediate）的执行顺序。

开场问题：同一个脚本里，把 setTimeout(() => log('timer'), 0) 写在 setImmediate(() => log('immediate')) 前面，直接跑，两次运行谁先打日志居然会变；可只要把这两行一起塞进一个 fs.readFile 的回调里，immediate 就每次都赢——它们不都是「尽快执行」吗，顺序为什么会浮动？

宏任务与微任务解释不了

在浏览器那套事件循环里，你已经记住一条朴素结论：同步代码先跑，然后清空微任务，再取下一个宏任务。可搬进 Node.js，它当场卡壳：setTimeout(fn, 0) 和 setImmediate 同为宏任务，顺序为什么会翻转？process.nextTick 凭什么总排在 Promise.then 前面？你写的 setTimeout(fn, 10)，又怎么会拖到几十甚至上百毫秒才响？

根子在于：Node 要同时照看定时器、网络 I/O、文件 I/O、子进程退出、连接关闭这么多类事情，它的事件循环就不是「一条队列轮着取」，而是一圈一圈扫过的若干阶段。只拿宏任务 / 微任务两层去套，必然会卡住。

把循环拆成六个阶段

不推翻「微任务优先」，而是先把这一圈拆成六个首尾相接的阶段，按顺序走：

  1. Timers（定时器）：执行已经到期的 setTimeout / setInterval 回调。
  2. Pending callbacks（待处理回调）：处理上一轮遗留的系统级回调，比如某些 TCP 错误。
  3. Idle / Prepare：Node 内部使用，业务代码基本不碰。
  4. Poll（轮询）：核心阶段。取回并执行 I/O 回调；队列空了就在这里稍作等待。
  5. Check（检查）：执行 setImmediate 的回调。这是 Node 特有的一站，浏览器里没有。
  6. Close callbacks（关闭回调）：处理 close 这类事件，例如 socket.on('close')。

六个阶段排好之后，开场那句「不都是尽快执行吗」就有了新的落点：所谓「尽快」，指的其实是「落在六个阶段里的哪一站」，而不是「延迟写了多少毫秒」。

阶段之间先清空两条微任务队列

光有阶段还不够，还要记住「回调之间怎么插队」的规则：在每个阶段结束、进入下一阶段之前，先把 process.nextTick 队列清空，再清空 Promise 微任务队列。注意这是两条独立队列，且 nextTick 优先。

这就解释了第二个现象：process.nextTick(fn) 永远跑在 Promise.then 之前——它不在 Promise 那条队伍里，而是一条优先级更高的队列。另外，一条宏任务回调中新增的微任务，也会在这次清空里被一并处理掉，不会留到下一圈，这正是你在演示里看到「每两个宏任务之间微任务被一口气清空」的原因。

I/O 回调里 setImmediate 必然更早

现在回头看开场那个反复横跳的例子。顶层脚本刚进入事件循环时，能不能在第一个 Timers 阶段就命中这个定时器，取决于「脚本自己跑了多久」——跑得快就命中、跑得慢就错过，于是 setTimeout(fn, 0) 与 setImmediate 谁先谁后并不确定。

但把这两行一起放进 fs.readFile 的回调里，情况就固定了：I/O 回调发生在 Poll 阶段，而 Poll 的下一站正是 Check，所以 setImmediate 必然先执行；setTimeout(fn, 0) 得再等一整圈绕回 Timers。决定顺序的不是写在前后，而是它们落在环形阶段里的哪一站。

顺带钉住两个容易背错的事实：setImmediate 是 Node.js 特有的 API，浏览器里根本不存在；至于「定时器不按时」，同样是阶段模型的自然结果——setTimeout(fn, 10) 只保证「至少 10 毫秒后进入可执行状态」，真正执行还要等前面各阶段和微任务队列都走完。

一个能把服务拖死的坑：不要在 process.nextTick 里再调度一个 process.nextTick。它会在「本阶段结束前」被反复清空，形成一个永远填不满的队列，事件循环被饿死，I/O 与定时器再也轮不上。需要让出控制权时，改用 setImmediate，把后续丢到下一个 Check 阶段。

看一遍真实的执行顺序

顺序取决于落在哪一站

理论讲完，还得和实测对照着看：先给出一段脚本预测顺序，再跑起来比对，错了就回到六个阶段的模型里找原因。Node 的事件循环不是一层「宏任务队列」，而是 Timers、Pending、Poll、Check、Close 首尾相接的一圈；每走过一个阶段，先清 nextTick、再清 Promise 微任务。看懂阶段之后，setImmediate 与 setTimeout(fn, 0) 的顺序之谜、定时器为何不守时，就都变成了同一个问题——它落在哪一站。

「process.nextTick 队列」是 Node 在事件循环每个阶段之间优先清空的一条微任务队列，优先级高于 Promise 微任务，因此 process.nextTick(fn) 总排在 Promise.then 之前。边界与例外：nextTick 里递归调度 nextTick 会让队列无限清空、饿死事件循环；要「让出一次执行权」让 I/O 有机会推进，应改用 setImmediate。

关键代码

JavaScript
// ═══════════════════════════════════════════
// 1. 事件循环六阶段首尾相接
// ═══════════════════════════════════════════

import { readFile } from 'node:fs'

// 一圈依次扫过六个阶段，走完再从头开始
const phases = ['timers', 'pending', 'idle,prepare', 'poll', 'check', 'close']
// timers  ：到期的 setTimeout / setInterval 回调
// pending ：上一轮遗留的系统级回调（如 TCP 错误）
// poll    ：I/O 回调，队列空时在此稍作等待
// check   ：setImmediate 回调
// close   ：socket.on('close') 等关闭回调
console.log(phases.length)                    // 结果：6

// ═══════════════════════════════════════════
// 2. 微任务分两条队列，nextTick 优先于 Promise
// ═══════════════════════════════════════════

console.log('sync start')                     // 结果：同步代码最先跑
process.nextTick(() => console.log('nextTick'))       // 结果：独立队列，最先清空
Promise.resolve().then(() => console.log('promise'))  // 结果：紧跟 nextTick 之后
console.log('sync end')                       // 结果：两个微任务排在它后面
// 输出：sync start → sync end → nextTick → promise

// ═══════════════════════════════════════════
// 3. 每阶段结束先清 nextTick 再清 Promise
// ═══════════════════════════════════════════

setTimeout(() => {
  console.log('timer')                        // 结果：宏任务，timers 阶段执行
  process.nextTick(() => console.log('timer: nextTick'))      // 结果：本阶段先清它
  Promise.resolve().then(() => console.log('timer: promise')) // 结果：紧接其后
}, 0)
// 这一组微任务会在进入下一阶段前被整体清空

// ═══════════════════════════════════════════
// 4. I/O 回调中 setImmediate 先于 setTimeout(0)
// ═══════════════════════════════════════════

readFile(import.meta.filename, () => {
  setTimeout(() => console.log('timeout'), 0)   // 结果：要再等一圈回到 timers
  setImmediate(() => console.log('immediate'))  // 结果：poll 的下一站是 check，必然更早
})

// ═══════════════════════════════════════════
// 5. 递归 nextTick 会饿死事件循环
// ═══════════════════════════════════════════

function badRecursive() {
  process.nextTick(badRecursive)              // 说明：每阶段前被反复清空，I/O 永远排不上
}

function goodRecursive() {
  setImmediate(goodRecursive)                 // 结果：Check 每轮只跑一次，让出控制权
}
