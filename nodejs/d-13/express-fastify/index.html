Express 与 Fastify 路由对比

对比 Express 中间件链和 Fastify Schema 验证两种路由模式。

开场问题：用户列表接口上线后，响应里连密码哈希都一起返回给了前端；另一个创建接口，客户端漏传了 email，服务端一声不吭，往库里写了一条空记录——这两件事其实是同一类问题的两个方向。

校验与序列化

你在写一个 Web 服务，每个接口都要做两件「和业务无关、却绝不能出错」的事：进来的数据要校验（字段在不在、类型对不对、该拒的拒），出去的数据要按约定序列化（只给客户端该看的字段，别把内部字段顺手带出去）。

这两件事有个共同点：它们对每个接口都成立，而且一旦漏掉一处就是一个真实事故——校验漏了，脏数据进库；序列化漏了，敏感字段出库。如果把判断分散到几十个处理函数里、靠人记得，出错只是时间问题。所以真正的问题是：能不能把「输入是什么、输出是什么」从命令式的代码里抽出来，写成一份框架能替你执行的契约？

处理函数手写校验

最省事的做法，就是在每个处理函数里手写：进来先 if (!req.body.email) return res.status(400).json({ error: 'email required' })，出去前手动挑字段 res.json({ id: user.id, name: user.name })。

这个方案做对了一件事：校验和裁剪确实发生了，而且就写在逻辑旁边、改起来最直接。接口只有一两个、字段只有两三个时，它是最快能跑通的写法。

重复校验维护隐患

  • 同样的校验代码在几十个处理函数里复制，改一条规则要改几十处，漏一处就是一个洞。
  • 裁剪输出靠手写 res.json({...})，新增一个内部字段时没人会记得同时更新每一处白名单，password 就是这样漏出去的。
  • 校验规则和接口文档各写各的，两者迟早对不上：文档说必填，代码却没拦。
  • 把校验、裁剪和业务揉在一个函数里，很难单独验证「契约」这一层是否可靠。

中间件与声明式校验

不推翻「在请求边界做校验与序列化」，而是改变它们被表达、被执行的层次。两条主线各有各的走法。

Express 的答案是中间件链。它用 app.use() 把横切逻辑按注册顺序串成一条链，请求沿链条被逐层处理，每个中间件改完 req / res 后调用 next() 把控制权交给下一个，命中路由后返回响应。于是校验可以从处理函数里提出来，变成一个通用中间件，鉴权、日志也排在业务路由之前统一起作用。

Fastify 走的是另一条路：声明式 Schema 加生命周期钩子。你把每个路由的输入与输出写成 JSON Schema，框架在启动阶段就把 Schema 编译成高效的校验函数与序列化函数，运行时不再逐字段解释——这正是它比手写更快的地方。请求进来先按 schema.body / schema.querystring 验证输入，不合法直接返回 400，业务处理函数根本不会被调用；响应返回时再按 schema.response 序列化输出，Schema 里没声明的字段会被丢掉，密码这类字段天然出不去。

  1. 为路由声明 schema：body / querystring 约束输入，response 约束输出。
  2. 启动时框架把 Schema 编译成校验函数与序列化函数（一次性成本，换运行时提速）。
  3. 请求到达：先跑输入校验，失败即 400，不进入业务。
  4. 处理函数返回数据：按 response Schema 序列化，多余字段被过滤掉。

为什么要先补输入、再补输出？因为输入校验拦住的是「脏数据写进系统」，离源头最近；输出序列化拦住的是「内部数据流出去」，防的方向正好相反，缺一不可。而把两者都做成 Schema 的意义在于：契约从代码里的隐含约定，变成了框架启动时就会编译、每次请求都会执行的显式声明——人和机器看的是同一份定义。

一个很容易搞错的区分：Express 的中间件是线性 next 传递——请求一条道走到头；那种「请求先穿进去、响应再穿出来」的洋葱模型属于 Koa，别安到 Express 头上。另外，中间件是按注册顺序执行的，鉴权、日志这类通用逻辑必须排在业务路由之前才有效。

那到底怎么选？没有绝对优劣，看你的诉求：生态成熟、要灵活、团队熟悉，Express 更顺；接口契约严格、想要 Schema 带来的验证与序列化加速、又需要内置结构化日志，Fastify 更合适。真要切换框架时，稳妥的路径是先保持路由与响应格式完全不变，让行为对齐，再做内部优化——否则你分不清变的是框架，还是接口本身。

两种框架路由对照

请求处理组织方式

框架的差别，本质是「请求处理的组织方式」不同：Express 用顺序中间件链把通用逻辑串起来，Fastify 用生命周期钩子加 JSON Schema，把校验与序列化变成启动期编译、运行时执行的声明式契约。选型的关键不是谁更强，而是你的接口约束有多严、团队更熟哪一套。

「Schema 驱动路由」Fastify 允许在路由上声明 JSON Schema：body / querystring 验证输入，response 约束并序列化输出，并在启动阶段编译成校验函数与序列化函数，因而比逐字段手写更快，且只输出 Schema 声明的字段（多余字段被丢弃）。与之相对，Express 以 app.use() 的顺序中间件链组织逻辑，靠 next() 线性传递；需要「请求穿入、响应穿出」的洋葱模型请用 Koa。
