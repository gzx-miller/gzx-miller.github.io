timers 定时器详解

深入理解 setTimeout、setInterval、setImmediate、process.nextTick 的语义差异和执行时机。

开场问题：你在接口末尾写了 setTimeout(() => metrics.flush(), 0)，想让「本次请求一处理完就尽快把指标刷出去」。结果这个回调排在了 process.nextTick 和 Promise.then 后面，还跟你另一处的 setImmediate 顺序对不上。同样是「尽快执行」，为什么时机完全不同？

延时写法等价性

「等一会儿再执行」在 Node 里有一堆写法，可它们并不等价，各自落在事件循环的不同阶段。最省事的理解——「延时设成 0 就是最快」——把三笔成本留给了你：

  • 把 setTimeout(fn, 0) 当成「立即执行」，忽略了它至少要等一个 timers 阶段的轮次，而且精度根本不保证。
  • 分不清两种「稍后」：一种是插当前操作的队（process.nextTick、Promise.then），另一种是等本轮回合走完（setTimeout、setImmediate）。混着用，顺序就只能靠猜。
  • 在 I/O 回调里，setImmediate 与 setTimeout(fn, 0) 的顺序和顶层脚本里还不一样，凭直觉写必然出错。

面对不同的「需要什么时机执行」，到底该挑哪一个定时器？

统一使用定时器

最偷懒的做法：不区分场景，凡是「稍后」都用 setTimeout，需要立即就用 setTimeout(fn, 0)。

它做对了一件事：setTimeout 是唯一能直白表达「延迟一段真实时间后执行」的 API，语义清楚，而且只要不 clearTimeout，回调总会被安排执行。作为「延时」的基本工具，它没有错。

零延时实际滞后

  • setTimeout(fn, 0) 的实际延迟至少是 1ms 量级，还会被前面的任务拖后，它并不「立即」。
  • 它排在 process.nextTick 和 Promise.then 之后——因为后两者是微任务，会在当前操作一结束就被整体清空。
  • 在 I/O 回调里，setImmediate 会先于 setTimeout(fn, 0) 执行，靠「延迟 0」根本排不出确定顺序。
  • setInterval 的回调若执行时间超过间隔，任务会堆积、触发时刻越走越偏。
  • 传入一个巨大的毫秒数（超过 32 位整数上限）会溢出，反倒变成「立即执行」——本想延后很久，结果马上跑了。

按执行时机选工具

不推翻 setTimeout，而是先把「时机」分成几档，再按需选工具。选择前的第一句话不是「用哪个 API」，而是「我需要它在什么时机执行」：

  1. 要插到「当前操作刚结束、别的 I/O 回调还没跑」的位置 → process.nextTick（微任务，优先级最高，甚至高于 Promise.then）。
  2. 要在微任务序列里排队、和 Promise 一致 → Promise.then / queueMicrotask。
  3. 要延迟一段真实时间 → setTimeout / setInterval，回调在 timers 阶段执行。
  4. 在 I/O 回调里要「本轮回合尽量早」 → setImmediate，它在 check 阶段执行，比 setTimeout(fn, 0) 更确定。

先补 setImmediate，因为 I/O 回调里「立即」是最常见的需求，而 setTimeout(fn, 0) 在这里顺序不确定；setImmediate 正是专治这个场景，语义也直白。

再补 process.nextTick 的边界：它优先级最高，但只能用于极短的内部逻辑。nextTick 队列清空之前，事件循环不会继续往下走，你若拿它包一个耗时任务，会把整个循环卡住，甚至饿死 I/O 回调——这比慢一点危险得多。

接着补 setInterval 的替代方案：如果回调耗时可能超过间隔，长周期任务改用递归 setTimeout（这次回调执行完，再排下一次），而不是固定间隔的 setInterval，这样就不会堆积、也不会漂移。

最后补大延时这一条：需要延后很久时，别用单个巨大的毫秒值（会溢出），改成记录一个目标时间点、用小步长去检查，或配合其它调度手段。

记住这句：setTimeout(fn, 0) 不等于「立即执行」，它只是「尽快排进 timers 阶段」；真正执行的时刻还要等前面的微任务和当前阶段走完。setImmediate 的名字里有「immediate」，但在顶层脚本里它和 setTimeout(fn, 0) 的先后其实不确定，只有在 I/O 回调内部才稳定地更早。

真实执行顺序观察

回调阶段与微宏任务

Node 的定时器差异，本质上不是「谁更快」，而是「回调落在事件循环的哪个阶段、属于微任务还是宏任务」。写之前先问一句「我需要什么时机执行」，再对号入座：插队的归微任务，延时的归 timers 阶段，I/O 回调里的「立即」归 check 阶段的 setImmediate。

「定时器漂移」指 setInterval 这类周期任务，因为回调执行时间与调度延迟不断累积，实际触发时刻逐渐偏离理论间隔（越走越晚，甚至出现堆积）的现象。边界：漂移只影响「由同一个定时器反复触发」的周期任务，单次 setTimeout 不受其影响；要消除漂移，应改用「回调执行完后重新排一次 setTimeout」的递归写法；无论哪种方式，实际触发时刻都取决于事件循环的拥挤程度，高精度的长周期调度不能只依赖 setInterval。

// 更安全的方式：递归 setTimeout
function repeat(fn, interval) {
  const timer = { id: null }

  function run() {
    fn()
    timer.id = setTimeout(run, interval)
  }

  timer.id = setTimeout(run, interval)
  return () => clearTimeout(timer.id)
}

// ───────── 常见使用模式 ─────────

// 1. 防抖 (Debounce)
//    事件停止后等待一段时间才执行
//    用于：输入框搜索、窗口 resize

function debounce(fn, delay) {
  let timer = null
  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => {
      fn.apply(this, args)
    }, delay)
  }
}

// 2. 节流 (Throttle)
//    保证在一段时间内最多执行一次
//    用于：滚动事件、按钮防重复点击

function throttle(fn, interval) {
  let lastTime = 0
  return function (...args) {
    const now = Date.now()
    if (now - lastTime >= interval) {
      lastTime = now
      fn.apply(this, args)
    }
  }
}

// 3. 超时取消
function withTimeout(promise, timeoutMs) {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => {
      reject(new Error('超时'))
    }, timeoutMs)

    promise
      .then((result) => {
        clearTimeout(timer)
        resolve(result)
      })
      .catch((err) => {
        clearTimeout(timer)
        reject(err)
      })
  })
}

// 用 AbortController 更现代
async function fetchWithTimeout(url, timeout = 5000) {
  const controller = new AbortController()
  const id = setTimeout(() => controller.abort(), timeout)

  try {
    const response = await fetch(url, {
      signal: controller.signal
    })
    return response
  } finally {
    clearTimeout(id)
  }
}
