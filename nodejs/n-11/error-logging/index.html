错误边界与结构化日志

区分操作型错误与程序错误，并记录可检索的结构化上下文。

开场问题：用户请求了一个根本不存在的课程 id，接口却返回 500「服务器内部错误」；用户以为是自己网不好、反复重试，运维还在告警群里排查一台根本没坏的服务器——一个再普通不过的业务错误，为什么会被包装成系统级故障？

出错时要同时做两件事

服务跑起来就免不了出错，而出错之后你要同时完成两个目标：给调用方一个合适的响应，也给自己留一条能排查的线索。最省事的做法，是在请求入口统一 try ... catch，把异常 console.log 出来，一律返回 500。

这一手至少保证了一件事：所有错误都有统一出口——响应总能正常结束，进程也不至于因一个未捕获的异常直接倒下。它的问题在于，把两类完全不同的错误压成了同一个结果。

一锅端的后账

  • 调用方分不清「你参数传错了（重试也没用）」和「我这边炸了（稍后或许能好）」，只能盲目重试。
  • console.log(err) 只留下堆栈，缺请求 ID、用户 ID 与入参，几十条并发日志里根本串不出是谁、在哪一步失败的。
  • 把 err.message 或堆栈直接回给客户端，等于把内部结构、甚至内部路径与 SQL 暴露出去。
  • 真正该被重视的 bug 被吞掉后，进程可能带着不一致的状态继续处理后续请求，每一个都是错的。
  • 日志里混进 token、密码、手机号，排查没帮上忙，先造成了一次越权泄漏。

问题落到一句话：错误该不该分类？给调用方的，和自己要留的，分别是什么？

先分类：操作型与程序型

一切处理都由一次分类开始。操作型错误是预期之内、能对应调用方一个具体动作的问题——参数缺失、权限不足、资源不存在、下游超时；程序型错误是本不该出现的 bug 或崩溃级故障。它们对应两条完全不同的出路：前者转成稳定的错误码交还给调用方，后者记录完整上下文后交给进程管理器重启。

再给操作型错误建立稳定的「错误码 → HTTP 状态」映射：资源不存在用 404、参数不合法用 400、未认证用 401。调用方拿到错误码就能决定是提示用户改参数、还是稍后重试，而不是对着一个笼统的 500 干猜。

在系统边界捕获并映射

捕获的位置也讲究：放在系统边界——请求入口、以及调用下游服务的那条出口。这样异步错误才在它将要泄漏到系统之外的地方被接住。整个流程可以拆成几步：

  1. 在边界用 try ... catch 捕获异常，注意异步函数里的错误要 await 到才会被接住。
  2. 把内部错误映射成公开的错误码与合适的 HTTP 状态。
  3. 用固定字段记录请求 ID 与内部原因，堆栈只进服务端日志。
  4. 故意制造一次失败，核对返回的错误码与日志字段是否对得上。

给程序型错误设计出口时，判断只有一条：捕获后记录完整堆栈与上下文，对外只回一个不带内部细节的笼统 500，然后把进程交给进程管理器去重启。不让它带病继续运行，比任何补救都重要。串接错误链时可以用 Error 的 cause 选项，把底层异常挂在自定义错误的背后，既不丢失根因，也不把它暴露给外部。

结构化日志与脱敏

自己这一侧要的可排查性，靠的是结构化日志：以 JSON 输出、字段固定（时间、级别、错误码、请求 ID、用户 ID、简短原因）。这样的日志既看得懂，也能被检索和聚合。把请求 ID 从入口一路带到每个日志点，同一笔请求的所有记录就串成一条线。

与「记全」相反的另一头是脱敏：落盘前剔除 token、密码、身份证、手机号这类敏感字段；序列化错误对象时只取进白名单的字段，而不是把整个对象原样倒出去。可排查与不泄漏，要一起满足。

全局兜底别当耳旁风

再补两道最后防线：注册 process.on('uncaughtException') 与 process.on('unhandledRejection')，接住那些漏网的异常与未处理的 Promise 拒绝。要记住它们不是「打印一下、接着跑」，而是记录后按既定策略退出或上报——否则进程就带着一个未知的坏状态继续服务。

两件最容易被忽略的事：未处理的 Promise 拒绝如果只 console.log 就放过，等于把一个失控状态留着不管；任何时候都不要把 err.stack 或原始 err.message 直接返回给客户端——对外只给稳定错误码，堆栈留给服务端日志。

日志里的稳定错误码

先分类，再分别处置

错误处理的关键是「先分类、再分别对待」：操作型错误转成稳定错误码与恰当的状态码，交给调用方去处理；程序型错误留下完整上下文后交给进程管理器重启；日志用固定字段的结构化形式记录，才查得动、也追得下去。

「操作型错误（operational error）」指运行时可预期、且调用方能理解并处理的问题，如参数缺失、权限不足、资源不存在、下游超时；它应被映射为稳定的错误码与合适的状态码（404 / 400 / 401 等），交给调用方决定是否重试。边界与例外：它与程序型错误（代码 bug、崩溃级故障）相对，后者应记录完整堆栈与上下文后交给进程管理器重启，不能伪装成 4xx 掩盖；错误对象可能携带敏感字段，落日志前必须脱敏。

关键代码

JavaScript
// ═══════════════════════════════════════════
// 1. 用稳定错误码区分错误类型
// ═══════════════════════════════════════════

class AppError extends Error {
  constructor(message, code, status = 500) {
    super(message)
    this.code = code                                          // 对外稳定错误码
    this.status = status                                      // 对应 HTTP 状态
  }
}

const notFound = (id) => new AppError(`课程 ${id} 不存在`, 'COURSE_NOT_FOUND', 404)

// ═══════════════════════════════════════════
// 2. 在系统边界捕获并映射响应
// ═══════════════════════════════════════════

import { randomUUID } from 'node:crypto'

const log = (level, message, fields) =>
  console[level === 'warn' ? 'warn' : 'error'](JSON.stringify({ level, message, ...fields }))

const loadCourse = async (id) => {
  if (id === 'missing') throw notFound(id)                    // 操作型错误：预期内
  return { id, title: '课程' }
}

async function handleRequest(req, res) {
  const requestId = randomUUID()                              // 每笔请求一个追踪 ID
  try {
    const course = await loadCourse(req.params.id)
    res.end(JSON.stringify({ ok: true, course }))
  } catch (error) {
    if (error instanceof AppError) {
      log('warn', '请求失败', { requestId, code: error.code }) // 结果：日志写稳定错误码
      res.statusCode = error.status
      res.end(JSON.stringify({ code: error.code }))            // 只回错误码，不暴露堆栈
    } else {
      log('error', '未预期错误', { requestId, stack: error.stack })
      res.statusCode = 500
      res.end(JSON.stringify({ code: 'INTERNAL_ERROR' }))      // 结果：对外无内部细节
    }
  }
}

// ═══════════════════════════════════════════
// 3. 程序型错误记录后交给进程管理器重启
// ═══════════════════════════════════════════

process.on('uncaughtException', (error) => {
  log('error', '未捕获异常', { stack: error.stack })          // 完整堆栈只写进日志
  process.exit(1)                                             // 不带病继续对外服务
})

// ═══════════════════════════════════════════
// 4. 写日志前脱敏
// ═══════════════════════════════════════════

const SENSITIVE = ['password', 'token', 'apiKey', 'authorization']
function redact(input) {
  const out = { ...input }
  for (const key of SENSITIVE) {
    if (key in out) out[key] = '***'                          // 结果：日志里看不到密钥
  }
  return out
}

// ═══════════════════════════════════════════
// 5. 兜住未处理的 Promise 拒绝
// ═══════════════════════════════════════════

process.on('unhandledRejection', (reason) => {
  log('error', '未处理的 Promise 拒绝', redact({ reason: String(reason) }))
  // 说明：不是打印后接着跑，而是上报并按既定策略退出，不把异常吞掉
})
