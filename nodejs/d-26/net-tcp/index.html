net TCP 网络编程

使用 net 模块创建 TCP 服务器和客户端，理解 Node.js 网络编程的底层基础。

开场问题：客户端连着调了两次 socket.write()，分别发出两段 JSON；服务端的 data 事件却只触发了一次，回调里的数据是两段拼在一起的一大串——你明明分两次写，它为什么一次就交上来了？

字节流无边界

你想在两个进程之间传消息：客户端发一条、服务端处理一条，来去清清楚楚。最直觉的写法是「一次 write() 对应一次 data」——我发一条，你就收一条。

但 TCP 从一开始就没打算满足这个假设。它承诺的只有三件事：连接是建立好的、字节按发送顺序到达、丢了会重传。它不承诺的恰恰是「你写了几次，我就分几次交给你」。TCP 只把数据看成一段连续的字节流：发送方怎么写、网络怎么分段、接收方缓冲区攒了多少，都会影响它一次交上来多少字节。

于是「按一次 write 收一条消息」这套做法，会留下几笔只能你自己扛的成本：你无法从字节流本身看出消息从哪开始、到哪结束；一次 data 可能是半条，也可能是三条半；想切分只能靠猜——用时间间隔切、用「大概每次都不会太大」来兜底。问题落到一句话：收到一段没有边界的字节流时，你怎么知道一条完整的消息在哪里结束？

换行符作为分隔

最省事的办法：约定「每条消息以换行符 \n 结尾」，收到数据就按 \n 切分，切出来的每一段就当成一条消息。

这个方案做对了一件关键的事：它给字节流定义了一个显式的边界标记。一旦有了边界，解析器才有可能判断「这条消息完了没有」——这正是所有应用层协议都要先回答的问题。回想 HTTP：它能一条条地工作，也是因为它在 TCP 之上又加了一层自己的边界（请求头，加上 Content-Length 或分块编码）。

分隔符自身冲突

  • 消息体自己就可能包含 \n（比如 JSON 字符串里的换行、或任意二进制数据），这个「分界」会被误当成结束符，消息被拦腰切断。
  • 一次 data 里可能装着三条完整消息加半条：直接切分、不做残留缓存，那半条就被丢了，或者被当成一条不完整的消息解析失败。
  • 反过来，一条消息也可能被拆到多次 data：每个分片单独切分，得到的都是碎片，永远拼不出完整消息。
  • 按字节切分还会和编码打架：一个多字节的汉字可能被拆在两个分片里，逐片按字符串解码会得到乱码。

缓冲与残留分帧

先把「一次 data 必须是一整条消息」这个念头扔掉，改成 缓冲区加残留。每收到一个 chunk，就把它追加到一个缓冲区里，然后尝试从缓冲区里切出尽可能多的完整消息，剩下的「半条」留在缓冲区，等下一个 chunk 到了再接上。这一步的要点是：解析器必须允许「残留半个包」，它是后面一切方案的地基。

接着解决「消息体里含分隔符就误判」的问题。把分隔符换成长度前缀分帧：约定每条消息最前面固定 4 字节 是一个大端无符号整数，表示后面消息体的字节数。解析器于是变成一台有明确状态的机器：

  1. 缓冲区不足 4 字节，等待，不做任何解析。
  2. 读满 4 字节头，解出消息体长度 N。
  3. 缓冲区不足 N 字节，继续等待，凑够再切。
  4. 切出这 N 字节作为一条完整消息，回到第 1 步处理剩下的字节。

这样一来，消息体里出现任何字符、任何二进制都无所谓——长度是显式给出的，不需要去猜哪里是结尾。服务端用 net.createServer 拿到 socket，在 data 里把收到的字节喂给上面这台状态机；客户端用 net.createConnection 连上，在 connect 回调里按同样的规则把「头 + 体」拼好再 write()。

再把几件工程上的边界补齐。一是错误与超时：socket 上要监听 error，否则对端异常断开会变成未捕获异常把进程带崩；也别忘了 setTimeout()，防止连接挂在那不动。二是安全边界：长度前缀同时也是攻击面——对端若声称「我这包 2GB」，你的解析器不能真去等；要先校验 N 是否超过协议约定的上限，超了立刻断开。三是加密边界：net 是明文传输，需要加密通信要换成 tls 模块。

三条容易踩的坑：不要假设一次 write() 对应一次 data，粘包与拆包都是正常现象；解析器必须缓存「半条」消息，而且长度字段本身也可能被拆到两次 data 里；长度前缀既要对数值做上限校验，也要记住它给出的字节数未必会一次到齐。

最后留一个验证习惯：故意构造一条远超单次缓冲的消息，让它必然被拆成多个分片发出去，观察接收端的解析器是否仍能把它还原成一条完整消息。能过这一关，分帧才算真的写对。

粘包拆包现象

应用层定义消息边界

TCP 给你的是「一串有序的字节」，不是「一条条消息」；消息的边界必须由应用层自己定义。解析器要缓存残留的半个包，再用长度前缀这类显式规则确定「一条消息到哪里结束」，粘包与拆包才会从 bug 变成可控的常态。

「长度前缀分帧」指在每条消息体之前固定写入一段表示其字节数的字段（如 4 字节大端整数），接收端先读这段长度、再等缓冲区凑齐相应字节数，才切出一条完整消息。边界与例外：长度字段本身也可能被拆到多次 data 里，同样要先进缓冲区；必须对长度做上限校验，防止对端用超大数值耗尽内存；分帧规则由应用层自定义，换个协议就不通用。

import net from 'node:net'

// ───────── TCP 服务器 ─────────

// 创建 TCP 服务器
const server = net.createServer((socket) => {
  // 新的客户端连接
  console.log('客户端连接:', socket.remoteAddress + ':' + socket.remotePort)

  // 设置编码
  socket.setEncoding('utf-8')

  // 接收数据
  socket.on('data', (data) => {
    console.log('收到数据:', data.toString().trim())

    // 回显数据
    socket.write(`服务器收到: ${data}`)

    // 如果收到 bye，关闭连接
    if (data.toString().trim().toLowerCase() === 'bye') {
      socket.end('再见！\n')
    }
  })

  // 连接关闭
  socket.on('close', () => {
    console.log('客户端断开连接')
  })

  // 连接错误
  socket.on('error', (err) => {
    console.error('连接错误:', err.message)
  })

  // 超时
  socket.setTimeout(30000) // 30 秒无数据则超时
  socket.on('timeout', () => {
    console.log('连接超时，关闭')
    socket.end('超时断开\n')
  })
})

// 解决方案：

// 3. 长度前缀（前 N 字节表示包长度）

// 方案1：换行符分隔（简单文本协议）
function readLines(socket, callback) {
  let buffer = ''

  socket.on('data', (data) => {
    buffer += data.toString()

    // 找到所有完整的行
    let newlineIndex
    while ((newlineIndex = buffer.indexOf('\n')) !== -1) {
      const line = buffer.slice(0, newlineIndex)
      buffer = buffer.slice(newlineIndex + 1)
      callback(line)
    }
  })
}

// 方案2：长度前缀（二进制协议，更可靠）
// 格式: [4字节长度][数据]

function readPackets(socket, callback) {
  let buffer = Buffer.alloc(0)

  socket.on('data', (data) => {
    buffer = Buffer.concat([buffer, data])

    while (buffer.length >= 4) {
      // 读取包长度（前4字节，大端）
      const packetLength = buffer.readUInt32BE(0)

      // 数据还不够，等下一次
      if (buffer.length < 4 + packetLength) break

      // 提取完整包
      const packet = buffer.slice(4, 4 + packetLength)

      // 移除已处理的数据
      buffer = buffer.slice(4 + packetLength)

      callback(packet)
    }
  })
}

// 发送长度前缀的包
function writePacket(socket, data) {
  const dataBuf = Buffer.from(data, 'utf-8')
  const lengthBuf = Buffer.alloc(4)
  lengthBuf.writeUInt32BE(dataBuf.length, 0)
  socket.write(Buffer.concat([lengthBuf, dataBuf]))
}
