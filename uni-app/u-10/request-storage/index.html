uni.request 封装与本地存储

把 uni.request 封装成返回 Promise 的请求层，配合 uni.setStorage/getStorage 做登录态与数据缓存。

开场问题：课程列表页每次进来都要白屏一两秒等接口，退出去再进来又是白屏；你想「把上次的数据先显示出来」，可同事那边用 uni.getStorageSync 存进去的对象，读出来变成了字符串 "[object Object]"。

服务器数据与本地缓存

这里其实有两个需求碰在一起：数据从服务器来——异步、可能失败、要带登录态；页面又希望打开就有内容——同步、在本地、能持久。最原始的做法是每个页面各写各的。

代价是三份重复。第一，每个请求都要重拼一遍 baseURL、塞 token、写 success 和 fail 两个回调，回调还会一层套一层。第二，401 要跳登录、超时要提示，这些逻辑散落在每个页面，漏改一处，某些接口就不跳登录了。第三，缓存想直接 uni.setStorageSync 塞对象，可它只认字符串，类型会悄悄丢失。

问题于是变得很清楚：请求能不能像普通函数一样 await？缓存又该用什么形态存、有什么边界？

回调式请求调用

先直接用回调式的 uni.request：uni.request({ url, success, fail })，在 success 里给列表赋值。

这个方案做对了一件事：它完成了最核心的那一步——把请求发出去、把结果收回来。只有一个接口、没有依赖时，这样写完全说得过去。

嵌套回调与配置重复

  • 多个接口有先后依赖时（先拿列表再拿详情），回调一层层嵌套，错误没法统一处理。
  • 每个调用点都要重复设置 baseURL、header 里的 token、超时时间与失败提示，改一处要改一片。
  • 登录过期（401）要在每个 success 里判断一次，漏了就成了「有的接口跳登录、有的不跳」。
  • 本地存储直接存对象会丢类型：uni.setStorageSync 只接受字符串，对象被 toString() 成 "[object Object]"。
  • 同步存储在大数据量写入时会阻塞主线程；各平台还有容量上限（小程序单个 key 约 1MB、总量约 10MB），超了会直接抛错。

异步请求统一封装

第一层，把回调包成 Promise。写一个函数，内部用 new Promise 包住 uni.request，success 里 resolve(res.data)，fail 里 reject(err)。调用点就能 await request(...)，用 try/catch 统一兜错，有依赖的请求也就变回了顺序代码。

第二层，统一出入口。把 baseURL、header、token 的拼接收进这个封装里，调用点只传业务参数（url、method、data）。于是 token 只在一个地方注入，改动只改一处。

第三层，加上拦截。在封装里做三件对所有接口都生效的事：

  1. 发请求前统一注入 token 和公共参数。
  2. 拿到响应后按业务约定判断（例如业务码不为 0 就抛错）。
  3. 遇到 401 就清缓存并跳登录。

这几步合起来就是请求拦截与响应拦截——同一套规则集中一处，不再散在页面里。

第四层，落到本地缓存。登录态、列表快照这类数据用 uni.setStorageSync / getStorageSync 读写。要点只有一个：它只存字符串，所以对象要先 JSON.stringify，读出来再 JSON.parse，否则就是开场那个 "[object Object]"。同时记住它有容量上限，别当数据库用，敏感数据也别明文存，登录态最好配一个过期时间。

第五层，同步还是异步，以及「先缓存后刷新」。同步 API 写起来顺手，但大数据量下会阻塞 UI，这时换异步的 uni.setStorage / getStorage 更稳。把两者合起来，就能做体验优化：进入页面先同步读缓存、立刻渲染，再发请求，回来后覆盖——这正是开场「白屏一两秒」的解药。

还差一步的边界：uni.request 默认超时要按业务显式设 timeout；不同小程序平台对请求域名有白名单要求，跨端上线前记得把后端域名配进各平台后台，否则真机上直接失败。

缓存先行异步刷新

远端近端数据分流

请求与缓存处理的是两类数据来源：远的交给 Promise 封装后的 uni.request，把 baseURL、token、错误与 401 收进一处；近的用本地存储持久化，但要记住它只认字符串、有容量、同步版会阻塞。把「先读缓存、再异步刷新」串起来，页面就不再每次都白屏。

「拦截器」在请求真正发出前、以及响应回来后被统一调用的一层钩子：请求拦截器可注入 token、baseURL、公共参数，响应拦截器可统一判业务码、抛错、处理 401 跳登录。边界：uni.request 本身不内置拦截器，需要在 Promise 封装里自行实现；拦截器里抛出的错误要能被调用方 catch 到，否则会变成静默失败。

关键代码

Vue
<script>
export default {
  data() {
    return { courses: [] }
  },

  onLoad() {
    // 先读缓存让页面秒开，再异步刷新覆盖
    const cached = uni.getStorageSync('courses')
    if (cached) this.courses = cached
    this.fetchCourses()
  },

  methods: {
    // 把 uni.request 封装成 Promise，统一注入 token 与错误处理
    request(options) {
      return new Promise((resolve, reject) => {
        const token = uni.getStorageSync('token')
        uni.request({
          url: options.url,
          method: options.method || 'GET',
          data: options.data,
          header: { Authorization: token ? `Bearer ${token}` : '' },
          timeout: 10000,
          success(res) {
            if (res.statusCode === 401) {
              uni.removeStorageSync('token')
              return reject(new Error('登录已过期'))
            }
            if (res.statusCode >= 200 && res.statusCode < 300) {
              resolve(res.data)
            } else {
              reject(new Error(`请求失败：${res.statusCode}`))
            }
          },
          fail: reject,
        })
      })
    },

    async fetchCourses() {
      try {
        const list = await this.request({ url: '/courses' })
        this.courses = list
        // 数据写入本地缓存，下次进入秒开
        uni.setStorageSync('courses', list)
      } catch (e) {
        uni.showToast({ title: e.message, icon: 'none' })
      }
    },
  },
}
</script>
