模块系统与生态

掌握常用 Nuxt 模块的安装配置、模块开发结构与生态使用要点。

开场问题：你想在项目里用 Pinia，按以往在 Vue 里的经验，脑子里已经开始盘算 app.use(createPinia()) 该写在哪。结果文档只说：往 nuxt.config.ts 的 modules 数组里加一行 '@pinia/nuxt' 就行。你照做了，store 竟然真的能用，连 import 都没写——这一行字符串，在构建的时候到底替你做了什么？

能力接入手工装配

给项目加一项能力（状态管理、图片优化、国际化），本质上都要做同一套「胶水」：装依赖、注册插件、配置自动导入的目录、往运行时的配置里塞值、必要时挂上构建钩子。换一个库，这套动作换汤不换药，但每一步的写法都不太一样。

旧办法是每个项目各写一遍接线。成本有三。第一，重复且分散：加一个库就要改插件、改配置、改导入目录，散落在好几个文件里，新同事根本不知道哪些文件是「胶水」。第二，升级即返工：库的大版本改了接线方式，你得把每个用过它的项目挨个改一遍。第三，时序没人约束：接线代码什么时候执行、和其他库的初始化谁先谁后，全靠约定，很容易「本地能跑、构建报错」。

于是问题落到：能不能把这套接线封装成一个可安装、可发布的包，让使用者只写一行配置？

一行安装接入方式

用 Nuxt 模块。先 pnpm add 装上模块依赖，再在 nuxt.config.ts 的 modules 数组里加一项（如 '@pinia/nuxt'）。模块的 setup 会在构建期执行，替你把插件、组件、自动导入这些接线登记好。

这个方案做对了一件事：把「接线」从每个项目里提了出来，做成可复用、可发布的包。使用者只面对一个自己理解和信任的「一行配置」，剩下的事情交回给模块作者去维护和升级。

数组顺序隐式依赖

  • 只写一行，顺序却没人管：modules 数组的顺序决定注册先后，两个有依赖关系的模块顺序颠倒了就会出错，而且是那种难复现的错。
  • 模块里既有构建期的部分（setup、hook），也有要随应用一起跑的部分（插件、composable、组件），全写在一个文件里，运行时代码会被搅进构建配置。
  • 使用者想改模块行为（比如换个组件前缀），没有统一入口，只能去改模块源码。
  • 生态里模块质量参差，选到一个维护不活跃的，某次升级 Nuxt 时它会最先出问题。

模块结构与配置入口

不推翻「一行安装」，而是把模块的结构、运行时代码的位置、配置入口与生态经验逐一理清。

先写清模块结构。用 defineNuxtModule 声明模块的 meta（name 与 configKey）和 defaults，再写 setup(options, nuxt)——它只在构建期运行。在 setup 里用 createResolver(globalThis._importMeta_.url) 解析模块内的路径，然后通过 Kit API 扩展 Nuxt：用 addPlugin 注册插件，用 nuxt.hook('imports:dirs', ...) 把 composable 目录加进自动导入，还可以往 nuxt.options.runtimeConfig 里注入值。

  1. 安装依赖，并在 nuxt.config.ts 的 modules 数组中按需排列注册顺序。
  2. 模块的 setup 在构建期运行，通过 addPlugin、addComponent、hook 等 Kit API 扩展 Nuxt。
  3. 把需要随应用运行的功能（插件、composable、组件）放进模块的 runtime/ 目录。
  4. 模块选项写在 nuxt.config.ts 中与模块 configKey 同名的配置项下。

接着把「随应用运行」的代码分离出去。构建期的 setup 只负责登记，真正的运行时插件、composable 与组件放进模块的 runtime/ 目录（例如 src/runtime/plugin.ts、src/runtime/composables/、src/runtime/components/）。分开之后，构建期不再背负运行时代码，职责也一目了然。

再规范用户的配置入口。模块把选项读成 configKey 同名的键：若 configKey 是 'myModule'，使用者在 nuxt.config.ts 里就写 myModule: { ... }，未填的项由 defaults 兜底。这就是「一行安装」之外仍然留给使用者的那个旋钮。

最后是使用生态时该守的几条经验。优先在 nuxt.com/modules 里挑选官方或高星的社区模块；本地开发或调试模块时，可以用 modulesDir 或直接引用本地路径；构建期靠 nuxt prepare 生成 .nuxt/ 下的类型声明，辅助模块开发；注册顺序即执行顺序，依赖其他模块能力的模块应放在其后注册。

顺序不是小事：modules 数组的顺序决定注册先后，也决定钩子与插件的执行次序。依赖别的模块的模块必须排在它之后——否则会出现在某台机器上偶发失败、换个环境又好了这类极难复现的问题，排查成本远高于当初多看一眼顺序。

常用模块与生态指南

构建期模块执行

Nuxt 模块是「构建期执行的接线包」：setup 在构建时通过 Kit API 替你注册插件、组件、自动导入与运行时配置，随应用运行的代码则被收进 runtime/，用户选项放在与 configKey 同名的键下。你自己装模块时只需一行，自己写模块时才需要关心结构、顺序与这套 Kit API——也正是在那一刻，你才真正看清那一行字符串到底做了什么。

「Nuxt 模块（Nuxt Module）」一个在构建期通过 setup 执行的包，用 @nuxt/kit 的 API 扩展 Nuxt：注册插件与组件、加入自动导入目录、注入运行时配置、挂载构建钩子。边界：setup 只在构建期运行，任何需要随应用运行的功能必须放进模块的 runtime/ 目录；模块选项通过 nuxt.config.ts 中与 configKey 同名的键传入；modules 数组的顺序即注册顺序，会影响钩子与插件的执行次序，存在依赖关系的模块必须注意先后。

const moduleStructure = `// 模块目录结构
my-module/
├── src/
│   ├── module.ts          # 模块入口（defineNuxtModule）
│   ├── runtime/           # 运行时代码
│   │   ├── plugin.ts      # 插件
│   │   ├── composables/   # 组合式函数
│   │   └── components/    # 组件
│   └── types.ts           # 类型定义
├── package.json
└── README.md`

const moduleCode = `// src/module.ts
import { defineNuxtModule, addPlugin, createResolver } from '@nuxt/kit'

export default defineNuxtModule({
  meta: {
    name: 'my-module',
    configKey: 'myModule',
  },
  defaults: {
    enabled: true,
    prefix: 'My',
  },
  setup(options, nuxt) {
    if (!options.enabled) return
    
    const { resolve } = createResolver(import.meta.url)
    
    // 注册插件
    addPlugin(resolve('./runtime/plugin'))
    
    // 注册 composables
    nuxt.hook('imports:dirs', (dirs) => {
      dirs.push(resolve('./runtime/composables'))
    })
    
    // 添加运行时配置
    nuxt.options.runtimeConfig.public.myModule = {
      prefix: options.prefix,
    }
  },
})`
