v4 安装与构建工具集成

比较 Vite、PostCSS 和 CLI 三种接入路径，建立最小 CSS 入口。

开场问题：我按文档装了 Tailwind，Vite 插件和 PostCSS 两套配置都配上了，结果产物里的样式体积翻了一倍——为什么「都配上」反而成了问题？

接入路径与构建环境

你给一个已有项目接入 Tailwind v4。项目本身可能有不同的构建环境：有的是 Vite 的 SPA，有的是被临时压缩成一行 CSS 的老站点，还有的需要在命令行里单独产出样式文件。接入方式看着有好几种，到底该选哪条路？

更现实的问题出现在升级时：项目里原本就有一套 PostCSS 配置，现在要换成 v4，新配置和旧配置会不会同时生效？如果会，会发生什么？

全量配置冗余

最省事的思路是「能配的都配上」：装好核心包，Vite 插件配一套，PostCSS 插件再配一套，CSS 入口里把指令都写全，心想这样总不会漏。

这个方案想对了一件事：Tailwind 需要有人把源码里的类名扫描出来、再生成最终样式，所以必须有一个「适配器」参与构建。方向没错，问题出在数量上。

同入口重复编译

  • 两套适配器同时处理同一个 CSS 入口，等于同一件事被做了两遍，样式被重复编译。
  • 旧的 PostCSS 配置没清干净，和新机制一起生效，可能出现互相覆盖的奇怪结果。
  • 非标准目录下的模板文件扫描不到，明明写了类名，产物里却没有对应样式。
  • 往往是生产构建时才发现问题，排查起来要从构建链一路往前翻。

核心包适配器分工

先建立一个最小的心智模型：核心包提供工具与运行时，适配器负责把它接进你现有的构建流程。所以接入的复杂度并不来自 Tailwind 本身，而来自你的项目里已经存在几条 CSS 处理链。看清这一点，选路就收窄成了一个问题——我的项目靠什么打包。

再具体到 v4 的结构：它由核心包和构建适配器两部分协作。CSS 入口只需要一行 @import "tailwindcss";，而扫描源码、生成最终样式这件事交给适配器完成。在 CSS-first 配置下，不再需要 tailwind.config.js。

适配器有三条路，按现有构建链选一条、且只选一条：

路径适用场景接入方式
Vite 插件Vite 项目（首选）插件列表里加 tailwindcss()
PostCSS 插件已有 PostCSS 管道配置里加 "@tailwindcss/postcss"
独立 CLI无构建工具、需单独产出命令行指定输入与输出文件
一条铁律：不要让多个适配器处理同一个 CSS 入口。Vite 项目优先用官方 Vite 插件；从旧版本升级到 v4 时，先移除 PostCSS 插件链里的旧配置，再接入新方案，避免两套机制同时生效、重复编译。

以一个 Vite 项目为例，实际步骤其实很短：装上核心包与 Vite 插件，在插件列表里注册它，再在全局样式入口写下那一行 @import，剩下的扫描与生成都由插件完成。不需要额外的配置文件，也不需要维护一串内容路径。

再就是扫描范围。v4 默认会自动检测项目源文件，但非标准目录或来自外部包的内容不一定在范围内，这时需要用 @source 显式声明，否则模板里写了类名也会被漏掉。

最后记住升级时的顺序：先拆旧、再装新。旧 PostCSS 配置还在的时候就直接加新方案，很容易得到两份重复的样式，而且这类问题往往要到比对产物体积时才暴露出来——已经在线上跑了很久才发现，就很被动了。

  1. 按现有构建链选择唯一的适配器，Vite 项目就用官方 Vite 插件。
  2. 在全局 CSS 入口导入 Tailwind，并保持这个入口唯一。
  3. 验证开发热更新与生产构建都能正确扫描到模板源文件。
  4. 在产物里确认样式只生成了一份，没有重复编译的入口。

三种适配器对照

唯一CSS入口

接入 Tailwind v4 的关键词是「唯一」。一份 CSS 入口、一个适配器，剩下的交给核心包去扫描和生成；配置能省则省，因为 CSS-first 本就不需要旧式配置文件。升级时最容易翻车的地方不是少配了，而是旧配置没清干净。

「构建适配器」是负责扫描源码类名并生成最终样式的构建侧组件，v4 提供 Vite 插件、PostCSS 插件与独立 CLI 三条路径。原则是一个 CSS 入口只配一个适配器；入口只需 @import "tailwindcss";，非标准目录用 @source 显式声明，升级时先移除旧 PostCSS 配置，避免重复编译。
