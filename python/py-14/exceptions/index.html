异常处理与错误设计

掌握 try/except/else/finally 的执行规则、异常类型匹配、raise 与自定义异常，以及 EAFP 风格。

开场问题：在 try 里写了三步，其中第二步抛出了 KeyError，而 except 里只写了 ValueError。按理说这个异常没人接，程序应该直接崩掉，可写在 finally 里的清理代码竟然照样执行了。莫非 finally 有办法「绕过」错误？

先看最朴素的做法

一开始，代码里满是「先判断再动手」的写法：if key in data: value = data[key] else: value = None，读取文件前先 if os.path.exists(...)。这类检查能挡住一部分意外，写起来也直白，对简单场景够用。

但判断和实际动作之间始终存在一个缝隙：检查通过、真正执行的那一刻，情况可能已经变了（文件刚被删、键刚被清）。于是每个操作都得配一圈判断，主流程被大量「防御代码」淹没，真正想做的事反而看不清。更麻烦的是，很多错误无法预先判断，只能等它真的发生。

try/except/else/finally 的执行顺序

用 try 把「可能出错的正常流程」圈起来，用 except 接住特定错误，主流程就能保持干净。这四个关键字各司其职，执行顺序也有明确规则：

  1. try：正常执行的代码块。没有异常时，一路执行到底。
  2. except：只有 try 块抛出了匹配的异常时才执行，用于处理错误。
  3. else：只有 try 块没有抛异常时才执行，放「成功之后」的后续动作。
  4. finally：无论是否发生异常、无论异常是否被处理，都必定执行，用来做清理，比如关闭文件、释放连接。

开场那个疑问的答案就在第四条：finally 的定位是「善后」，它不关心异常有没有被接住，只保证清理一定会跑。因此哪怕 KeyError 无人处理、正准备向上抛出，finally 里的代码也照样执行完，然后异常才继续往外传播。

异常类型匹配与 except 顺序

except 后面跟的是异常类型，而不是随便一个名字。它会拿 try 块抛出的异常去逐个比对：类型相同（或属于其子类）才算匹配，匹配上就执行对应分支，其余的继续往后面的 except 找。

由此有一条重要规则：子类要排在父类之前。如果把宽泛的 except Exception 写在前面，后面针对具体子类的分支就永远轮不到——因为所有异常都被前面那个先接走了。顺序从上到下、先具体后宽泛，才能让每种错误都落到该去的地方。想一次接住多种类型，可以写成元组 except (ValueError, TypeError)。

raise 抛出与自定义异常

raise 用来主动抛出异常：raise ValueError('数量必须为正')。相比返回一个含糊的 None 或错误码，抛出异常的好处是无法被忽略——调用方要么接住处理，要么让它一路暴露出去，不会被悄悄漏掉。

当内建异常不够精确时，可以自定义异常：继承 Exception（或其子类）定义一个新类型，例如 class InsufficientBalance(Exception): pass。这样一来，调用方既能用 except InsufficientBalance 精准接住这一种情形，也能借异常类型名把业务语义表达清楚。自定义异常通常应继承 Exception，而不是笼统的 BaseException。

异常链 raise ... from 与裸 except 的危害

在 except 块里再 raise 另一个异常时，直接抛会把原始错误信息冲淡。加上 from 就能把两者串起来：raise RuntimeError('保存失败') from error，既抛出新的业务异常，又保留了「它由谁引起」这条线索，排查时不会丢失现场。

另一件要提防的是裸 except:——不写任何类型，它会连 KeyboardInterrupt、系统退出这类不该被吞的信号一并接走，把程序拖进异常状态却看不出原因。真要兜底，至少写成 except Exception:，并且别只写一个 pass 把错误悄悄吞掉：接住之后要么处理、要么记录、要么重新抛出，否则问题只是被藏起来了。

常见误区：用 except Exception: pass 让所有错误「静默」通过，短期看似不报错，长期却让真正的缺陷极难定位。捕获范围要尽量小，且每次捕获都该有明确的应对逻辑。

EAFP 风格：先做，出错再说

前面的「先判断再动手」是 LBYL（先看后跳）。Python 更推崇的反而是 EAFP（先求原谅）——直接去做，万一出错再接住异常。例如不先判断键是否存在，而是直接取值，捕获 KeyError；不先检查文件，而是直接打开，捕获 FileNotFoundError。

EAFP 的好处是主流程只写「正常情况」，异常路径集中在 except 里，代码更紧凑；也避免了「检查通过后条件又变化」的竞态缝隙。当然它并非绝对更好：若「出错」其实是常见且可预期的分支，用判断反而更清晰。判断标准是——出错的概率低就用 EAFP，出错属于常态就用 LBYL。

看一遍异常流程与类型匹配

一句话收敛

try 圈住正常流程，except 只接匹配的异常，else 只在无异常时走，finally 无论如何都执行——这正是它能在异常未处理时依然完成清理的原因。except 匹配的是类型，子类须排在父类之前；用 raise 主动抛出、用自定义异常表达业务错误、用 raise ... from 保住异常链。捕获范围要小而具体，别用裸 except 或 pass 吞掉错误。最后，出错概率低时用 EAFP 让主流程更干净。

「EAFP」是「先求原谅，再谈许可」的缩写：直接执行操作、用异常处理错误，而非先做一堆前置检查（LBYL）。边界与例外：当某种错误属于可预期的高频分支时，显式判断更清晰；此外捕获范围应尽量具体，笼统接住所有异常会掩盖真正的缺陷。

# ════════════════════════════════════════════
# 1. try/except/else/finally 的执行顺序
# ════════════════════════════════════════════

def divide(a, b):
    try:
        result = a / b                # try：正常流程
    except ZeroDivisionError as error:
        print("捕获到除零:", error)  # except：出错时执行
        return None
    else:
        print("一切正常，结果", result)   # else：无异常时执行
        return result
    finally:
        print("finally 一定会执行")   # finally：无论如何都执行

print(divide(10, 2))
# 结果：一切正常，结果 5.0 / finally 一定会执行 / 5.0
print(divide(10, 0))
# 结果：捕获到除零: division by zero / finally 一定会执行 / None


# ════════════════════════════════════════════
# 2. 捕获多种异常与 except 顺序
# ════════════════════════════════════════════

def to_int(text):
    try:
        return int(text)
    except (ValueError, TypeError) as error:   # 一次接住多种类型
        print("无法转换:", error)
        return None

print(to_int("42"))                   # 结果：42
print(to_int("abc"))                  # 结果：无法转换: ... / None

def pick(first):
    try:
        return first[0]
    except IndexError:                # 具体的子类放在前面
        return "索引越界"
    except Exception:                 # 宽泛的兜底放在后面
        return "其他错误"

print(pick([]))                       # 结果：索引越界


# ════════════════════════════════════════════
# 3. 自定义异常类
# ════════════════════════════════════════════

class InsufficientBalance(Exception):
    """余额不足时抛出。"""            # 自定义异常通常继承 Exception

class Wallet:
    def __init__(self, balance):
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise InsufficientBalance(f"余额 {self.balance} 不足以取出 {amount}")
        self.balance -= amount
        return self.balance

try:
    Wallet(50).withdraw(100)
except InsufficientBalance as error:
    print("业务异常:", error)         # 结果：业务异常: 余额 50 不足以取出 100


# ════════════════════════════════════════════
# 4. raise ... from 保留异常链
# ════════════════════════════════════════════

class ConfigError(Exception):
    pass

def load_config(text):
    try:
        return int(text)
    except ValueError as error:
        raise ConfigError("配置项不是整数") from error   # 说明：保留原始异常

try:
    load_config("abc")
except ConfigError as error:
    print("配置错误:", error)          # 结果：配置错误: 配置项不是整数
    print("起因是:", type(error.__cause__).__name__)   # 结果：起因是: ValueError


# ════════════════════════════════════════════
# 5. EAFP：先做，出错再处理
# ════════════════════════════════════════════

data = {"name": "小明"}

try:
    age = data["age"]                 # 直接取值，出错再说
except KeyError:
    age = 0                           # 结果：没有 age 键，回退为 0
print(age)                            # 结果：0
