并发编程：线程与进程

理解 GIL 的影响，按瓶颈选择 threading 或 multiprocessing，并用 concurrent.futures 统一并发。

开场问题：你的程序要做 4 次网络请求，串行跑要 2 秒。于是你起了 4 个线程，本以为会缩短到 0.5 秒，结果时间几乎没变。线程明明「同时」在跑，为什么没有变快？

先看最朴素的做法

串行是最容易写对的方案：一个循环，做完一件再做下一件，逻辑清晰、没有共享状态、结果确定。4 个请求就是 req1 → req2 → req3 → req4，总耗时等于各自耗时相加。

可当任务多起来，串行就显得浪费——每个网络请求大部分时间都在等待，而 CPU 只能干瞪眼等第一个返回。直觉告诉我们「同时发起不就好了」，于是就有了多线程。问题是：加线程真的能变快吗？答案取决于这些任务在等什么。

GIL：为什么线程常常加了个寂寞

CPython 有一把全局解释器锁（Global Interpreter Lock，GIL）：在任意时刻，只有一个线程能执行 Python 字节码。这意味着即便你起 10 个线程，纯 Python 计算也只能一个个排队跑——多线程在这种场景下不带来加速，甚至因为切换开销更慢。

但 GIL 并非「一票否决」多线程。关键在于：线程执行阻塞式 I/O（等网络、等磁盘、等锁）时，会主动释放 GIL，别的线程可以趁机运行。所以 GIL 限制的是「纯计算的并行」，而不是「等待的重叠」。这正好解释了开场问题——如果那 4 个请求是 I/O 等待，多线程应当明显变快；若时间没变，多半是你测的其实是 CPU 计算。

threading：I/O 密集的第一选择

判断依据是任务的瓶颈在哪：任务大部分时间在等外部资源（I/O 密集），就用 threading。线程创建开销小，能共享同一进程内存，写起来也直接：

  • 用 Thread(target=func, args=(...)) 建立线程，start() 启动，join() 等它结束。
  • 多个线程同时读写同一份数据，必须用 Lock 保护，否则会出现竞态。
  • 线程适合「等待型」任务：抓取网页、批量读文件、数据库查询。

multiprocessing：CPU 密集靠多进程

当瓶颈是计算本身（大量循环、数值运算、图像处理），线程受 GIL 限制帮不上忙，就改用 multiprocessing：每个进程有自己独立的解释器和 GIL，因此可以真正同时计算，把多核吃满。

代价也要认清楚：进程不共享内存，数据要序列化（pickle）后传递，因此传大对象、频繁通信会很慢；进程启动也有可观开销。这也是 CPU 密集任务「进程数不是越多越好」的原因——超过核数只会增加调度与序列化成本。

concurrent.futures：两种池的统一入口

手写 Thread / Process 太底层，标准库提供了更高级的封装——执行器。ThreadPoolExecutor 管线程池，ProcessPoolExecutor 管进程池，接口几乎一致，切换只需换一个类名：

  1. executor.map(func, items)：把任务逐个分发，返回结果顺序与输入一致，写起来最像普通循环。
  2. futures = [executor.submit(func, x) for x in items]：提交后立刻拿到 Future 句柄，可稍后取结果。
  3. concurrent.futures.as_completed(futures)：谁先完成就先产出谁，适合「先到先处理」，不必等最慢的那个。

用 with 语句包住执行器，退出时会自动等待并回收线程/进程，和文件一样不用手动清理。

线程安全：共享数据必须上锁

多线程最容易出错的地方，是「读—改—写」不是原子的。比如 counter += 1 会被拆成读值、加一、写回三步，两个线程交错执行就可能丢掉一次加一。解药是 Lock：进入临界区前 acquire()（或用 with lock:），改完再释放，保证同一时刻只有一个线程在改。

能用消息传递，就别共享状态：共享变量越多、越复杂，越难保证线程安全。优先让每个任务只处理自己的数据，把结果汇总到一处；必须共享时才加锁，并尽量缩小临界区范围。

怎么选：一句话判断

先问瓶颈是「等」还是「算」：等一下就用线程，算得多就用进程，两者都要就组合起来。I/O 密集的任务用 ThreadPoolExecutor；CPU 密集的任务用 ProcessPoolExecutor；数量不大又要求先到先处理时，顺带用上 as_completed。不确定时，先做小规模计时实验再决定，别凭感觉。

看一遍对比与耗时

一句话收敛

GIL 让纯 Python 计算无法靠线程并行，所以I/O 密集用 threading（等待时释放 GIL），CPU 密集用 multiprocessing（绕开 GIL）；concurrent.futures 用 ThreadPoolExecutor / ProcessPoolExecutor 统一了两种池的接口，as_completed 让先完成的先产出；共享状态必须加 Lock，进程间传参要承受序列化成本。

「GIL」即全局解释器锁，保证 CPython 同一时刻只有一个线程执行字节码。边界与例外：它限制的是纯 Python 计算的并行，不阻止 I/O 等待的重叠；执行阻塞 I/O 时会释放锁，因此线程仍能加速 I/O 密集任务；想真正并行计算必须改用多进程或原生扩展。

# ═══════════════════════════════════════════
# 1. threading + Lock：共享计数器要加锁
# ═══════════════════════════════════════════

import threading
import time

counter = 0
lock = threading.Lock()

def worker() -> None:
    global counter
    for _ in range(1000):
        with lock:                    # 临界区加锁，避免读-改-写竞态
            counter += 1

threads = [threading.Thread(target=worker) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()                          # 等所有线程结束

print(counter)                        # 结果：4000，加锁后不会丢计数

# ═══════════════════════════════════════════
# 2. GIL 现象：纯计算线程不加速
# ═══════════════════════════════════════════

def busy(n: int) -> int:
    return sum(i * i for i in range(n))   # 纯 Python 计算，全程持有 GIL

t0 = time.perf_counter()
busy(300_000)
serial_cost = time.perf_counter() - t0
print(round(serial_cost, 3) >= 0)     # 结果：True，串行单次耗时被记录

t0 = time.perf_counter()
ts = [threading.Thread(target=busy, args=(300_000,)) for _ in range(2)]
for t in ts:
    t.start()
for t in ts:
    t.join()
thread_cost = time.perf_counter() - t0
print(thread_cost)                    # 结果：与串行两次耗时接近，GIL 下难并行

# ═══════════════════════════════════════════
# 3. ThreadPoolExecutor.map：I/O 密集首选
# ═══════════════════════════════════════════

from concurrent.futures import ThreadPoolExecutor

def fetch(url: str) -> str:
    time.sleep(0.1)                   # 模拟一次网络等待（等待时释放 GIL）
    return f"done:{url}"

urls = ["a", "b", "c", "d"]
with ThreadPoolExecutor(max_workers=4) as executor:
    results = list(executor.map(fetch, urls))   # 结果顺序与输入一致
print(results)                        # 结果：['done:a', 'done:b', 'done:c', 'done:d']

# ═══════════════════════════════════════════
# 4. ProcessPoolExecutor：CPU 密集绕开 GIL
# ═══════════════════════════════════════════

from concurrent.futures import ProcessPoolExecutor, as_completed

def compute(n: int) -> int:
    return sum(i * i for i in range(n))         # 顶层函数才能被 pickle 传递

if __name__ == "__main__":                      # Windows 上多进程入口必须加保护
    with ProcessPoolExecutor(max_workers=2) as executor:
        futures = [executor.submit(compute, 200_000) for _ in range(4)]
        for done in as_completed(futures):      # 谁先算完就先产出谁
            print(done.result())                # 结果：4 个相同的平方和
