Jotai 与 Recoil：原子状态与派生图

用数量、价格与总价 Atom 演示 Jotai 的原子组合与依赖追踪，并用 Recoil 的 Atom/Selector 理解细粒度派生更新。

开场问题：结算页的总价是这么算的：const total = useMemo(() => count * price, [count, price])。后来你加了会员开关，单价改成 isMember ? memberPrice : price，却忘了把 isMember 补进依赖数组——切一下会员开关，单价明明变了，总价却停在旧值一动不动。依赖关系得你亲手列，漏一个就静默出错。

基础值与派生值

这一页的真实状态其实是几个彼此独立的小事实：数量、单价、是否会员。而总价根本不是「又一份状态」，它是从这几个事实算出来的。问题在于：当一个值由别的值派生而来时，谁来记住「它依赖了谁」？

旧办法各有各的成本。把所有字段塞进一个 useState({ count, price, isMember }) 对象：任何字段变化都会产生新对象，读它的组件统统重渲染，粒度太粗。用几个独立 useState 再加 useMemo 手写依赖数组：依赖关系靠人维护，漏写就得到开场那个永远不变的总价，多写又白白重算。干脆把总价也存成一份 state，每次数量变了手动 setTotal：于是又多出一个必须和来源保持同步的真相来源，两处一不同步就打架。

所以要回答的是：能不能让「状态」和「从状态算出来的值」都各自成为一个最小单元，依赖关系由「读取」这个动作自动建立、而不是靠人列依赖数组；并且让每个组件只订阅它真正读到的那几个单元？

状态原子化拆分

最朴素的做法：Jotai 把状态拆成最小单元 atom。每个基础 atom 直接持有一个值——const countAtom = atom(1)、const priceAtom = atom(129)，组件里 const [count, setCount] = useAtom(countAtom) 就读写它。

这个方案做对了一件事：它不再按「页面」或「对象」打包状态，而是拆到了可独立订阅的最小粒度。改数量只会碰到订阅数量的组件，单价那边纹丝不动；而且 atom 定义在模块顶层、住在 React 树外面，和 Store 一样不依赖组件树。

计算逻辑归属

  • 光有基础原子，总价在哪算？如果还是塞进某个组件里 count * price，它只是个临时变量——另一个组件想要「总价」就得重算一遍，还得自己保证算法和这里完全一致。
  • 继续用 useMemo 算总价：又回到手写依赖数组，像开场那样漏掉 isMember，总价会永远停在旧值，而且编译器不报错。
  • 把总价也做成一个可写 atom 存起来，每次数量变了手动 set 一下：立刻制造出第二个真相来源，两处不同步时谁对谁错都说不清。
  • 只关心总价的组件却直接订阅了 countAtom：数量每变一次，这个和数量无关的组件也白白重渲染一次，精细拆分的意义被抵消。

派生原子定义

不推翻「最小单元」，而是让派生这件事也成为一种原子。Jotai 允许 atom 不是给一个初值，而是给一个读取函数：const totalAtom = atom((get) => get(countAtom) * get(priceAtom))。它自己没有值、也不存值，每次需要时现算现得。这就像把派生值也放进同一个「单元体系」里，区别只是它靠计算而不是靠存储。

  1. 先补「派生原子」。写下 totalAtom 的读取函数，里面用 get(countAtom)、get(priceAtom) 去读别的 atom。注意：这就是全部声明，没有额外的依赖数组——你不需要告诉系统它依赖了谁。
  2. 再理解依赖是怎么建立起来的。派生 atom 一旦被读取，Jotai 在求值时就会调它的读取函数；读取函数里每执行一次 get(otherAtom)，系统就记下一条「读边」。等价的说法是：依赖关系由「读取动作」自动声明，而不是由人在依赖数组里列举。
  3. 再把订阅粒度收回来。组件用 useAtomValue(totalAtom) 只订阅总价，它压根没读 countAtom / priceAtom，所以将来如果新增一个与总价无关的 atom，读它的组件完全不理会；某个原子变化时，只有依赖链路上真正受影响的消费者会被触发。再把派生链放进组件树，更新范围就自然收敛到了那条链上。
  4. 再补可写性的边界。派生原子本身不可直写——useAtom(totalAtom) 拿到的 setter 是空的，除非你显式给读取函数再配一个写入函数。它的值始终来自依赖原子的当前状态，想改就改上游的基础原子。
  5. 再补组织方式。atom 按功能领域拆分并在模块顶层集中定义、导出，保持引用稳定；如果确实要按 id 动态创建大量 atom（比如每门课程一个），引入 atomFamily 来统一管理，别自己手搓缓存。
  6. 最后回到开场。把 isMember 也做成 atom，在 totalAtom 的读取函数里加一句 get(isMemberAtom)，这条依赖就自动挂上了。以后谁再往里加引用，只要读了，就进了依赖图——漏依赖这件事从根上被消掉了。

再体会一下「派生」和「存储」的区别：countAtom、priceAtom 有价值、可以被写；totalAtom 没有自己的值，它只是「读的时候才跑的一段计算」。正因为如此，它永远不可能和上游不同步——它压根没存过副本。

两条容易忽略的边界：派生原子不可直写，它的值只来自上游原子，想改请改上游；atom 的定义要放在组件外部，若在渲染过程中新建 atom，每次渲染都是一个全新的引用，既拿不到缓存，订阅也会错位。

总价随数量联动

读取建立依赖

Jotai 把状态拆成最小 atom，让「基础值」和「派生值」活在同一套单元体系里：基础 atom 存值，派生 atom 用读取函数现算。依赖关系由 get 的读取动作自动建立成一张图，某个原子一变，只有链路上真正受影响的消费者会被触发。你从此不必再手写依赖数组，也就不再有「漏列一个依赖」的错误。

「派生状态（derived state）」指不额外存储、而是由其它状态经纯计算得到的值。Jotai 用读取函数 atom((get) => ...) 表达它：读取函数里每读一个上游原子，就自动建立一条依赖边。边界：派生状态只读、不可直写，想改要改上游；它不应再被复制成一份独立的可变状态，否则会出现需要同步的第二个真相来源；读取函数必须保持纯净，别在派生里产生副作用。
承接上文：一个统计面板要显示「完成率」，它订阅的是整份 todo 数组。你勾掉一项，整份列表重渲染是应该的，可那个只显示 3/5 的小面板也跟着重渲染——它明明只关心完成数，凭什么数组一变它就得跟着跑一遍？

原始值与派生值

当状态被塞进一个大对象时，谁读这个大对象，谁就得在它任何字段变化时重渲染。可业务里的两类东西本不该捆在一起：文字是原始事实，字符数是算出来的；todo 数组是原始事实，完成率是算出来的。旧办法各有各的成本。

用 Context 存大对象：任何字段一变，全部消费者重渲染，粒度粗。手写 selector + useMemo：派生逻辑散落在各个组件里，依赖靠人列，换个组件想复用同一算法就得重抄一遍。全局 store 里放 selector：能复用，但「派生引派生」的多级关系、以及异步派生，仍然缺一套统一的表达。

所以要回答的是：能不能让每个「事实」和每个「派生值」都成为独立的节点，节点之间靠「读取」连成一张有方向的依赖图，谁只读自己关心的节点，就只在那条链上被触发？

原子状态单元

最朴素的做法：Recoil 用 atom 把状态拆成最小单元——const textState = atom({ key: 'textState', default: '' })，组件里 const [text, setText] = useRecoilState(textState) 读写。这个方案做对了一件事：它把「一个大对象」拆成了可独立订阅的最小单元，改一个 atom 只惊动读它的组件。

但只要只有原子，派生值还是临时变量。

组件内派生计算

  • 字符数、完成率这类派生如果写在组件里 text.length，就只是个临时变量：另一个组件要同样的值得重算一遍，算法一旦不同步就冒出两个「字符数」。
  • 「派生引派生」——比如完成率依赖已完成数、已完成数依赖列表——没有统一写法，只能层层硬塞进同一个组件。
  • 异步派生无从表达：按 userId 去取用户资料这种「算一半要去网络拿」的值，纯同步函数写不出来。
  • 组件直接读整个数组 atom，哪怕只用到完成数，数组一变它照样重渲染，粒度又粗回去了。

派生提升为节点

不推翻「最小单元」，而是让派生也成为一种节点，并把节点连成一张有方向的图。一层层补上：

  1. 先补「派生节点」：引入 selector，它是个纯函数，用 get 去读别的 atom / selector，产出派生值。于是「字符数」「完成率」不再散落在组件里，而是图上一个有名字的节点。
  2. 再补「节点可复用」这个关键：每个 atom 与 selector 都必须有一个全局唯一的 key，这个 key 就是节点在图里的身份。任意组件都能按同一个节点引用同一份计算与结果，「派生写一遍、处处可用」才成立——这正是它和「把派生写死在某个组件里」的根本区别。
  3. 再看依赖是有方向的：selector 可以读 selector，节点便连成一张有向无环图。greetingSelector 同时读 userNameAtom 与 userMoodAtom，两个原子任一变它都重算；而只读 collectedLeavesAtom 的叶子计数器，完全不受昵称影响。
  4. 再补订阅粒度：组件用 useRecoilValue 只订阅它读的那几个节点。改一个 atom，只有图上真正连到它的订阅者被触发，旁支纹丝不动——开场那个「只关心完成数却被数组连累」的统计面板就此脱身。
  5. 再补异步：selector 的 get 可以返回 Promise，于是「派生」也能是异步的。读到这样一个异步 selector 的组件会进入挂起状态，由外层 Suspense 展示后备界面；依赖的 atom 一变，它还能失效重算。
  6. 最后守住边界：key 必须全局唯一，重名会直接报错，这是把一堆散落派生组织成一张图的前提；selector 的 get 要保持纯净，别在里面写副作用。
选型提醒：这类原子化方案与 React 生态深度绑定，主要面向 React 项目。同一个团队后来推出了新的原子化工具，采用前先确认它仍在积极维护，再决定是否落到生产。

两节点共同派生

有向无环依赖图

Recoil 把状态切成最小 atom，再用 selector 表达派生，atom 与 selector 通过「谁读了谁」连成一张有向无环图。全局唯一的 key 让每个节点都能被任意组件引用，派生逻辑从此写一遍、处处可用；组件只订阅自己读到的节点，更新就沿着图里真正相关的那条链传播，而不是整棵树一起动。

「有向无环依赖图（DAG）」指若干节点用有方向的边连接、且不存在环的图。在这里，atom 是源节点、selector 是派生节点，selector 每次 get 到一个上游节点，就相当于画了一条从上游指向它的边；因为读取是单向的、派生不能回头改上游，这张图不会有环，也就不会互相触发成死循环。边界：每个节点的 key 必须全局唯一，否则图无法确定身份；selector 必须纯净、不产生副作用。

关键代码

JSX
import React from 'react'
import { createRoot } from 'react-dom/client'
import { atom, useAtom, useAtomValue } from 'jotai'

const countAtom = atom(1)
const priceAtom = atom(129)
const totalAtom = atom((get) => get(countAtom) * get(priceAtom))

function App() {
  const [count, setCount] = useAtom(countAtom)
  const total = useAtomValue(totalAtom)
  return <main className="app"><p className="kicker">Jotai 原子依赖图</p><p>课程数量：<strong>{count}</strong></p><p className="metric">¥{total}</p><div className="actions"><button onClick={() => setCount((value) => value + 1)}>增加</button><button className="secondary" onClick={() => setCount((value) => Math.max(1, value - 1))}>减少</button></div></main>
}
createRoot(document.getElementById('root')).render(<App />)
