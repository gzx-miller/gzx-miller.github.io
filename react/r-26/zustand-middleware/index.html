Zustand Middleware 与选择性订阅

用课程进度演示 subscribeWithSelector 中间件的选择性订阅。

开场问题：你只想在课程进度跨过某个值那一刻上报一次埋点，于是写了 useCourseStore.subscribe(cb)。结果只要 Store 里任何一个字段动一下——未读数加一、弹窗开关切一次——回调都被调一遍，日志刷屏；更别扭的是回调只给你新状态，你根本不知道它是从多少跳上来的，也就判断不出「刚刚到底有没有跨过那条线」。

横切能力归属

这份 Store 除了业务状态本身，还压着几件和业务无关的事：要能把数据存进 localStorage、要能接上 Redux DevTools 看每次改动、写更新时又想用 state.progress += 20 这种可变写法省掉一堆展开。这些能力有个共同点——它们和「进度是多少」这件事正交，几乎每个 Store 都要有，却都不属于某个具体的业务字段。

旧办法各有各的代价。把持久化和调试逻辑手写进每个 action：一个 action 里既改状态又写存储又报 devtools，业务代码被横切逻辑淹掉，改一处存储键要翻遍所有 action；在组件里用 effect 手动订阅整个 Store：任何字段变化都触发回调，还只拿到新值，无从判断切片的前后差异；要接 DevTools 就自己调 window.__REDUX_DEVTOOLS_EXTENSION__：样板代码散落各处，稍不留神就和 Store 的规范对不上。

所以要回答的是：能不能在一个地方，给 Store 一次性挂上这些横切能力，而组件的消费方式一行都不用改；同时把「监听」收窄到某个切片，并能拿到它的前后两个值？

高阶函数包裹

最朴素的做法：中间件本质上是一个包裹 create 创建器的高阶函数。你写的业务创建器 (set) => ({ progress: 0, advance: () => set(...) }) 原封不动，外面套一层 subscribeWithSelector 再交给 create：create(subscribeWithSelector((set) => ({ ... })))。

这个方案做对了一件事：它把横切能力和业务状态解耦了。业务里只声明「有哪些状态、怎么改」，持久化、调试、选择性订阅这些能力，全部由中间件在外层统一追加——组件那边 useCourseStore((s) => s.progress) 照旧写，看不出 Store 外面裹了几层。

订阅粒度与顺序

  • 裸的 subscribe(listener) 不认切片：未读数变一次也回调一次，「只有 progress 变化才通知我」这条根本不成立，埋点会重复上报。
  • 回调只给一个新状态：你会看到「现在是 40%」，却拿不到「刚才还是 20%」，跨阈值判断天然做不了。
  • subscribe 返回的取消函数如果没在 useEffect 清理阶段调用，组件卸载后回调还在跑；重复挂载会叠加多个监听，一次变化触发好几次。
  • 把中间件顺序写反，比如写成 persist(devtools(...))：DevTools 里动作名会带上 persist/ 前缀，回放出来的状态和历史对不上，某些组合顺序还会让 TypeScript 类型推导直接崩掉。
  • persist 不给固定的 key、或改了 key：找不到旧的存储记录，等于每次刷新都从头开始，用户以为保存过的东西全没了。
  • 升级了状态结构却没写 version 与 migrate：用户浏览器里存的还是老结构，反序列化后新字段是 undefined，页面拿到就崩。

中间件叠加次序

不推翻「中间件包裹创建器」这条主线，而是一层一层把能力补上，并且记住越靠外层的中间件，看到的越接近最终 store 的完整行为。

  1. 先补「选择性订阅」。用 subscribeWithSelector 包住创建器，store.subscribe(selector, listener) 这个重载才存在。中间件为每个订阅记下上一次的切片值，状态变化时先算一遍 selector，只有切片变了才通知回调，并把 (value, previous) 两个值一起交给你——「从 20% 跳到 40%」终于能判断了。
  2. 再补「订阅的生命周期」。subscribe 会返回一个取消函数，把它放进 useEffect 的清理阶段调用。依赖数组写空，让这次订阅只在挂载时建立、卸载时拆掉，避免泄漏和重复监听。
  3. 再补「持久化」。外面再套一层 persist，用常量的 key 指定存储位置；一旦状态结构会演进，就同时给出 version 和 migrate，让旧数据在反序列化时被升级到新结构。
  4. 再补「调试与写法」。devtools 让每次 set 都出现在 Redux DevTools 的时间线里；immer 让你在 set 里直接写 state.progress += 20，由 immer 负责把它转成不可变更新，省掉手写展开。
  5. 最后固定组合顺序。从内到外大致是：业务创建器 → immer / subscribeWithSelector（改变赋值与订阅行为的）→ persist（负责落盘的）→ devtools（最外层的记录者）。因为 devtools 在最外层，它记录到的才是经过所有中间件之后的最终命名与结构。

拿着这套回头看开场那幕就通了：advance 只改 progress，而回调是「按 progress 这个切片」订阅的，所以别处字段怎么动它都不吭声；切片真变了，回调同时收到新旧两个值，跨没跨过那条线一目了然。刷新页面时，persist 把上次的进度从存储里读回来——而这一切都不需要组件多写一行。

两条最容易踩的边界：中间件的组合顺序会改变行为与类型推导，不要凭感觉叠，按「改行为的在内、落盘与记录在外」来排；persist 的 key 必须是常量，状态结构一旦调整就要升 version 并写好 migrate，否则老用户浏览器里的旧数据会让新代码直接崩溃。

统一包裹管理

Zustand 中间件把持久化、DevTools、Immer、选择性订阅这些横切能力从业务状态里剥离出来，用一层包裹统一追加，组件消费方式保持不变。真正决定你「能不能只听某个字段」的，是 subscribeWithSelector 那层：它让订阅带上了 selector 和前后值。叠中间件时按职责排好顺序，再把存储的 Key 与版本迁移照顾到，这套机制就能既干净又可靠。

「横切关注点（cross-cutting concern）」指那些与核心业务逻辑正交、却需要在多处统一处理的能力，例如日志、持久化、调试、鉴权、埋点。中间件正是把它从业务代码里抽出来、用一层包裹集中处理的手段。边界：横切层是隐式的调用栈，多个中间件的叠加顺序会改变结果与类型推导（越靠外层越接近最终行为，记录类中间件应放最外），因此顺序不能随意调换；持久化这类落到外部存储的能力，还要额外规划常量 Key 与版本迁移。

关键代码

JSX
import React, { useEffect, useState } from 'react'
import { createRoot } from 'react-dom/client'
import { create } from 'zustand'
import { subscribeWithSelector } from 'zustand/middleware'

const useCourseStore = create(subscribeWithSelector((set) => ({
  progress: 0,
  advance: () => set((state) => ({ progress: Math.min(100, state.progress + 20) })),
})))

function App() {
  const progress = useCourseStore((state) => state.progress)
  const advance = useCourseStore((state) => state.advance)
  const [events, setEvents] = useState([])
  useEffect(() => useCourseStore.subscribe((state) => state.progress, (value, previous) => {
    setEvents((items) => [`${previous}% → ${value}%`, ...items])
  }), [])
  return <main className="app"><p className="kicker">subscribeWithSelector</p><p className="metric">{progress}%</p><button onClick={advance}>完成一阶段</button><ul>{events.map((event) => <li key={event}>{event}</li>)}</ul></main>
}
createRoot(document.getElementById('root')).render(<App />)
