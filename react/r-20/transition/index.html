useTransition：标记非紧急状态更新

用大列表搜索演示 useTransition 的 isPending 与将筛选标记为可中断过渡更新的思路。

开场问题：你在一个有一百多门课程的搜索框里连着敲「并发」两个字，手指明明很快，输入框却像被拖住——第一个字的结果还没渲染完，第二个字已经打上去了，于是框里的字符迟迟不肯出现。

同一优先级更新冲突

输入框是受控的，每次 onChange 都用 setKeyword 更新状态，而这个关键词同时驱动两件事：输入框自己要显示这个值，结果区域要拿它去过滤一百多条数据。两件事由同一次状态更新引发，也就落在了同一个优先级上，必须一起同步走完——输入框想立刻更新，却被排在它后面的昂贵筛选拖住了。

退一步看，你要区分的其实是两种更新：输入反馈关乎手感，必须立刻；列表结果慢一拍完全可以接受。可默认模型不区分它们，于是两笔成本压到业务代码上：其一，你没法在框架层面告诉 React「这次更新不重要」，只能眼看着输入被拖慢；其二，想缓解就得自己引入防抖、节流，把调度问题从框架手里接回到自己手里，而这套调度还认不出「谁更紧急」。

问题于是明确：当一次输入会触发昂贵的列表渲染时，怎么让输入框始终保持流畅响应？

定时器延后筛选

最省事的一招是把两件事拆开：输入框的值用一次 setState 同步更新，保证键入即时可见；昂贵的列表筛选则用 setTimeout(() => setFiltered(...), 0) 推到下一个宏任务，先让浏览器把输入框画出来，再去做重活。

这个方案确实做对了一件事：它承认了「输入」和「结果」可以有不同的更新节奏，并且优先把最小的那一笔（输入框）先提交出去。方向是对的。

固定延迟不可抢占

  • 延迟是固定的：快机器上一会儿就干完了，却还要白等；慢机器上即使延迟是 0 也照样卡住下一次输入。
  • 无法被抢占。连打几个字，之前的筛选任务一个个排着队，新的输入并不能把它们叫停，结果只会越来越滞后。
  • 界面不知道「正在进行」：没有内建的状态告诉你筛选还没结束，你只能再手搓一个 loading 布尔值。
  • 定时器要自己清理：组件卸载、快速连打、路由切换，漏一次就是对已卸载组件更新。
  • 换成 requestAnimationFrame 也不解决根子——它只是把活挪到某个时机，并没有区分更新的紧急程度。

内建优先级调度

不推翻「两个节奏」，而是把「手动延迟」换成 React 内建的优先级调度。React 给出的是 useTransition()，它返回一对值 [isPending, startTransition]。用法是：把那次昂贵、但不紧急的状态更新包进 startTransition 里，告诉 React「这次更新可以低优先级、慢慢来」；而文本框自身的状态更新留在外面，保持紧急同步。

  1. onChange 里同步 setKeyword，键入必须即时可见——这一步绝不放进 Transition。
  2. 由关键词推导出的筛选结果照常在渲染阶段计算，结果区域据此展示。
  3. 把驱动结果更新的那次 setState 包进 startTransition，把它标记为低优先级的过渡更新。
  4. 一旦有更紧急的更新（比如又一次键入）到来，React 会中断过渡更新、优先推进输入，等空闲了再接着算结果。

它和之前那套手写延迟的差别在于：延迟是死的，优先级是活的。startTransition 不谈毫秒，只谈紧急程度——紧急的输入一到，正在进行的过渡就让路。而且要记住：过渡更新可以被中断，却不会被丢弃，React 保证最终一定会提交出一个一致的状态，你不会看到半成品的结果。

顺势还能拿到一个免费的反馈：isPending 会在过渡进行时为 true，拿它给结果区域降低透明度、或把标题换成「正在更新列表…」，用户就知道列表正在追赶，而不是卡死了。

最容易踩反的一处：控制文本输入的那个 setState 必须保持紧急同步，绝不能包进 startTransition，否则连键入都会失去即时反馈，输入框开始「吃字」——这恰好把要解决的问题反了过来。另外，useDeferredValue 是 useTransition 的声明式替代，适合不需要显式控制触发时机的场景；过渡更新的收益要以实际测量为准，若拆细后反而失去批处理优势，就该回退。

即时输入与列表滞后

更新紧急度分级

useTransition 补上的不是「怎么把活做快」，而是「哪笔更新更紧急」：把昂贵而不急的更新交给 startTransition，React 便会在紧急输入到来时中断它、给它让路，事后再把结果补齐。输入保持紧急、结果降级为过渡，界面就流畅了。

「过渡更新（Transition）」指通过 startTransition 标记的低优先级状态更新，可被更高优先级的更新（如文本键入）中断并稍后继续；useTransition 返回的 isPending 用于标识它是否仍在进行。边界与例外：控制输入的 setState 必须保持在紧急更新中，不可放进 Transition；过渡更新会被中断但不会被丢弃，最终提交一致状态；它是调度层面的优化，不减少计算量，收益需以实测为准，useDeferredValue 是其声明式替代。

关键代码

JSX
import { useState, useTransition } from 'react'
import { createRoot } from 'react-dom/client'

const courses = Array.from({ length: 150 }, (_, i) => ({
  id: i + 1,
  title: `课程 ${String(i + 1).padStart(3, '0')}：${['React 基础', 'Hooks 入门', '状态管理', '路由设计', '并发渲染'][i % 5]}`,
  level: ['基础', '进阶', '高级'][i % 3],
}))

function App() {
  const [keyword, setKeyword] = useState('')
  const [isPending, startTransition] = useTransition()

  const filtered = courses.filter((c) =>
    c.title.includes(keyword) || c.level.includes(keyword),
  )

  function handleChange(event) {
    const value = event.target.value
    setKeyword(value)
  }

  return (
    <main className="app">
      <header>
        <p className="kicker">useTransition</p>
        <h3>标记非紧急状态更新</h3>
      </header>
      <p className="muted">输入立即更新，列表筛选作为过渡更新在后台执行，不会阻塞输入。</p>
      <div className="toolbar">
        <input
          placeholder="搜索课程..."
          value={keyword}
          onChange={handleChange}
          style={{ maxWidth: '220px' }}
        />
        <span className="muted">{filtered.length} / {courses.length} 门课程</span>
      </div>
      <section className="panel" style={isPending ? { opacity: 0.6 } : undefined}>
        <strong>{isPending ? '正在更新列表...' : '课程列表'}</strong>
        <div style={{ maxHeight: '180px', overflow: 'auto', marginTop: '8px' }}>
          {filtered.slice(0, 30).map((course) => (
            <div key={course.id} className="muted" style={{ padding: '2px 0' }}>{course.title}</div>
          ))}
        </div>
        {filtered.length > 30 && <p className="muted">还有 {filtered.length - 30} 门课程...</p>}
      </section>
    </main>
  )
}

createRoot(document.getElementById('root')).render(<App />)
