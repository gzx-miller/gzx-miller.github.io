异步编程：事件循环、Promise 与 async/await

从事件循环与微任务出发，串起 Promise 组合器与 async/await 的串行并发取舍。

开场问题：页面上三个数据——课程、通知、进度——要一起加载，最早写成三段 await 依次获取，正确是正确了，可整页非要等最慢的那段跑完才显示；改成并发之后不到两百毫秒就齐了。同样是三个请求，为什么「排队」和「一起发」差这么多？还有，加载状态为什么必须放进 finally 才靠谱？

单线程与事件循环

JavaScript 只有一个线程执行代码，同一时刻只有一段代码在跑，靠调用栈记住「现在执行到哪」。麻烦在于：网络请求、定时器这些慢活儿，绝不能堵住这唯一的一条线程。

语言的办法是把慢活儿交出去，等它们好了再排队回来执行。等待执行的任务分成两类：微任务（Promise 的 then 回调、queueMicrotask）和宏任务（setTimeout、事件回调）。事件循环的规则是：每执行完一段同步代码，先把微任务队列清空，再去取下一个宏任务。

顺序是固定的，所以 Promise.resolve().then(...) 里的回调，永远排在同一个脚本里的 setTimeout 之前打印。开头的困惑里，「一起发」之所以快，正是因为几个请求同时在等待队列里跑，而不是一个接一个占用时间。

Promise 的三种状态

要让「稍后回来的结果」能被写成一句可读的代码，语言给了 Promise。一个 Promise 只会处在三种状态之一：pending（未落定）、fulfilled（成功）、rejected（失败），而且一旦落定就再也不改变。

  • then 处理成功，拿到返回值。
  • catch 处理失败，接住拒绝原因。
  • finally 不改变结果，只做收尾——比如关闭加载状态，这正是开头第二个问题的答案。

Promise 的贡献是把「回调套回调」的横向嵌套摊平成一条纵向的链；链上任何一步抛出或被拒绝，都会一路冒泡到最近的那个 catch。

组合器各管一段

多个请求常常要一起处理。Promise 提供了四个组合器，名字很像，行为却差得很远：

  • all：全部成功才成功，返回结果数组；只要有一个拒绝，整体立即拒绝。
  • allSettled：等全部结束，无论成败，返回每一项的 { status, value / reason }，适合「谁挂了都不影响其余」。
  • race：取最先落定的那个，成功或失败都算。
  • any：取最先成功的那个；只有全部失败，才以 AggregateError 拒绝。

选错组合器，等于选错了「一个失败该不该拖垮整批」的语义。all 与 allSettled 的差别，往往就是一处线上事故的差别。

async 函数的时机

Promise 链写长了还是难受，async/await 是它的语法糖，但有两个时机必须记住：

  • async 函数总是返回 Promise：哪怕里面 return 1，拿到的也是包着 1 的 Promise。
  • await 之前的代码是同步执行的；await 处的等待会让函数暂挂，await 之后的代码被排进微任务队列，所以它不会阻塞当前的同步代码。

换句话说，await 只「暂停」函数自己，不暂停整个线程——这解释了为什么它既保留了同步写法的可读性，又没牺牲单线程的响应性。

串行与并发的取舍

面对几个互不依赖的请求，写法直接决定耗时：

  • 串行 for...of + await：一个一个来，总耗时是它们之和，适合有先后依赖的步骤（先登录拿令牌，再用令牌取数据）。
  • 并发 Promise.all：一起发出，总耗时约等于最慢的那一个，适合彼此独立的数据。

顺带两个边界。第一，用 try/catch 处理 await 链上的拒绝：await 一个被拒绝的 Promise，会当场抛出异常，被外层 try/catch 接住，比 .catch 更贴近同步写法。第二，没人处理的拒绝不会消失，它会变成 unhandledrejection 事件——如果全局没有监听，一般就只剩控制台里一行警告。

执行顺序当场验证

先问依赖再定并发

异步的骨架其实是三件事：单线程的调用栈负责同步执行，事件循环用「先微任务、后宏任务」的规则安排那些回不来的活儿，Promise 把「稍后回来的结果」变成可链、可组合的值；async/await 则在此之上提供同步写法的糖。写并发时先问一句：这几件事彼此有没有依赖？没有就用 Promise.all 一起发，有就用 for...of + await 排好序；再顺手用 finally 收尾、用 try/catch 与 unhandledrejection 兜住拒绝。

「微任务」指当前宏任务结束后、在下一个宏任务开始前被清空的队列，来源包括 Promise.then 的回调与 queueMicrotask。事件循环的规则是：执行完一段同步代码后先清空微任务队列，再取下一个宏任务（如定时器回调）。因此同一轮里，then 里的代码永远排在 setTimeout 之前。

关键代码

JavaScript
// ═══════════════════════════════════════════
// 1. 单线程与调用栈
// ═══════════════════════════════════════════

function second() { console.log('2') }
function first() { console.log('1'); second(); console.log('3') }
first()                                       // 依次输出 1 → 2 → 3（调用栈后进先出）

// ═══════════════════════════════════════════
// 2. 事件循环：先清空微任务，再取宏任务
// ═══════════════════════════════════════════

console.log('脚本开始')
setTimeout(() => console.log('宏任务 setTimeout'))            // 最后执行
queueMicrotask(() => console.log('微任务 queueMicrotask'))   // 次先执行
Promise.resolve().then(() => console.log('微任务 then'))      // 最先执行
console.log('脚本结束')
// 顺序：脚本开始 → 脚本结束 → 微任务 then → 微任务 queueMicrotask → 宏任务 setTimeout

// ═══════════════════════════════════════════
// 3. Promise 的三种状态
// ═══════════════════════════════════════════

const p = Promise.resolve('done')             // 状态只能是 pending / fulfilled / rejected
p.then(v => v)                                // 'done'   ← fulfilled 后进入 then
p.catch(e => e)                               // 未被拒绝，此回调不执行
p.finally(() => '清理')                        // 结果不变，只做收尾

// ═══════════════════════════════════════════
// 4. 组合器的差异
// ═══════════════════════════════════════════

Promise.all([Promise.resolve(1), Promise.resolve(2)])         // 全部成功 → [1, 2]
Promise.all([Promise.resolve(1), Promise.reject('err')])      // 一个拒绝 → 立即以 'err' 拒绝
Promise.allSettled([Promise.resolve(1), Promise.reject('err')])
// 结果：[{ status: 'fulfilled', value: 1 }, { status: 'rejected', reason: 'err' }]
Promise.race([Promise.resolve('快'), new Promise(() => {})])   // 最先落定 → '快'
Promise.any([Promise.reject('a'), Promise.resolve('b')])       // 首个成功 → 'b'
Promise.any([Promise.reject('a'), Promise.reject('b')])        // 全部失败 → 以 AggregateError 拒绝

// ═══════════════════════════════════════════
// 5. async 总返回 Promise，await 之后的时机
// ═══════════════════════════════════════════

async function f() { return 1 }
f() instanceof Promise                        // true   ← 返回值被包成 Promise
async function g() {
  console.log('await 之前同步')
  await null
  console.log('await 之后进入微任务')
}
console.log('调用 g 前'); g(); console.log('调用 g 后')
// 输出：调用 g 前 → await 之前同步 → 调用 g 后 → await 之后进入微任务

// ═══════════════════════════════════════════
// 6. 串行与并发的耗时取舍
// ═══════════════════════════════════════════

const delay = (ms) => new Promise((r) => setTimeout(r, ms))
async function serial() { for (const ms of [100, 100, 100]) await delay(ms) }   // 约 300ms
async function parallel() { await Promise.all([delay(100), delay(100), delay(100)]) } // 约 100ms

// ═══════════════════════════════════════════
// 7. 用 try/catch 处理 await 链上的拒绝
// ═══════════════════════════════════════════

async function load() {
  try { await Promise.reject(new Error('接口失败')) }
  catch (e) { e.message }                     // '接口失败'  ← await 的拒绝被当场抛出并接住
}
load()
Promise.reject(new Error('没人处理'))          // 触发 unhandledrejection 事件
window.addEventListener('unhandledrejection', (e) => {})   // 全局兜底未处理的拒绝
