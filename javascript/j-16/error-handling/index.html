错误处理与自定义异常

用 try/catch/finally 和自定义 Error 子类构建可恢复的错误流，并用 cause 保留错误链。

开场问题：报名表单里，姓名字段没填够两个字，和服务器返回 503，失败后进了同一个 catch，前端一律弹出「提交失败，请重试」。同事排查了半天才发现：一个是用户自己填错了，重试一百次也没用；一个是网络抖动，重试一次就好。两句完全不同的失败被同一句话糊住了——可它们本来就该被分开对待。

错误与抛出

你想做的是一件小事：出错时别让程序闷头崩掉，得有个地方把它接住。语言给的初版答案就是 try/catch——把可能出错的代码包进 try，一旦抛错就跳到 catch 里执行。

先看清被接住的到底是什么。运行时抛出的错误不是一句字符串，而是对象，并且按来源分成几族：SyntaxError（代码本身没法解析）、TypeError（值的类型不对，比如对 undefined 取属性）、ReferenceError（引用了不存在的变量）、RangeError（数值或长度超出允许范围）。

  • 它们都继承自 Error，所以 catch 拿到的对象自带 message 与 stack——前者是文字说明，后者是调用栈。
  • 这套内置类型的好处是：光看 name 就能判断错误出在哪一类，不用去猜字符串内容。
  • 还有一个常见误解要纠正：throw 并不要求你抛 Error，抛数字、字符串、对象都合法。

但合法不等于应该。一旦抛出的是字符串，catch 里既没有 message 也没有 stack，链路上每一层都只能靠猜。所以约定是：throw 只抛 Error 或它的子类。

捕获与收尾的顺序

最省事的做法是：try 里写业务，catch 里写提示。它确实做对了一件事——错误被局部接住，后面的代码还能继续跑，不至于因为一次失败整页停摆。

可它漏掉了「无论如何都要收尾」这件事：请求既然发出去了，不管成功还是失败，加载状态都得关掉、连接都得释放——而 catch 只在出错时才执行，正常返回时它根本轮不到。这时就需要 finally：它无条件在 try 与 catch 之后执行，即使 try 里已经 return 了也照样会跑。执行顺序固定为 try →（出错则）catch → finally。

其中有两个细节最容易忽略：

  • catch 的绑定可以省略（ES2019 起）：catch { ... }，当你不关心错误对象、只想「接住并忽略」时更简洁。
  • finally 里写 return 会覆盖 try 与 catch 的返回值——前面算好的结果会被直接丢弃。

所以给 finally 划一条界线：只用它做清理，不要在里面写 return。

给错误起个名字

回到开头的困惑。默认的 Error 只有一个 message，catch 接到的无论是校验失败还是网络失败，都长得一模一样，只能靠字符串里有没有「503」去猜。

更好的做法是继承 Error，定义业务异常类，并在构造函数里把 name 设成类名。这样 err.name 直接告诉你是哪一类，instanceof 也能精确区分：

  • class ValidationError extends Error，构造里 this.name = 'ValidationError'，并把业务字段（比如 field）一并挂上去。
  • 这样造出的实例仍然是 Error（instanceof Error 为真），所以兜底的 catch 也接得住它。
  • 分流时用 instanceof：是 ValidationError 就提示用户改输入，是 NetworkError 就提示稍后重试。

于是「同一个 catch 里的两种失败」终于有了不同的后续处理——这正是开头那个问题需要的答案。

别丢掉原始错误

分层调用里，错误常常被「翻译」：底层抛的是 SyntaxError（配置文件没法解析），可你希望上层抛一句业务话「解析配置失败」，好让调用方读懂。于是你新建一个 Error 抛出去。

可这样一来，底层那条原始错误就没了——排查时只看到业务话，根本不知道根因是解析失败。更准确地说，你把「是什么」替换成了「看起来像什么」。补救方式是 cause 选项：new Error('解析配置失败', { cause: lowError })，把原始错误挂在 cause 上。

这样形成的是一条错误链：上层读 err.message 得到业务化的说明，顺着 err.cause 才能拿到根因；链可以一层层串下去，一直到最初那个错误。既保留了可读的提示文案，又不丢失排错线索。

异步边界的漏网

还有一个最容易踩的边界：try/catch 接不住异步回调里抛出的同步错误。try { setTimeout(() => { throw new Error() }, 0) } catch (e) { ... } 里的 catch 根本不会执行——定时器回调是在当前调用栈清空之后才运行的，那时 try/catch 早就退出了。Promise 被拒绝同理，它不会自己走进 try/catch（除非你 await 它）。

这类「谁都没接住」的错误，只能靠全局兜底：

  • window.onerror 或 window.addEventListener('error', ...) 接住未捕获的同步错误。
  • window.addEventListener('unhandledrejection', ...) 接住没有被任何 catch 处理的 Promise 拒绝。
  • 它们的作用是把漏网的错误送到日志或监控，而不是就地恢复流程——到那时出错的上下文早已不在。

异常链路逐步观察

先分类再处理

错误处理从来不是「用一个 catch 包住所有东西」。内置错误类型族帮你认出错误来源，try/catch/finally 负责执行顺序与收尾，自定义 Error 子类配合 name 与 instanceof 让业务能按类型分流，cause 把原始错误串成链，全局兜底接住异步边界的漏网之鱼。写 catch 时先问一句：这个错误属于哪一类、原始错误又在哪里，再决定怎么处理。

「错误链」指错误在被逐层「翻译」时，用 new Error('上层说明', { cause: 原始错误 }) 把底层错误挂在 cause 属性上所形成的一条链。上层读到的是业务化的 message，沿着 cause 一路向下就能找到最初的根因——既保留了可读的提示，又不丢失排错线索。

关键代码

JavaScript
// ═══════════════════════════════════════════
// 1. 内置错误类型族
// ═══════════════════════════════════════════

try { null.foo } catch (e) { e.name }          // 'TypeError'
try { notDefined } catch (e) { e.name }        // 'ReferenceError'
try { new Array(-1) } catch (e) { e.name }     // 'RangeError'
try { JSON.parse('{') } catch (e) { e.name }   // 'SyntaxError'
new Error('出错').message                      // '出错'

// ═══════════════════════════════════════════
// 2. throw 可以抛任意值，但应抛 Error
// ═══════════════════════════════════════════

try { throw '字符串' } catch (e) { typeof e }    // 'string'  ← 能抛，但丢了 message 与 stack
try { throw { code: 42 } } catch (e) { e.code }  // 42       ← 对象也能抛，但不是 Error
new Error('推荐').name                           // 'Error'  ← 应抛 Error 或其子类

// ═══════════════════════════════════════════
// 3. try/catch/finally 的执行顺序
// ═══════════════════════════════════════════

const order = []
try { order.push('try'); throw new Error('x') }
catch (e) { order.push('catch') }
finally { order.push('finally') }
order.join(' → ')                              // 'try → catch → finally'

// ═══════════════════════════════════════════
// 4. catch 绑定可省略（ES2019）
// ═══════════════════════════════════════════

try { JSON.parse('{') } catch { '接住并忽略，不绑定错误对象' }   // 合法

// ═══════════════════════════════════════════
// 5. finally 里的 return 会覆盖 try/catch 的返回
// ═══════════════════════════════════════════

function a() { try { return 'ok' } finally { return 'finally' } }
a()                                            // 'finally'  ← try 的返回值被丢弃
function b() { try { throw new Error() } catch { return 'caught' } finally { return 'finally' } }
b()                                            // 'finally'  ← catch 的返回值也被覆盖

// ═══════════════════════════════════════════
// 6. 继承 Error 定义带业务字段的异常
// ═══════════════════════════════════════════

class ValidationError extends Error {
  constructor(field, message) {
    super(message)
    this.name = 'ValidationError'
    this.field = field
  }
}
const err = new ValidationError('name', '姓名至少 2 个字符')
err.name                                       // 'ValidationError'
err.field                                      // 'name'
err instanceof ValidationError                 // true
err instanceof Error                           // true   ← 仍是一般的 Error，兜底也能接

// ═══════════════════════════════════════════
// 7. 用 cause 保留原始错误，形成错误链
// ═══════════════════════════════════════════

try {
  try { JSON.parse('bad') }
  catch (low) { throw new Error('解析配置失败', { cause: low }) }
} catch (top) {
  top.message                                  // '解析配置失败'
  top.cause.name                               // 'SyntaxError'  ← 根因仍在链上
}

// ═══════════════════════════════════════════
// 8. try/catch 接不住的异步边界
// ═══════════════════════════════════════════

try { setTimeout(() => { throw new Error('定时器内') }, 0) }
catch (e) { console.log('不会执行') }          // 回调在栈清空后运行，catch 早已退出
window.addEventListener('error', (e) => {})               // 全局兜底未捕获的同步错误
window.addEventListener('unhandledrejection', (e) => {})  // 兜底没人处理的 Promise 拒绝
