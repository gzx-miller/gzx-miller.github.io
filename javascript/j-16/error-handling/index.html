错误处理与自定义异常

用 try/catch/finally 和自定义 Error 类构建可恢复的错误流。

开场问题：表单提交失败时界面只弹一句「操作失败」，你怎么分辨这次到底是「姓名太短」还是「服务器 503」？

失败来源分类

真实程序里，失败来自四面八方：JSON.parse() 拿到坏数据会抛错、网络请求会超时、业务规则校验会不通过。你希望它们能被分别处理，并且在向上传递时保留「到底哪一步出的错」，好在界面上给出准确的提示。

不做统一处理的代价是：错误散落各处，有的被静默吞掉，有的只剩一句笼统的「失败」，排查时只能靠猜。

更麻烦的是，同一个错误往往要在多层函数之间传递：底层知道原因，上层要给用户提示，中间几层只负责转发。如果没有一种能承载上下文的载体，信息会在每一层被压扁成一句笼统的话，等真正要处理时，原始原因早就丢失了。

返回值错误表达

最省事的做法：用返回值表达错误——函数失败就 return 一个错误字符串或 false，让调用方自己判断。

这个方案做对了一件事：不打断执行流程，逻辑线性、简单直接，适合纯粹的、可预期的失败分支。

但它有个隐含前提：调用方足够自觉。只要有一个人少写一个判断，错误就顺着返回值一路漂过去，最后在别处爆发成更难查的问题——那时你已经看不到它最初是从哪冒出来的了。

错误信息表达局限

  • 可被无视：调用方完全可以不检查返回值继续往下跑，错误被悄悄吞掉。
  • 只有一条消息：拿到的是一句字符串，没法按「类型」分流，只能去解析 message 文本，脆弱又难维护。
  • 丢上下文：原始错误（哪个字段、哪次请求）在层层传参途中就丢了。
  • 异步更别扭：Promise 与 await 的结果里混着错误，用返回值表达非常难受。

异常抛出与捕获

不推翻「判断失败」，而是让失败升级为一种可抛、可捕获、可携带信息的一等对象。

核心是 try/catch/finally。用 try 包住可能抛错的代码，catch 捕获抛出的异常，finally 无论成功失败都执行——适合放清理逻辑（关闭连接、复位状态）。关键的一点是，catch 不只捕获同步异常，也能捕获 async/await 中被拒绝的 Promise，于是同步与异步边界的失败可以汇入同一处来处理。

接着把错误分类：继承 Error 定义自定义异常类，比如 class ValidationError extends Error，在构造函数里塞进业务字段（哪个字段不合法），并设置 this.name。处理时就可以用 instanceof 或 err.name 分支，而不再去解析 message 字符串这种脆弱做法。这样一来，「姓名太短」和「服务器 503」就是两种能被程序分辨的类型，界面自然给得出不同文案。

再解决上下文丢失：Error 构造器支持 cause 选项（ES2022），super(message, { cause: err }) 能把原始错误挂到新错误上，形成错误链——你在外层抛出更友好的错误，同时底层原因完整保留。

自定义异常还有个实际好处：调用方可以用 instanceof 精确判断「这是我关心的业务错误」还是「意料之外的崩溃」。前者给用户一句友好提示，后者记录日志并上报，两条处理路径泾渭分明。反观只拿一句 message 字符串去判断，靠的是文本比对，改动一处文案就可能让分支逻辑失效。

两个边界要知道：try/catch 捕获不到 setTimeout 这类异步回调内部的同步抛出，因为回调在另一个任务里执行，调用栈早已不同；Promise 链连续 then 时用最后的 catch 兜底，未处理的拒绝还要配置全局监听，否则会静默丢失。

类型分流与上下文

系统边界统一收口

错误处理的关键，是把失败当成设计对象而非意外：在系统边界统一收口，用类型清晰分流，用 cause 保留底层上下文。这样「失败」才是一条可追踪、可恢复的路径。

从一个笼统的字符串，到一条带类型、带原因、可被精确捕获的错误链，中间差的不是语法，而是把「失败」纳入设计的态度。

「异常与错误链」try/catch 捕获同步异常以及 async/await 中被拒绝的 Promise，finally 无论成败都执行清理；继承 Error 可定义携带业务字段的自定义异常，按类型或 name 分流；super(message, { cause: err }) 用 cause（ES2022）把原始错误挂到新错误上，形成错误链、保留底层上下文。

关键代码

JavaScript
// 错误处理与自定义异常

// ── try / catch / finally 基础 ──
function parseJSON(str) {
  try {
    return JSON.parse(str)
  } catch (err) {
    console.error('解析失败：', err.message)
    return null
  } finally {
    console.log('解析结束（无论成败）')
  }
}

// ── 自定义异常类 ──
class ValidationError extends Error {
  constructor(field, message) {
    super(message)
    this.name = 'ValidationError'
    this.field = field
  }
}

class NetworkError extends Error {
  constructor(message, statusCode) {
    super(message)
    this.name = 'NetworkError'
    this.statusCode = statusCode
  }
}

// ── error.cause 错误链（ES2022） ──
function saveCourse(data) {
  try {
    if (!data.title) throw new ValidationError('title', '课程标题不能为空')
  } catch (err) {
    // 包装原始错误，保留上下文
    throw new Error('保存课程失败', { cause: err })
  }
}
try {
  saveCourse({ title: '' })
} catch (err) {
  console.log(err.message)           // '保存课程失败'
  console.log(err.cause.name)        // 'ValidationError'
  console.log(err.cause.field)       // 'title'
}

// ── 内置错误类型 ──
// TypeError  — 类型不对  null.foo
// RangeError — 超出范围  new Array(-1)
// SyntaxError — 语法错误  eval('let let')
// ReferenceError — 引用不存在  unknownVar

// ── 异步错误处理 ──
async function safeFetch(url) {
  try {
    const res = await fetch(url)
    if (!res.ok) throw new NetworkError(res.statusText, res.status)
    return await res.json()
  } catch (err) {
    // async 中的 catch 能捕获 await 链上的所有 reject
    console.error(`${err.name}: ${err.message}`)
  }
}
