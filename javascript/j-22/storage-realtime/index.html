浏览器存储与实时通信

对比 localStorage/sessionStorage 与 IndexedDB 的选型，用 WebSocket 建立持久双向连接。

开场问题：用户在 A 标签页里登录后改了昵称，切到 B 标签页，头像旁边还是旧名字，非得手动刷新一下才更新——同一份 localStorage 数据，为什么另一个标签页像没看见一样？

两种本地存储

想在浏览器里存点东西，最常见的钥匙就是 localStorage。它按「键值对」存取，刷新页面不丢，关掉浏览器再打开也还在——几乎所有需要「记住我」的功能都靠它。用着用着，很容易把所有状态都往里塞，直到碰上另一个需求：那份「只在本次填写里生效」的草稿，其实不该长期留着。

这时 sessionStorage 才显出自己的定位。两者的用法一模一样，差别在生命周期：localStorage 是持久的，跨会话保留；sessionStorage 以标签页为单位，标签页一关就清空，同一个站点的两个标签页各自独立、互不影响。需要「填一次就够」的临时状态放 sessionStorage，需要「下次还认得你」的放 localStorage，各归其位才不互相干扰。

只能存字符串

第一次往 localStorage 存对象，多半会踩到坑：读出来是一串 [object Object]。原因是它只接受字符串，写入时会把非字符串的值强制转成字符串，这层转换你根本看不见。

要存结构化的数据，就得自己承担这层转换：写入前用 JSON.stringify() 序列化成字符串，读取时用 JSON.parse() 还原。多了这两步，对象、数组乃至布尔值、数字都能安全地存下来；代价是自己记住——数字存进去再读出来会变成字符串形态，需要运算时得显式转回。

storage 事件与配额

回到开场那个「另一个标签页不更新」的问题：它其实对应一个专门的机制——storage 事件。当某份存储被修改时，浏览器会通知其他同源的标签页；监听它，就能在别处同步更新界面，把跨标签页的状态拉齐。

这里有个极易误解的点：storage 事件只在「其他」标签页触发。写入数据的那一个页面自己收不到事件，它本来就是变更的发起方，无需再被通知。所以跨页同步要「一边写、一边在别处听」，指望同一页面听自己的写入会落空。

另一个边界是容量。存储是有配额的，写入超出上限时会抛出 QuotaExceededError。这意味着「存进去」并不是一个可以省略错误处理的动作，尤其当内容由用户输入或接口返回时，最好用 try/catch 兜住，以免整段逻辑因为一次超限而中断。

同步读写的代价

localStorage 用起来顺手，是因为它读写同步——调用就立刻拿到结果，没有回调也没有 Promise。方便的另一面是隐患：同步意味着这段读写会占住主线程，期间页面无法响应交互。存几十字节无感，可一旦序列化几万条记录再写进去，卡顿就会肉眼可见。

大数据量该换 IndexedDB。它完全不同：异步，读写都返回请求对象或 Promise，不阻塞主线程；基于事务，一组操作要么全成功、要么一起回滚，不会写到一半留下不一致；数据存在对象仓库（object store）里，可以建索引、做范围查询，能力接近一个内嵌的小型数据库。代价是用起来更重，简单的键值存取反而不值得。

从轮询到长连接

存储解决的是「本地留数据」，可聊天、行情、协同编辑这类需求，数据要的是「服务端主动送过来」。最笨的做法是轮询：客户端每隔几秒去问一次「有新消息吗」。它简单，却把大量请求花在「没有」上，延迟还不稳定。

WebSocket 换了一条路。它先用一次普通的 HTTP 请求做升级握手，握手成功后，这条连接就升级为持久、双向的通道——双方随时可以向对方发送数据，不必再一问一答。代价是状态要靠事件管理：连接建立触发 open，收到数据触发 message，连接关闭触发 close，出错触发 error。少了哪一个都会让连接状态变得难以预料。

亲手存储与连接

重连心跳与选型

WebSocket 有一个必须自己补上的短板：它不会自动重连。网络一抖、连接一断，就是真的断了，得在 close 事件里自行发起重连，通常配上逐次加长的退避间隔，避免服务器刚恢复就被重连风暴打垮。此外长时间空闲的连接可能被中间层掐断，所以要定期发送心跳保活，确认通道仍然可用。

并不是所有「服务端推数据」都值得上 WebSocket。若只是服务端单向推送，比如进度通知、日志流，SSE/EventSource 更省事：它就是一条长连接，服务端往客户端单向发，而且断线后浏览器会自动重连，重连逻辑不用自己写。选型的分界线很清楚——只有需要客户端也主动、频繁地发数据（全双工）时，才用 WebSocket；只需单向推送，SSE 就够了。

「全双工」指通信双方可以同时收发数据，WebSocket 在 HTTP 升级握手后建立的正是这样的通道；与之相对，SSE/EventSource 是服务端到客户端的单向推送。前者适合聊天、协同编辑等双向频繁交互，后者适合进度、通知等单向流。

// ═══════════════════════════════════════════
// 1. localStorage 与 sessionStorage 的生命周期
// ═══════════════════════════════════════════

localStorage.setItem('theme', 'dark')     // 持久保存，关闭浏览器仍在
sessionStorage.setItem('step', '2')       // 仅当前标签页，关闭即清空
localStorage.getItem('theme')             // 'dark'
sessionStorage.getItem('step')            // '2'
// 两者用法一致，差别只在生命周期：一个跨会话，一个以标签页为单位

// ═══════════════════════════════════════════
// 2. 只能存字符串，存对象要序列化
// ═══════════════════════════════════════════

localStorage.setItem('cart', { n: 1 })                  // 实际存成 "[object Object]"
localStorage.setItem('cart', JSON.stringify({ n: 1 }))  // 正确写法：先序列化
JSON.parse(localStorage.getItem('cart')).n             // 1   ← 读时再还原
localStorage.getItem('count')                          // '3' ← 数字存进去会变字符串

// ═══════════════════════════════════════════
// 3. storage 事件只在本页之外的标签页触发
// ═══════════════════════════════════════════

window.addEventListener('storage', (e) => {
  e.key        // 变化的键名，仅在“其他”同源标签页触发
  e.newValue   // 新值；写入数据的那一页自己收不到该事件
})
// 跨标签页同步：一边写、一边在别处监听，才能在另一个页面拉齐界面

// ═══════════════════════════════════════════
// 4. 超出配额抛出 QuotaExceededError
// ═══════════════════════════════════════════

try {
  localStorage.setItem('big', 'x'.repeat(5_000_000))
} catch (e) {
  e.name       // 'QuotaExceededError'  ← 写入超出存储配额
}
// 「存进去」不是必然成功，内容来自用户或接口时要用 try/catch 兜住

// ═══════════════════════════════════════════
// 5. localStorage 同步读写会阻塞主线程
// ═══════════════════════════════════════════

localStorage.setItem('cache', JSON.stringify(rows))   // 同步写，主线程被占住
// 几十字节无感，几万条记录再序列化就会卡顿
// 大数据量改用 IndexedDB：异步、基于事务，不阻塞主线程

// ═══════════════════════════════════════════
// 6. IndexedDB 的事务与对象仓库
// ═══════════════════════════════════════════

const db = await openDB('shop', 1)                     // 异步打开数据库
const tx = db.transaction('orders', 'readwrite')       // 三、一组操作放进事务
tx.objectStore('orders').put({ id: 1, total: 99 })     // 对象仓库写入
// 事务要么全成功、要么一起回滚，不会写到一半留下不一致
// 对象仓库可建索引、做范围查询，能力接近一个内嵌的小型数据库

// ═══════════════════════════════════════════
// 7. WebSocket 的 open / message / close / error
// ═══════════════════════════════════════════

const ws = new WebSocket('wss://example.com/chat')   // HTTP 升级握手后建立连接
ws.onopen = () => { /* 握手完成，通道建立 */ }
ws.onmessage = (e) => { e.data /* 服务端推来的数据帧 */ }
ws.onclose = () => { /* 连接关闭，需自行重连 */ }
ws.onerror = () => { /* 连接出错 */ }
ws.send('hello')                                     // 客户端可随时主动发送

// ═══════════════════════════════════════════
// 8. 生产环境的重连与心跳
// ═══════════════════════════════════════════

function scheduleReconnect() {
  setTimeout(connect, 1000)          // 断线后自行重连，间隔逐次加长防重连风暴
}
setInterval(() => ws.send('ping'), 30000)   // 定期心跳，确认通道仍然可用
// WebSocket 不会自动重连，这两件事必须自己补上

// ═══════════════════════════════════════════
// 9. SSE 是服务端单向推送，自带断线重连
// ═══════════════════════════════════════════

const es = new EventSource('/api/stream')   // 单向：仅服务端 → 客户端
es.onmessage = (e) => console.log(e.data)   // 断线后浏览器自动重连，无需自写
// 只需单向推送（进度、通知）选 SSE；需要双向频繁交互才用 WebSocket
