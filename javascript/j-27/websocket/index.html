WebSocket 与实时通信

用 WebSocket 建立持久双向连接，理解与服务端推送（SSE）的差异。

开场问题：聊天窗口里对方发来的消息，你没点任何按钮、也没刷新页面，它就自己冒出来了——浏览器是怎么「知道」服务端有话说？

服务端主动推送

假设你在做一个多人协作的看板，或者一个聊天室。这里有一条硬性要求：服务端产生的新数据，要能主动送到客户端。别人新增了一张卡片，你的界面就应该立刻多出一张，而不是等你手点刷新才看见。

可 fetch 的模型天生是反过来的——它由客户端发起，问一次、答一次，然后连接就结束了。服务端想找你，没有门路，因为它在这次「一问一答」里没有任何主动权。于是你只能让浏览器每隔几秒去问一次「有新消息吗」。这种轮询的代价很实在：大部分请求都在问「没有」，白白消耗流量和服务器资源；而真正的消息，最快也要等到下一次轮询才被看到，始终慢半拍。

定时轮询实现

最省事的做法就是轮询：写一个 setInterval，每隔两秒调一次接口，把最新的消息列表拿回来渲染。它不需要服务端配合任何新协议，用现成的接口就能跑起来。

这个方案确实做对了一件事：它证明了「客户端持续获取更新」这条路是可行的，只要不断去问，就总能问到。这个「保持数据同步」的目标要保留，问题出在实现方式上。

轮询延迟与开销

  • 绝大部分请求的答案都是「没有新消息」，流量和服务器的算力被大量浪费。
  • 延迟固定等于轮询间隔。想更快只能缩短间隔，代价是请求量进一步翻倍。
  • 每一次轮询都要重新建连接、走一遍 HTTP 头，开销远大于真正传输的那点数据。
  • 它本质上是单向的「我来问、你来答」，服务端永远无法主动开口，实时性被结构性地限制住了。

长连接建立与握手

问题的根子在于「一问一答、答完就断」。那能不能让这条连接一直开着？可以——这就是 WebSocket。它先用一次普通的 HTTP 请求做「升级握手」，服务器同意之后，这条连接就从「一次性」变成了持久的双向通道：此后客户端和服务端随时都能往对面推数据，不必谁先问谁才答，这就是所谓全双工。延迟从「一个轮询周期」降到了「一次网络往返」。

用起来也很直接。先 new WebSocket(url) 创建实例，然后给它挂上几个回调：onopen 在连接建立时触发，onmessage 在有数据到达时触发，onclose 在连接关闭时触发，onerror 处理连接层面的异常。连接一旦 open，就能随时用 ws.send() 发消息。有两个细节必须记住：协议前缀是 ws:// 与 wss://（带 TLS 的加密版本，生产环境用它）；onmessage 里拿到的 event.data 是字符串，如果对面发的是 JSON，你得自己 JSON.parse()。另外，在这些回调里想用外层的 this，记得写成箭头函数，否则 this 会指向别处。

不过，双向通道并不是所有场景都需要。如果业务只是「服务端单向播报」——比如股价推送、日志流、运营公告——那么另一套更轻的方案更合适：SSE（Server-Sent Events，服务端推送事件）。它走的就是一条普通的 HTTP 长连接，响应类型是 text/event-stream，服务端沿着这条连接不停地把事件推下来，客户端用一个 EventSource 对象接收即可。它的好处是简单，而且 EventSource 自带断线重连，你几乎不用管网络抖动；缺点也明确——只能服务端到客户端单向推送，客户端要上传数据还得另开普通请求。

所以选型其实是一句话：需要真正双向、低延迟的交互（聊天、协作、对战）用 WebSocket；只需要服务端单向播报、又想要省心的重连用 SSE。而且要注意，WebSocket 不像 EventSource 那样自动重连，一旦连接断开就得自己处理——生产环境里通常还要补上重连、心跳和消息队列这几件事：重连负责在断开后按退避策略重新连上，心跳负责及时发现「假死」的连接，消息队列负责把断线期间没发出去的消息暂存下来，等连上再补发。

连接事件次序

双向通道与单向推送

WebSocket 要解决的，是「服务端主动开口」这件事：用一次 HTTP 握手换一条一直开着的双向通道，把实时性从轮询的固定延迟里解放出来。当需求只是单向推送时，别忘了还有更轻的 SSE；而当选择了双向通道，也就意味着你要自己补齐重连、心跳和队列这些工程细节。

「WebSocket」是一种在 HTTP 升级握手后建立的持久、双向通信协议，使用 ws:// 与 wss:// 前缀，客户端与服务端可随时互发数据。用法是 new WebSocket(url) 并监听 open / message / close 事件，event.data 为字符串、JSON 需自行解析，回调中的 this 需用箭头函数捕获。与之相对的 SSE 是普通 HTTP 长连接（text/event-stream），仅由服务端单向推送但 EventSource 自带断线重连；WebSocket 则需自行实现重连、心跳与消息队列。

关键代码

JavaScript
// WebSocket：建立持久双向连接
const ws = new WebSocket('wss://example.com/ws')

ws.onopen = () => {
  // 连接建立后，可随时双向发送数据
  ws.send(JSON.stringify({ type: 'join', room: 'chat' }))
}

ws.onmessage = (event) => {
  const data = JSON.parse(event.data)
  console.log('收到消息：', data)
}

ws.onclose = () => console.log('连接关闭')

// 发送消息
ws.send('Hello Server!')

// Server-Sent Events（服务端推送，单向）
const eventSource = new EventSource('/api/stream')

eventSource.onmessage = (event) => {
  console.log('收到推送：', event.data)
}

eventSource.addEventListener('update', (event) => {
  console.log('更新：', event.data)
})

// 关闭 SSE
eventSource.close()
