环境变量与 next.config

掌握 NEXT_PUBLIC_ 前缀规则、env 文件优先级和 next.config.js 核心配置项。

开场问题：本地调得好好的，一部署到测试环境就连不上数据库——因为地址被我写死在代码里了；更吓人的是，有个密钥好像跟着前端一起打包出去了，在浏览器里就能搜到。

多环境配置差异

一个站点通常要跑好几套环境：本地开发、测试、预发、生产。它们的数据库地址不同、接口域名不同、统计标识不同，但代码只有一份。于是「配置」必须和「代码」分开，同一份代码在不同环境下读出不同的值。

这里还藏着一个前端特有的陷阱。同一段代码，有的跑在服务器上，有的会被打包发到用户浏览器里。能读到哪些配置，取决于这段代码跑在哪里；一旦把服务端专用的配置放到了会进浏览器的代码里，那就不只是「读不到」，而是直接把秘密公开了。

代码内写死配置

最简单的做法是把配置直接写在代码里：数据库地址、接口域名、密钥，全都硬编码。它确实「能用」，因为所有值都一目了然，不依赖任何外部文件。

这种做法唯一的优点是简单。但它把两个本该分开的东西——会变化的配置和相对稳定的代码——焊在了一起，代价是所有环境只能共用一套值。

硬编码暴露风险

  • 敏感信息随代码进入仓库，一旦仓库泄露或被协作者误看，风险不可控。
  • 切换环境要改代码再重新打包，容易漏改、也容易把测试值带上生产。
  • 前端打包产物里能搜到不该暴露的值，等于把密钥递给了用户。
  • 站点的行为配置（图片允许的域名、重定向规则、输出模式）散落在各处，没有统一入口。
  • 同一个变量在不同环境的名字与含义不一致，排查问题时要反复确认。

公开变量前缀

第一步是把配置挪进环境变量文件。项目根目录下放不同用途的配置文件，代码里通过统一的方式读取。但前端有个硬性规矩：只有带特定前缀（NEXT_PUBLIC_）的变量才会被内联进前端产物、允许客户端读取；不带前缀的变量只能留在服务端。

这条规则的含义要想清楚：加了前缀，等于主动声明「这个值可以公开，请把它打进浏览器能看到的代码里」。所以它适合站点地址、统计标识这类本就公开的值。密钥、数据库连接串永远不要加这个前缀，否则就等于把秘密印在了网页源码里。

第二步是理清多个配置文件的优先级。同名变量在不同文件里出现时，覆盖顺序是明确的：

  1. 本地覆盖文件优先级最高，通常也被版本控制忽略，用来放只属于你这台机器的敏感配置。
  2. 其次是按环境区分的文件（开发环境、生产环境各自一份），用来放各环境的差异值。
  3. 最后是通用文件，作为所有环境共享的默认值，优先级最低。

第三步是选对读取位置。在服务端的代码里可以直接读进程环境变量，把数据库连接、密钥留在这层；在客户端组件里只能读带前缀的变量，能不用就尽量不用。一个实用的思路是：把需要保密的逻辑留在服务端，只把最终结果传给客户端，这样客户端根本不需要碰任何敏感配置。

第四步是把站点级的行为配置集中到配置文件里。图片允许的域名、接口重写、旧地址重定向、输出模式、是否开启严格模式，都可以在这里统一声明，而不是散落到各个业务文件里。

一个最容易忽略的事实：这些变量是在构建时被替换进产物的。也就是说，一旦构建完成，再去改环境变量文件对已经打好的产物毫无作用，必须重新构建。所以上线流程里，「先设好环境变量，再构建」这个顺序不能颠倒。

变量去向与覆盖

配置注入与优先级

环境配置的核心只有两句话：配置和代码分开，服务端和客户端分开。用前缀决定一个变量能否公开，用文件优先级决定环境差异，用构建时机决定它何时生效。思路清楚了，就既不会把密钥送到用户手里，也不会再出现「本地好好的、线上连不上」。

「NEXT_PUBLIC_ 前缀」环境变量加上 NEXT_PUBLIC_ 前缀会被内联进前端产物、客户端可读；不加前缀则只在服务端可读。配置文件优先级为：本地覆盖文件 高于 环境专属文件 高于 通用文件。变量在构建时替换，构建后修改无效，必须重新构建；密钥等敏感值绝不可加前缀。

关键代码

JSX
// .env.local - 本地环境变量（不提交到 git）
// 仅服务端可用的变量（无 NEXT_PUBLIC_ 前缀）
DATABASE_URL=postgresql://user:pass@localhost:5432/mydb
SECRET_KEY=your-secret-key-here
API_KEY=sk-xxxxxxxxxxxxxxxx

// 客户端可用的变量（NEXT_PUBLIC_ 前缀）
NEXT_PUBLIC_SITE_URL=https://example.com
NEXT_PUBLIC_ANALYTICS_ID=G-XXXXXXXXXX

// ============================================

// .env.development - 开发环境
NODE_ENV=development
NEXT_PUBLIC_API_BASE=http://localhost:3000/api

// .env.production - 生产环境
NODE_ENV=production
NEXT_PUBLIC_API_BASE=https://api.example.com

// ============================================

// env 文件优先级（从高到低）：
// 1. .env.local - 本地覆盖（最高优先级）
// 2. .env.[environment] - 环境特定（development/production）
// 3. .env - 默认值（最低优先级）

// ============================================

// 服务端使用环境变量
// app/lib/db.ts
import { PrismaClient } from '@prisma/client'

// 直接使用，不会暴露到客户端
const prisma = new PrismaClient({
  datasources: {
    db: {
      url: process.env.DATABASE_URL,
    },
  },
})

// ============================================

// 客户端使用环境变量
// 必须有 NEXT_PUBLIC_ 前缀
'use client'

export function Analytics() {
  // NEXT_PUBLIC_ 前缀的变量可以在客户端使用
  const analyticsId = process.env.NEXT_PUBLIC_ANALYTICS_ID

  return (
    <div>
      <p>Analytics ID: {analyticsId}</p>
    </div>
  )
}

// next.config.js - 完整配置示例
/** @type {import('next').NextConfig} */
const nextConfig = {
  // React 严格模式
  reactStrictMode: true,

  // 图片配置
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname: 'images.example.com',
      },
    ],
    formats: ['image/avif', 'image/webp'],
  },

  // 重写规则
  async rewrites() {
    return [
      {
        source: '/api/:path*',
        destination: 'https://api.example.com/:path*',
      },
    ]
  },

  // 重定向规则
  async redirects() {
    return [
      {
        source: '/old-path',
        destination: '/new-path',
        permanent: true, // 308 永久重定向
      },
    ]
  },

  // 自定义页面扩展名
  pageExtensions: ['ts', 'tsx', 'js', 'jsx'],

  // 输出模式
  // output: 'standalone', // Node.js 自托管
  // output: 'export',     // 纯静态导出
  // output: undefined,    // 默认（Node.js 服务）

  // 压缩
  compress: true,

  // 构建指示器
  devIndicators: {
    buildActivity: true,
    buildActivityPosition: 'bottom-right',
  },
}

module.exports = nextConfig
