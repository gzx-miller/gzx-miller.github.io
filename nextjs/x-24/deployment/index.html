部署与 Vercel

掌握 Vercel、Node 自托管、Docker、静态导出四种部署目标的特点与配置。

开场问题：本地构建完，我把整个文件夹传上服务器，站点却起不来——有人告诉我「不能直接当静态文件跑」，那我到底该把哪些东西部署上去？

产物托管可行性

项目终于写完了，接下来是把它放到线上。你按着「前端构建完就是一个文件夹」的直觉，把产物打包传上去，用静态服务器一托管，结果页面要么空白、要么报错。困惑来了：同样一个项目，为什么有的人说「推送即上线」，有的人却在折腾服务器、镜像和反向代理？

关键在于：Next.js 不是一个只在浏览器里跑的静态站点。它有服务端渲染、表单提交、接口处理这些需要「服务器参与」的能力。能不能用一个静态目录托管，取决于你的项目到底用没用这些能力。所以要选部署方式，先得回答一个问题——我的项目需要服务器吗。

构建产物直传

最省事的做法是：本地构建出产物，把产物整个目录扔到任意静态托管上，配个域名就完事。对纯静态项目，这确实可行，而且便宜、稳定。

但它默认了一个前提——所有内容都能在构建时算好，运行时不需要任何服务端逻辑。一旦项目里有需要按请求处理、或按用户身份变化的部分，这个前提就崩了。

纯静态托管边界

  • 服务端渲染、表单操作、接口处理这些能力需要 Node 服务，纯静态托管根本接不住。
  • 想自己托管时，产物里并不直接包含运行所需的一切，静态资源要额外搬运，容易漏。
  • 环境变量、域名、HTTPS、缓存这些都得自己配，漏一项线上就出问题。
  • 「纯静态导出」听起来万能，其实会禁掉一批动态能力，构建时才会暴露。
  • 没有健康检查与回滚预案，一旦上线出问题只能手忙脚乱地改。

部署目标取舍

与其死记某一种做法，不如先认清四种部署目标各自适合什么，再按项目需要挑一种。

部署目标运行方式特点与适用
官方托管平台全托管零配置、自动构建部署，支持全部特性，生产环境首选。
Node 自托管独立产物 + 启动脚本用独立产物模式构建，输出自带运行时，需自行搬运静态资源与公共目录，适合自有服务器。
容器化镜像基于独立产物做多阶段构建，适合云原生环境与统一交付。
纯静态导出静态文件导出为纯 HTML，可放任意静态托管，但有明显能力限制。

自己托管时，需要额外付出、也最容易出错的一步是：独立产物并不包含运行所需的全部文件。它生成了一个最小的运行时和依赖，但静态资源与公共目录要你手动搬运到约定位置。漏了这一步，表现往往就是「服务起来了，但页面没样式、图片全挂」。

容器化则是在自托管之上再包一层：分阶段构建，先在构建阶段装依赖并构建，再把独立产物和静态资源复制进一个干净的运行阶段，最后用一个非特权用户启动。这样镜像小、职责清晰。

纯静态导出是最需要警惕的一种：代价是一批动态能力直接不可用——表单服务端操作、中间件、按需图片优化、按请求渲染、增量再生成都会失效，图片优化也要显式关闭。所以它只适合内容在构建时就完全确定的站点，比如纯展示的文档站或营销页。

无论选哪种，上线前都有一份共同的检查清单：把生产环境变量配齐、绑好域名并开启 HTTPS、给静态资源配置缓存、接入日志与错误上报、准备好健康检查与回滚方式、为站点提供站点地图与爬虫规则。

一个常见的判断错误：很多人先选了「静态导出」图省事，开发到一半才发现某个表单提交、某个按用户变化的页面做不了，只能推倒重来。正确顺序是先梳理功能需要哪些能力，再倒推部署目标，而不是先定目标再削功能。

四类目标能力对照

按服务端能力选型

部署的决策点只有一个：项目是否需要服务端能力。需要就交给全托管平台、自托管 Node 或容器；不需要才考虑纯静态导出，并接受它的能力限制。选之前先看功能清单，选之后补上环境变量、域名与监控。

「部署目标」Next.js 支持多种部署方式：官方平台全托管、零配置且支持全部特性；Node 自托管用独立产物模式，需自行搬运静态资源和公共目录；容器化基于独立产物做多阶段构建；纯静态导出生成纯 HTML，可放任意静态托管，但不支持表单服务端操作、中间件、按需图片优化与按请求渲染等动态能力。

// 1. Vercel 部署（推荐）
// 零配置，支持所有 Next.js 特性
// 步骤：
// 1. 连接 Git 仓库（GitHub/GitLab/Bitbucket）
// 2. 配置环境变量
// 3. 自动部署，每次 push 自动更新

// vercel.json - 可选配置
{
  "buildCommand": "next build",
  "devCommand": "next dev",
  "installCommand": "pnpm install",
  "framework": "nextjs"
}

// ============================================

// 2. Node.js 自托管（output: 'standalone'）
// next.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'standalone', // 生成独立部署包
}

module.exports = nextConfig

// 构建命令：
// pnpm next build
// 生成的 .next/standalone/ 目录可独立运行
// 需要复制 public/ 和 .next/static/ 到对应位置

// 启动命令：
// node server.js
// 或
// node .next/standalone/server.js

// ============================================

// 3. Docker 部署
// Dockerfile
FROM node:20-alpine AS base

# 安装依赖
FROM base AS deps
WORKDIR /app
COPY package.json pnpm-lock.yaml* ./
RUN corepack enable && pnpm install --frozen-lockfile

# 构建
FROM base AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN corepack enable && pnpm next build

# 运行
FROM base AS runner
WORKDIR /app

ENV NODE_ENV=production

RUN addgroup --system --gid 1001 nodejs
RUN adduser --system --uid 1001 nextjs

# 复制 standalone 输出
COPY --from=builder /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

USER nextjs

EXPOSE 3000

ENV PORT=3000
ENV HOSTNAME=0.0.0.0

CMD ["node", "server.js"]

// .dockerignore
node_modules
.next
.git
.env.local
.env*.local

// ============================================

// 4. 静态导出（output: 'export'）
// next.config.js
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'export', // 纯静态导出
  images: {
    unoptimized: true, // 静态导出需要关闭图片优化
  },
}

module.exports = nextConfig

// 构建命令：
// pnpm next build
// 生成 out/ 目录，包含所有静态文件

// 部署：
// 把 out/ 目录上传到任何静态托管服务
// Vercel / Netlify / GitHub Pages / Cloudflare Pages / Nginx

// 静态导出限制：
// - 不支持 Server Components 的动态特性
// - 不支持 Server Actions
// - 不支持 Middleware
// - 不支持 Image Optimization（需 unoptimized: true）
// - 不支持 Route Handlers（API Routes）
// - 不支持 Incremental Static Regeneration
